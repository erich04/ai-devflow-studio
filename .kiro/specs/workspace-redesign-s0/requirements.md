# 需求文档：工作区改造 S0 基线与核实

## 简介

本 spec 对应[工作区改造方案](../../../docs/plans/task-centered-workspace-redesign-2026-09-28.zh-CN.md)（第 4 版）第 7 节的 S0 批次。S0 不改产品代码，交付三样东西：

1. 可重复运行的首屏测量脚本，以及改前基线；
2. S1 验收要用的状态样例；
3. 方案 2.3 节待验证项的结论。

S1 的量化验收、D3/T4 的文案和 P1 的确认框都以这些结果为前提。

不在范围内：产品界面、写入路径、同步规则和数据库结构的任何改动；真实模型调用；远端发布。

术语：

- **内容区**：Electron 窗口的网页内容区域，即 CSS 视口，以左上角为原点。
- **状态样例**：在隔离环境中按固定步骤制备的任务页状态。“冻结”指样例定义与制备脚本固定并入库，每次运行重新制备，不提交用户数据快照。

## 需求

### 需求 1：首屏测量脚本

**用户故事：** 作为改造负责人，我希望用一条命令在真实 Electron 窗口中测量任务页首屏，以便 S1 前后在相同条件下对比。

#### 验收标准

1. 当运行测量命令时，脚本应在系统临时目录中创建隔离的用户数据目录、数据环境注册表和示例 Git 仓库，并自行启动使用内存存储、独立端口的演示 Team API 与确定性模拟运行时。
2. 脚本不得读写默认用户数据或已有数据库，不得调用真实模型，不得依赖开发者已启动的 Vite、API 或 Web 服务。
3. 当测量一个样例时，脚本应输出方案 2.2 节的全部指标：状态行底部位置（改前以节点头部底部作对照）、默认页签首个正文区块的顶部位置、顶栏与状态条总高度、顶栏与状态条中的控件数、视口内可交互控件数、“当前位置”相关表达的出现次数、主区渲染字号的种类与最小值、讨论栏宽度、各阶段标签是否被截断。
4. 统计字号时，脚本应以文本节点为单位，按文本节点自身的矩形判断是否位于内容区内且可见；混合内容元素中的文本也要计入，滚出视口或隐藏的文本不计入。
5. 统计控件时，脚本应只计入内容区内可见的 button、带 href 的链接、tab、input、select、textarea、summary，并输出每个控件的可读名称，便于人工核对。
6. 当测量完成时，脚本应把指标与环境信息写入 JSON，并保存同一时刻的截图。环境信息包括内容区尺寸、设备像素比、页面缩放、主题、代码提交、Electron 与 Node 版本、样例 ID 和生成时间。
7. 如果内容区的实际尺寸与请求不一致，脚本应记录实际尺寸，并把该次测量标记为无效。
8. 脚本不得修改产品代码或产品配置。测量需要低于窗口最小尺寸时，只在测量进程内临时调整。
9. 当脚本结束或失败时，应关闭它启动的 Electron 与 API 进程；默认删除临时目录，调试时可以保留。

### 需求 2：三档内容区尺寸

**用户故事：** 作为改造负责人，我希望三档内容区尺寸固定且可复现，以便验收覆盖常见宽度。

#### 验收标准

1. 主基线应为 1440×742。另两档宽度为 1280 与 1024，高度在真实 Electron 窗口中确定，并写入脚本默认配置与基线报告。（2026-09-28 确定：三档高度都为 742，即 1440×742、1280×742、1024×742。）
2. 当某一档低于主进程窗口的最小尺寸（当前为 1180×760）时，脚本应在测量进程内临时放开最小尺寸，并在记录中注明这一点，以及它对应的用户场景：放大页面后的等效宽度。
3. 基线报告应写明测量机器的屏幕可用区域和系统缩放。换一台机器复测时，应先确认三档尺寸都能实际达到。
4. 需求确认 Gate 的常规场景应在三档尺寸下各测一次数字指标。主基线另存深色主题和 200% 页面缩放的截图，这两种情况不计入数字目标。

### 需求 3：状态样例

**用户故事：** 作为改造负责人，我希望 S1 验收用到的每个起始状态都能在隔离环境中重复制备，以便改前改后的截图取自同一样例。

#### 验收标准

1. 样例集应覆盖六个阶段，每个阶段一个常规状态：需求确认 Gate、方案评审 Gate、开发实现、测试验证、PR 交付、业务验收。
2. 样例集应包含方案 8.1 节验收需要的起始状态：
   - Gate 可审批的三种情况：缺少门禁审查且策略仅警告、已有审查只剩非阻断建议、没有建议；
   - 强制阻断；等待上游；需求有 v1、v2 两个版本并可阅读历史版本；
   - 执行中（可停止）、待处理的权限请求、执行失败或中断；
   - 未连接团队、已连接团队、已有凭据（用于重新配对确认），以及方案 6.5 节结果上传的五种情况；
   - 方案 6.4 节测试证据的七种情况；
   - 空讨论和有消息的讨论。
3. 每个样例都应能用一条命令重新制备，同一输入得到同一状态。瞬时状态（执行中、测试执行中、待处理的权限请求）由脚本现场制造，状态稳定后立即截图。
4. 样例清单应记录每个样例的 ID、对应的方案条目、制备方式（真实界面、IPC 快进、直接写入本地存储、仅渲染层夹具）、是否使用模拟，以及已知局限。按方案 8.3 节，用 IPC 或直接写入准备的样例只用于布局对比，不作为用户路径的证据。
5. 每个样例都应在主基线尺寸下保存改前截图。
6. 如果某个状态无法在真实 Electron 窗口中制备，清单应写明原因和替代验证方式（例如渲染层组件测试），不得用其他状态顶替。
7. 样例制备只能依赖脚本自己启动的服务，不得依赖测量机器上已有的数据、凭据或网络服务。

### 需求 4：待验证项核实

**用户故事：** 作为改造负责人，我希望方案 2.3 节的待验证项都有明确结论，以便 S1 的文案和确认框按事实设计。

#### 验收标准

1. 方案 2.3 节“待验证”的七项应逐项给出结论、依据（代码位置、运行记录或两者）和置信度。运行得出的结论应写明步骤和所用样例。
2. D3 应记录未绑定项目下终止记录的实际错误码，并区分“没有任何凭据”与“其他本地项目已配对”两种情况。
3. “拉取后团队数据仍为空”一项必须通过正常绑定表单重做。
4. 当某项结论改变方案 6.5 节、P1 或 S1 改动清单的前提时，应同步修订方案，并在修订记录中说明；结论与方案一致时，只把 2.3 节的待验证项改写为结论。
5. 所有结论都应在隔离环境中得出，不使用已有用户数据。

### 需求 5：基线记录与交付

**用户故事：** 作为评审人，我希望基线结果集中存放且可追溯，以便 S1 评审时直接对照。

#### 验收标准

1. 基线应存入仓库：报告放在 `docs/validation/`，指标 JSON、样例清单和截图放在 `docs/validation/evidence/` 下的同名目录。截图沿用仓库现有的 JPG 格式，按 CSS 像素保存以控制体积。
2. 基线报告应汇总三档尺寸下的指标、样例清单和待验证项结论，并标明哪些结果来自模拟、哪些样例用 IPC 或直接写入准备。
3. 方案 2.2 节的“现状”列应按基线更新，包括状态行对照、首个正文区块位置和字号复测，并在方案修订记录中说明。
4. 截图与 JSON 不得包含凭据、配对码或令牌。本机路径只允许出现脚本创建的临时目录。
5. 新脚本应加入 `scripts/check-cross-platform.mjs` 的检查：不硬编码 `/tmp/`，使用 `os.tmpdir()` 与 `path.join`，Windows 下解析 `corepack.cmd`。`corepack pnpm verify` 应通过。
6. S0 完成后，方案的状态行应注明 S0 已完成，并链接基线报告。
