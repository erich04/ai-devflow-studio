# ADR 0028：原生会话与可恢复的讨论提案

- 状态：已接受，落实 #231 的后续设计
- 日期：2026-10-10（America/Chicago）
- 关联：[ADR 0027](0027-request-recovery-and-budget-continuation.md)、[#231](https://github.com/erich04/ai-devflow-studio/issues/231)

## 问题与决定

原有独立对话要求普通回答、工具决策、追问和完整提案都放在回答正文的 JSON 对象里。模型即使已完成调查，也可能因外层 JSON 不符合约定而丢失答复；候选生成与核对耦合，使核对失败后的内容难以继续使用。

新版 Direct Provider 对话将普通 Markdown、原生工具调用和候选提案分别处理。只在经验证的官方 DeepSeek `deepseek-flash` 上启用。模型输出正文中的 JSON 示例不会被解释为命令。正式阶段生成、门禁报告、编码器和 OpenCode 对话继续使用各自契约。

## 消息与工具

提供方返回 `text` 或 `tools` 两种结果。普通答案直接显示；工具必须来自 API 的 `tool_calls`，经过身份、名称、参数、项目和路径校验后才执行。读取批次最多 16 项，整批先校验再顺序执行；没有 Shell、写代码、批准 Gate 或发布能力。

复用现有只读查询，并提供三个单独调用的业务函数：

| 函数 | 作用 |
| --- | --- |
| `prepare_revision` | 读取目标的完整原始需求、已保存提案和当前正式材料，生成来源回执。 |
| `propose_revision` | 将完整候选正文落盘，随后由宿主独立核对。正文无需再复制进普通答案。 |
| `request_user_input` | 保存具体问题及选项，等待用户回答。 |

工具调用 ID 在会话内唯一，每条调用只对应一条结果。正文、工具历史和必要的 `reasoning_content` 原样保存在私有协议记录中；渲染进程只取得可阅读预览。工具结果与检查点一次写入；重启、手动重试或更换受支持 Provider 时从持久历史恢复尚未配对的调用，复用已经持久化的查询结果。损坏配对停止请求并显示明确诊断。

参数错误和不存在的目标允许模型在本步骤内修正两次；跨项目、路径越界及符号链接拒绝整批执行。每个成功步骤重置自动恢复次数；每次真实请求独立经过预算预留和结算。失败但有用量的请求仍计费，未知费用不作零处理。

## 候选保存与人工继续

候选正文及来源回执先原子落盘，再发起独立语义核对。核对输入包含原始需求、既有约定、当前正式材料、候选正文及生成候选的那条用户请求。核对用 `report_proposal_review` 逐项报告覆盖、遗漏或矛盾，宿主核验条件 ID 完整性；不存在正文 JSON 降级路径。

用户批准以下保存规则：

| 核对状态 | 用户可执行的动作 |
| --- | --- |
| 通过 | 保存为关联节点的待评审讨论提案。 |
| 有遗漏/矛盾，或核对超时、失败、中断 | 查看候选与意见；重新核对同一候选，或明确勾选人工确认后保存为尚未通过 AI 核对的待评审提案。 |
| 来源已变 | 重新生成候选，不能以人工确认绕过来源校验。 |

保存不调用模型，不替换正式材料，不推进 Run，也不批准 Gate。产物记录实际核对状态、意见和人工确认时间，不能将人工保存写成“AI 通过”。保存条件由主进程检查，SQLite 串行持久化写入时再检查当前来源回执，覆盖来源更新与发布交错的情况。重复保存按候选 ID 幂等。

核对重试始终针对同一候选、原用户请求与当前来源。重启将未完成核对标为可恢复的未完成状态；后续存储异常不降级已经完成的核对结论。

## 容量与上下文

宿主预检、Provider 预检和实际发送使用同一份请求序列化，包括 system、工具定义、完整消息、Thinking、`tool_choice` 和输出参数。Token 仍使用保守估算，并为输出和协议开销留余量；这不是精确 tokenizer，也不代表无界上下文。

超限时只在完整工具配对边界压缩模型可见历史，重新装入当前请求、项目事实、有效记忆和必要来源。完整原文及旧 Thinking 历史仍可回读，窗口边界持久化。关键材料本身仍放不下时停止发送、明确提示缩小范围，已生成候选可供人工阅读保存。工具参数总量使用正文接收容量，读取参数仍受既有小参数约束。

中断期间已接收的正文保存为“不完整参考”，不伪造为已完成助手消息回放。传输诊断和用量与私有原文分别保存。

## 启用、兼容与回滚

新建 Direct Provider 对话在首次选择 Provider 时绑定协议：官方 DeepSeek 精确模型 ID `deepseek-flash` 使用 v2；未支持组合继续原路径。绑定后不因一次失败静默改协议或改模型。旧对话未增加绑定标记，保持原协议、材料和进度；要使用新版，需要新建独立对话，仍可查询同一个项目和任务。

Electron 默认启用 `DEVFLOW_NATIVE_CONVERSATIONS_ENABLED`，设为 `0` 可回滚新能力。回滚后 v2 记录、草稿和候选可读，停止新执行，不把其历史伪装成旧 JSON 重放。旧的 `DEVFLOW_NATIVE_READONLY_PILOT_ENABLED=1` 保留隔离兼容测试入口；未开启新版时才在 UI 显示试点选项。

官方 flash 的 Thinking 关闭/low/high/max、流式/非流式均已做真实端点验证。DeepSeek Pro、别名、第三方兼容端点及其他提供方不在这一兼容承诺内。详见[验证记录](../validation/issue-231-native-conversation-20261010.md)。

## 顾问意见处置

Cursor 的两项实质发现均接受并修复：工具结果与检查点原子保存/幂等恢复，以及发布时的来源并发校验。额外接受完整请求度量、未知 ID 修正、核对终态保留与退出恢复提示。

聚焦复核确认上述两项已修复，并指出发布完成后的排队核对可能覆盖原核对状态。该风险也已接受：`retry_review` 在串行更新中再次确认候选尚未发布，交错测试证明不会覆盖已保存状态或再次调用模型。顾问未执行测试；结论采用宿主实测与代码证据。

`operation.version` 在同一用户轮次内仍稳定；当前允许的官方 flash 使用全上下文上界预留，不会因后续工具历史变长少预留费用。开放其他模型前需重新评估请求版本与预算边界。部分输出不加入已完成协议历史是有意设计：原文保留并可回读，但不宣称请求成功。
