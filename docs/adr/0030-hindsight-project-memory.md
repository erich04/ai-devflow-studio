# ADR 0030：项目记忆由 Hindsight 自动学习，DevFlow 负责采集、范围和预算

日期：2026-10-28。状态：已接受。第一期（采集、发件队列、模型中继）和第二期（召回注入、`memory_search`）已实现；记忆页、旧候选链路移除和知识页面分期实现，见文末。

## 背景

ADR 0024 第 4、5 节让 Coding Run 产出「记忆候选」，再按规则或人工晋升为正式记忆；2026-10-22 的[记忆共享与学习计划](../plans/memory-sharing-and-learning-2026-10-22.zh-CN.md)把讨论、阶段产物也接入这条候选链路，并增加「业务规则待确认」队列。ADR 0027 只把正式记忆以影子模式送进 Hindsight。实际使用中有三个问题：

- 用户要逐条审候选，记忆几乎不会自然增长。
- DevFlow 自己做抽取、去重、冲突判断，与 Hindsight 已有的抽取、实体解析和观察归纳（observation consolidation）重复，而且质量更差。
- 抽取模型由 Hindsight 部署自行配置，不经过项目预算。

Hindsight 官方的编码 Agent 接入（Claude Code、Codex 插件）和 Codex/Claude Code 自身的记忆做法相同：按会话或任务整段写入，由记忆系统在后台抽取和归纳，召回时自动注入，不需要人工批准每条记忆。

## 决定

1. **记忆只存在 Hindsight。** 每个项目与记忆归属用户对应一个 bank：`df-memory-<sha256([projectId, ownerUserId]) 前 32 位>`。配对用户改变时换新 bank，不混用两人的记忆。没有配置 Hindsight 就没有项目记忆。本地只保存开关和发件队列，不再保存候选或修订。
2. **自动采集，整段写入。** 宿主在来源提交的同一个持久化变更里登记文档，后台按 15 秒周期发送：
   - 讨论：整段公开对话（用户和助手消息），一次一个文档 `conversation:<id>`。空闲 3 分钟后发送，之后每轮更新替换同一文档。不含推理内容、工具输出和注入的上下文。
   - 编码：每个结束的 Coding Run（成功、失败、取消都算，`fake` 引擎除外）一个文档 `coding-run:<id>`：用户请求、给 Agent 的说明、结果、改动文件、Agent 活动摘要。DevFlow 自己运行的测试标为 `HOST_VERIFIED`，Agent 的说法标为声明。不含 Brief（避免把召回内容再写回去）。
   - 阶段产物：审批通过时记录被批准的澄清版本、设计和验收包；Gate 评审结果在保存时记录，标为评审意见而非决定。草稿不记录。
   - 统一限制：每个文档最多 48 KiB，超出时丢弃最早的消息或活动；写入前脱敏；不发送完整文件。
3. **Hindsight 负责抽取和归纳。** 发送使用 `update_mode: replace`、`observation_scopes: shared`。bank 配置开启观察归纳和自动 consolidation，抽取模式 `concise`，并写入 retain/observations/reflect 三段任务说明（`PROJECT_MEMORY_MISSIONS`）。DevFlow 不做逐条抽取、去重或冲突判断。
4. **抽取模型调用经过 DevFlow 中继，计入项目预算。** Hindsight 只持有中继令牌，不持有 Provider 密钥：
   - 中继监听本机 `127.0.0.1:8891`（`DEVFLOW_MEMORY_RELAY_PORT`，Linux Docker 可用 `DEVFLOW_MEMORY_RELAY_HOST` 指定网桥地址），校验 Bearer 令牌。令牌首次启动时生成，保存在 userData 的 `memory-relay-token`（权限 0600），也可由 `DEVFLOW_MEMORY_RELAY_TOKEN` 指定。
   - Hindsight 开启 `HINDSIGHT_API_LLM_SEND_BANK_AS_USER`，用 OpenAI `user` 字段带上 bank id。中继据此找到项目，转发前删除该字段。
   - 只有已配对团队项目、项目记忆已开启且归属一致时才放行；同项目当前的仓库知识 bank（ADR 0027）也走同一路由。每次调用通过 `governedModelCall` 预留和结算，没有预算续期提示；拒绝时返回 429，未配对或无法读取预算时返回 403，均不调用模型。
   - DeepSeek 关闭 thinking，单次输出上限 8192 tokens。
5. **配对与默认值。** 开启项目记忆要求项目已配对团队项目，并已保存所选 Provider 的凭据。配置绑定组织、团队项目、本地项目、用户和认证账号，任一变化后停止采集和放行，需要重新开启。已有项目不自动开启。
6. **业务规则只来自已批准的流程产物。** 记忆是背景资料，不能授权，不能覆盖当前请求或已批准产物，不作为 Gate 证据。取消「业务规则待确认」队列（第四期移除代码）。
7. **用户可以删除。** 删除先让本地文档立即失效、清空正文，再删除 Hindsight 中的文档；正在执行的写入结束后才算删除完成。同一来源之后的新版本不会把已删除的文档带回来。

## 召回

- 编码简报、阶段 Agent、Gate 评审和讨论栏在项目记忆开启时，从项目 bank 召回（`observation` 优先，同一事实不重复给出），不再查询本地记忆；未开启的项目保持原行为，直到第四期迁移。召回只检索，不调用模型。
- 查询沿用各入口原有的查询文本（截断到 1.5 KiB），结果按各入口原有的条数和字节预算选取，不拆分单条记忆。每条写成一行，带类型和日期，例如 `[observation] …`、`[fact 2026-10-20] …`，作为低信任背景，规则与 ADR 0024 第 3 节相同。
- 回执沿用原格式：`pm-<Hindsight id>`、revision 1、所发送文本的摘要。发送前（讨论、评审）和编码继续前都会检查项目记忆仍开启且归属未变，否则停止并要求用当前上下文重来。单条记忆被删除后的检查在第三期随删除功能加入。
- Hindsight 不可用时按「没有记忆」继续，不阻断任务，并记录一次降级日志。
- 讨论栏新增只读工具 `memory_search({query, limit≤8})`，Direct、OpenCode（MCP）和原生工具三种执行方式共用。没有加 `memory_save`：讨论工具保持只读，整段讨论本来就会自动写入记忆，用户说「记住……」的那句话会被 Hindsight 抽取。Native Coding v3 的 `memory_search` 在 v3 合并到 main 后接入。

## 发送与重试

- 每次写入使用固定的 operation id。提交被 4xx 拒绝时计一次尝试，换新的 operation id；共 3 次后标为 `failed`。
- 超时或传输失败时不重发，改为查询 operation：查不到（Hindsight 从未收到）用同一 operation id 重发且不计次；仍在处理则继续查询。
- 中继未运行时暂停新的发送（否则抽取必然失败并消耗尝试次数），查询和删除照常进行。
- 进程崩溃后，持有租约的文档改为查询，不盲目重发。

## 被替代的内容

- ADR 0024 第 4 节（从 Coding Run 提取候选）和第 5 节（去重与策略晋升）。
- ADR 0027 中正式记忆以影子模式投影到 Hindsight 的规则。
- 2026-10-22 记忆共享与学习计划中的候选、自动确认和业务规则待确认部分。

第一期期间旧链路仍在代码中：对已开启项目记忆的项目，旧候选链路不再采集。

## 影响

- 记忆增长不再需要人工操作，质量取决于 Hindsight 的抽取和任务说明；第五期用真实模型验证。
- 抽取和归纳会产生模型费用，按调用计入团队项目预算。
- 未配对的本地项目暂时没有项目记忆。
- `deploy/hindsight/compose.yaml` 默认把模型地址指向中继；没有令牌时所有调用被拒绝，不产生费用。
