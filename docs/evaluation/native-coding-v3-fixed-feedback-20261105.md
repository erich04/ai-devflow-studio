# Native Coding v3 固定验收反馈模式

2026-11-05，用户明确选择“给失败反馈，让 V3 继续修，先跑通十题”。下一轮使用宿主冻结的原验收用例，把实际失败原因返回 V3，允许它在原有额度内继续修改并重新提交。该模式单独记录，既有盲测结果保留。

## 实现范围

- 原十道题的题面、基线、公共测试命令、参考验收文件及模型配置保持原值。每题最多 15 分钟、80 步、192 次调用，单次输出上限 65,536 token，整轮费用上限为 2.70 美元。
- 宿主接收按原文件路径和内容摘要冻结的测试包，绑定本次目标、批准来源和基线。模型无法通过编码工具替换这份测试包。目标变更后需要重新绑定验收来源，当前任务会暂停。
- 固定模式直接使用这份测试包。原生成式私有验收路径继续服务未提供固定测试的任务。
- 每份修订在分别拥有的验证目录里运行公共测试与固定测试。固定测试目录从该修订的精确内容生成，恢复基线的测试配置并覆盖原固定验收文件。固定测试由实际 Vitest 入口运行，完整报告由宿主留存。模型收到文件名、失败用例和有长度限制的错误信息。
- 必须执行全部指定文件，实际用例数必须等于原资格记录的数量，所有用例通过，运行期间源码保持一致，才允许完成交付。测试跳过、模块加载错误、缺失报告、失败或取消均不能放行。
- 固定模式允许超过三次失败后继续修复，共享原任务步数、活动时间、墙钟和费用限制。可信基线的依赖准备也计入本次限时。最终独立外部评分继续分别观察交付 D 和候选 C。

宿主测试包属于评测适配器提供的可选输入。本次沿用正常 V3 会话、权限、工具、修订审批和事务交付入口。

## 回归覆盖

新增实际 Node、Vitest、SQLite 和 Git 路径测试，模型端使用确定性替身，依赖安装复用本地测试框架。

- 连续四次固定验收失败后，模型收到具体原因并修改代码。重启后仍按持久化的同一测试包验证，通过后才交付。
- 候选修改测试文件或运行配置，固定验收仍使用批准版本。
- 跳过用例、数量不符、模块加载失败和验证过程修改源码均被拒绝。
- 原步数限制仍生效。依赖准备耗尽活动时间时中止进程，模型尚未调用。
- 运行中的固定测试可以取消，验证进程结束后清理副本，原交付保留。
- 测试包内容不可替换，新的目标不能复用旧验收。默认生成式验收继续执行自己的既有回归。

本地 Node.js 24.18.0 下 `corepack pnpm verify` 通过，包含所有类型检查、5,762 项通过、22 项跳过和跨平台检查。十题测试包均已从原参考提交提取并通过路径、内容摘要及容量校验，用例数量依次为 81、339、111、46、215、3、51、320、7、17。

## 失败反馈的上下文

R11 的 02 题三次固定验收均停在 80/81。回传信息包含用例名和 `expected 2 to be 4`，但缺少计数器及模拟请求的准备代码。V3 随后修改了 Native pending 工具恢复，原测试实际通过 structured 提供方驱动模型请求失败后的自动恢复。它在最终报告中明确指出，无法从现有反馈判断断言统计的对象。

据此，后续固定模式反馈补充失败用例的批准源码摘录。宿主根据堆栈行号及已有 Vitest 夹具定位器找到对应测试，返回准备、操作和断言，并附原文件摘要。单份摘录最多 6,000 字符，长用例限制在失败位置附近，全部反馈继续做敏感信息脱敏。用例仍按原冻结内容执行，初次模型请求只接收任务和验收元信息。

新增回归通过实际 Vitest 制造次数断言失败，确认模型收到计数器、structured 设置及确切断言，其他通过用例的标记没有进入反馈。包含旧生成式验收的 27 项定向回归通过。随后本地全量验证通过 5,764 项、跳过 22 项，类型与跨平台检查通过。改动在隔离工作副本完成，R11 继续按自己的冻结版本运行。

真实十题结果以后续冻结运行的外部 D 评分为准。同轮十题全部交付通过且零误报仍是完成条件。

## 两组验证并行

R11 的 03 首次验证从 `07:47:39.772Z` 到 `07:51:14.405Z`，共约 215 秒。公共验证的依赖准备及测试耗时约 40、48 秒，固定验证的依赖准备及测试又用了约 39、14 秒。两套独立副本串行执行，占用了原 15 分钟中的修复窗口。

后续固定模式同时执行这两组验证，共用原活动时钟、墙钟截止时间和取消信号。每组继续拥有独立源码及可写依赖副本，分别校验原冻结配置。宿主收齐两边结果以后决定交付，任何一组失败都会拒绝完成。公共测试失败时，固定用例的具体失败信息仍可进入修复反馈。

固定验证清理只终止自己的依赖和测试命令，随后删除自己的副本。另一组验证继续由原宿主管理。回归通过真实 Node 进程证明两组确实重叠，公共测试失败时无法交付，并验证一侧准备抛错后仍等待另一侧结束及清理。

两项并行回归在修改前失败，修改后通过。本地全量验证为 5,767 项通过、22 项跳过，类型和跨平台检查通过。真实题目的耗时及交付效果继续以后续完整运行记录为准。
