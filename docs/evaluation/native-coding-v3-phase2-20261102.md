## 失败定位与补丁范围

- 02 的 `search_text.contextLines` 连续为 10/6、8，schema 上限是 5；06 的 `read_command.waitMs` 为 120,000、180,000，上限是 30,000。原反馈只有无效工具批，模型没有得到具体纠正依据。#298 增加字段路径和约束，例如 `read_command $.waitMs must be <= 30000`；不回显参数值、不截断参数，也不放宽授权或失败上限。
- 04 的独立作者请求 HTTP 200，但 `finishReason=length`，65,536 输出 token 全部用于思考，没有正文或检查工具调用，故暂停并记入已知费用。没有当作未交付重试。
- 03 和 05 已能跑过公开测试，却因私有检查失败暂停；仅返回 `objective` 过于粗糙，无法指导有界返修。独立检查摘要与公开测试计划摘要本来是不同对象，模型把两者当成同一计划也是当前反馈的局限。
- 07 到达 15 分钟上限，11 在私有检查失败后达到 80 步上限。其他题的确切停止类别与原始文件摘要见结果 JSON；不把所有失败都归因于一个补丁。

03、05、07、11 四题进入了产品内独立检查，均记录失败，均未提交第二份返修修订（`repairAttempts=0` 的统计口径是新增修订数，不代表模型没有尝试修改）。除了检查可靠性，还需为验收/返修预留步骤和时间；确定性测试覆盖两轮返修，不等于真实任务已经有效完成两轮。
