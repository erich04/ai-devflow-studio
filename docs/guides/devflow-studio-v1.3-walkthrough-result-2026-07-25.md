# DevFlow Studio v1.3 演练结果 - 2026-07-25

> 历史审计记录：以下结论对应 2026-07-25 的基线与隔离演练，不代表当前版本。保留当时的失败、未验证范围和逐字界面证据；当前发布状态由路线图统一维护。

本报告用于回答三个问题：

1. 项目当前进展到哪里；
2. 功能是否已经完整；
3. 下一步应按什么顺序演进。

本轮以文档更新前的 `main` 代码基线为对象，结合代码审计、测试/CI/发布审计、文档审计和
电脑控制操作 Electron / Web UI。除本报告及相关进展文档外，没有修改仓库代码或配置
文件；流程验证只向隔离的临时 `userData` / SQLite 写入应用状态和临时服务商配置。
临时服务在验收结束后已全部停止。

<a id="executive-summary"></a>

## 执行摘要

结论：**项目已经具备较宽的产品骨架和可演示的团队试点能力，但端到端交付状态机不可信，
目前不能称为功能完整，也不满足 v1.3 发布条件。**

- 最后正式发布仍是 `v1.2.0`。
- v1.3 交付流程的主要代码已经合入 `main`，但版本仍是 `1.2.0`，没有 v1.3 标签，
  也没有完成当前主干的发布验收。
- 请求、需求澄清、方案设计、门禁、知识审查、测试、PR 草稿、
  验收证据包等入口已经可见，部分动作可以真实落库。
- 核心阻塞不是“页面还少几个按钮”，而是工作流、同步、项目映射和写入路径
  之间没有形成单一、可靠的状态机。
- 本轮复现了两个状态完整性问题：
  - 测试失败、没有编码差异、PR 仍等待时，验收证据包仍可生成，最终门禁
    仍能把工作流实例标成 `completed`；
  - 完成后的本地工作流实例一经团队同步，会被远端摘要覆盖成无完整节点的远端 Run。
- 当前更适合定义为：**开发预览 / 内部演示版本**。修复关键阻塞并重新验收前，不宜作为
  可发布或外部团队可依赖的完整产品。

从能力覆盖面看，产品骨架已经较广；从“真实请求能可靠走完并交付”的标准看，仍处于
v1.3 加固阶段，而不是已完成状态。后文使用逐能力矩阵表达完成度，不给出缺少
统一权重的百分比。

### 测试证据与脱敏

本地测试失败原因是验收前已经存在的文档/样例不一致：

- `docs/knowledge/prompts/opendesign-design-prompts.md` 已改为相对链接；
- `packages/shared/src/fixtures.ts` 仍内嵌旧内容；
- `packages/shared/src/fixtures.test.ts` 因此失败。

测试 UI 正确归档了 `failed`、退出码 `1` 和耗时，但仍显示 `Redacted no`，标准输出和
产物内容包含完整本地工作目录。2026-06-26 演练中报告的路径泄漏问题仍然存在。

电脑控制的异步聚焦/点击重试使同一安全测试命令执行了两次，因此最终 UI 有两份内容
一致的失败证据；本报告不把“双份证据”本身归因为产品自动重复执行。

<a id="priority-findings"></a>

## 优先问题

<a id="p0---final-acceptance-can-bypass-the-delivery-chain"></a>

### P0 — 最终验收可绕过交付链

业务验收操作 没有验证开发代码差异、通过的测试、PR 草稿和当前节点顺序。结果是失败的交付
仍可被标成 `completed`。这是下一轮必须优先修复的状态完整性问题。

<a id="p0---completed-run-sync-replaces-local-truth-with-a-lossy-remote-summary"></a>

### P0 — 已完成 Run 同步以不完整远端摘要替代本地真实状态

团队同步后，桌面合并视图用同 ID 远端摘要替代本地完整工作流实例，六阶段节点、
产物和事件不再可见。桌面端还错误声称本地工作流实例已保留。必须先明确
本地/远端权威来源与合并契约。

<a id="p1---local-project-与-team-project-没有显式映射"></a>

### P1 — 本地项目与团队项目没有显式映射

配对成功不等于仓库映射成功。PR 草稿依赖映射，却没有正常 UI 完成该步骤；
其他代码路径还存在回退到第一个团队项目的风险。

<a id="p1---默认-fakeno-cost-walkthrough并不成立"></a>

### P1 — “默认模拟、无费用演练”并不成立

模拟编码运行时 可显式开启，但需求澄清/方案设计/知识审查仍需要手动配置 Agent 服务商。文档和实际启动路径必须一致，或提供真正的内置确定性服务商。

<a id="p1---redaction-boundary-is-incomplete"></a>

### P1 — 脱敏边界不完整

测试证据仍会存储并显示工作目录和标准输出中的完整本地路径，违反产品定义中的 本地私有边界。

<a id="p1---auth-and-budget-are-not-fail-closed"></a>

### P1 — 认证和预算未在不确定时拒绝继续

静态代码审计显示，`DEVFLOW_REQUIRE_AUTH` 已进入配置模型，但当前服务端仍可从未签名的
`x-devflow-*` 请求头构造身份/角色；远端预算服务异常时桌面端预算检查器回退
返回 `blocksRun: false`。本轮没有用真实付费模型服务商端到端验证“不确定时拒绝继续”的行为。在收紧并
验证这些写路径前，不应把当前自托管服务栈暴露到不可信网络，也不应依赖它保护真实
付费调用。

<a id="p1---current-cibuild-artifacts-are-not-release-ready"></a>

### P1 — 当前 CI/构建产物不满足发布条件

验收时有未提交变更的工作区的单测/E2E，以及干净主干的 Windows/Docker CI 都有明确失败；
API/Worker 全新构建产物不能直接启动，发布附件也不可直接安装或部署。

<a id="p2---web-and-management-surfaces-are-ahead-of-their-write-paths"></a>

### P2 — Web 与管理界面领先于写入流程

新 Web 外壳、知识、技能、MCP、团队概览已有完整视觉入口，但当前真实数据和动作
仍是部分或空状态，容易造成“已完成”的错觉。

<a id="recommended-evolution"></a>

## 建议演进顺序

<a id="phase-a---v13-state-integrity-and-release-hardening"></a>

### 阶段 A — V1.3 状态完整性与发布加固

1. 建立唯一工作流迁移/写入模型：
   - 每个节点的完成条件由同一共享状态迁移评估器决定；
   - 编码、测试、PR、业务验收结果都必须回写同一工作流实例；
   - 非当前节点动作、缺失上游证据、失败测试必须在写路径拒绝。
2. 修复同步契约：
   - 本地持久化 Run 不被远端摘要覆盖；
   - 远端契约要么携带可恢复的完整结构，要么只作为并列摘要；
   - 增加已完成 Run 往返同步回归。
3. 增加显式本地项目 ↔ 团队项目 ↔ 仓库映射。
4. 修复测试证据的工作目录/路径脱敏。
5. 让确定性模拟服务商与文档中的无成本启动方式真正一致。
6. 修复当前单测/E2E/Windows/Docker CI，重新执行完整电脑控制演练。
7. 让 API/Worker 等发布输出在全新环境通过最小启动冒烟测试。

<a id="phase-b---v14-pilot-trust-boundary"></a>

### 阶段 B — V1.4 试点信任边界

1. 把仓库知识索引接入真实 Electron/API 路径。
2. 收紧认证和预算：外部/付费路径必须在不确定时拒绝继续，演示模式必须显式隔离。
3. 补齐 Web 请求接收、门禁操作、配对和 Run 选择。
4. 把 v1.3 的最小可运行输出加固为可重复的 Electron/Web/API 试点包，并增加
   部署、升级和回滚冒烟。

<a id="phase-c---v15-delivery-and-operations-expansion"></a>

### 阶段 C — V1.5 及后续交付与运维扩展

只有阶段 A/B 验收通过后，再推进：

- GitHub App / 限定作用域令牌的真实 PR 创建；
- MCP 运行时、工具权限和遥测；
- 多桌面端协作、冲突和审计；
- Windows Electron 实机、安装器、签名、公证和自动更新；
- 更完整的自托管备份/恢复与运营能力。

<a id="v13-signoff-exit-criteria"></a>

## V1.3 验收退出条件

v1.3 重新签核前，至少应满足：

- 工作流实例不能在开发/测试/PR 任一前置条件失败时完成业务验收；
- 编码/测试/PR/业务验收都通过同一状态机推进当前节点；
- 已完成本地 Run 同步后仍保留完整工作流/产物/事件；
- 本地 ↔ 团队 ↔ 仓库映射有显式、可验证的 UI/API；
- 测试证据不包含完整工作目录或本地敏感路径；
- 无成本演练不需要临时替身服务或隐式凭据；
- `test`、`test:e2e`、Windows、Docker 和发布冒烟测试全绿；
- `verify:demo` / `test:electron-smoke` 在当前发布候选版上通过；
- 按仅发布时执行的验收规则在标签前完成并记录真实
  `DEVFLOW_RUN_OPENCODE_SMOKE=1 ... corepack pnpm test:opencode-smoke`；
- 全新 API/Worker/Electron/Web 产物可实际启动；
- 新的带日期的电脑控制演练通过，并由发布状态明确绑定当前 HEAD/tag。
