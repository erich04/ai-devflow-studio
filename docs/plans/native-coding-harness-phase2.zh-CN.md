## 第 7 条：独立验收

现有 V 会重跑公开测试，但不能据此断言需求全部实现。新增检查由独立模型请求在编码前生成，依据已批准需求、人工补充和不可变输入 B；检查正文保存在宿主私有记录，不进入实现者、子任务或压缩摘要的对话。

- 生成请求沿用现有模型调用收据、请求字节预算、取消、未知交付及重试机制；不另建绕过预算的提供方入口。
- 检查逐项绑定来源、目标版本与内容摘要。宿主冻结后不能替换；需求更新需生成新版本。
- 精确修订批准后，先跑公开测试，再在 V 运行冻结检查。必须有实际断言与完整宿主结果记录；单纯退出 0 不算通过。
- 失败只向实现者反馈来源明确的未通过验收条目，不泄露私有检查正文和预期值。恢复 D 后最多自动返修两轮，再停下等人处理。
- 人工验收保留原来的明确入口与 `manual_accepted` 证据，不能冒充独立自动验收。历史会话保留原证据含义。

## R2 评测后的修复清单（落实情况见下文）

真实日志已经证明，检查作者也会写出错误检查：03 的测试夹具自带 PR 材料，却被当作空夹具；05 的文件路径经过双重引号替换，生成无效 TypeScript。将冻结检查原样放在参考实现上，外部验收通过而生成检查失败。参数反馈补丁后的 02 定向复测又出现反方向问题：产品内检查通过并报告完成，外部验收仍为 80/81，出现假完成。因此失败条目不能一律解释成产品缺陷，通过条目也不能单凭生成者自己的断言数量证明需求已覆盖。

1. **先区分候选、检查和交付结果**：保留 D 的端到端交付评分，另在模型与命令停止后复制 C 做诊断；候选通过不能替代交付成功。原十题的 D 均保持基线，先前的 0/10 不能推断所有 C 都实现错误。
2. **统一测试框架适配**：现有宿主已管理外层私有脚本和进程；仍须把生成者自行拼装的框架测试文件、路径替换与报告解析收归宿主，生成者提供检查内容。区分语法/导入/夹具故障与需求断言失败，故障分类测试必须重现本轮具体问题。
3. **核验检查的前提与行为覆盖**：在不可变基线的隔离副本中检查语法、依赖和夹具，给检查作者足够的只读 API/测试上下文。区分新增行为与保持行为，分别核对基线上的预期失败/通过；新增行为失败不能和检查无效混为一谈。针对本轮漏检，加入不同中断点的反例与实际状态/副作用断言，不能把“没有错误提示”等弱代理条件当作功能完成。参考补丁和外部隐藏测试始终不提供给作者或实现者。
4. **改善可修复反馈与额度安排**：把批准需求映射为细粒度、有来源的验收条目；返修只收到可定位的条目和安全诊断，不提供私有正文或期望值。验收器故障与实现者返修次数分开核算。本轮四题进入独立检查后都没有提交第二份返修修订，需为验收和返修预留步骤/时间，再验证两轮返修在真实任务中能否发挥作用。
5. **重新冻结并跑完整十题**：保持原题目和外部评分，检查有效性与业务通过分别报告。达到原定十题门槛后再收尾第二阶段，之后才推进任务图与编排。
