# Native Coding v3 harness 路线图

日期：2026-11-01；进度更新：2026-11-02。阶段 1 已由 #291、#292 合入 V3。阶段 2 已启动，先实施第 7 条独立验收，详见[实施记录](native-coding-harness-phase2.zh-CN.md)；阶段 3 未开始，#238 继续保持草稿。

## 背景

Native Coding v3 是 DevFlow 自己写的编码 Agent harness，没有使用 OpenCode 的代码。它挂在桌面端的开发（build）节点上，只在项目配置 `nativeVersion: 3` 时启用；代码在分支 `codex/native-coding-harness-v3`，对应草稿 PR #238。宿主按批驱动持久会话，模型在私有候选仓库里多轮调查、编辑和测试；人批准冻结的修订后，宿主才写入交付 worktree。设计见 [ADR 0029](../adr/0029-native-coding-harness-v3.md)，用法见[使用指南](../guides/native-coding-harness-v3.md)，实施与验收见[实施记录](native-coding-harness-v3-implementation.md)。

2026-11-01 的评审把 learn.shareai.run 教程总结的 Claude Code 20 个方面加上 13 个补充方面，共 33 项，逐项对照 Claude Code、Codex、OpenCode、Pi、DeepSeek Harness、OpenHands 等 harness，按 0–4 分打分，平均 2.06。强项在副作用和花费可信：先写收据再执行、模型请求的交付状态分三类、人批准冻结修订、四个隔离的工作区、根/子预算同事务准入；4 分只有循环、工作区隔离、预算与缓存三项。任务管理和权限是短板：没有计划和任务图，对照题里委派 0 次（S05、S12 为 0 分）；权限没有规则，默认执行方式不是 OS 沙箱（S03、E1 为 2 分）。完成判定只看公开测试：r8 报告完成 5 次，评测方的独立断言全部没通过，r1–r8 对照轮的 27 次 v3 观测独立通过 0 次。所以按“先合入与稳固，再做完成判定与权限，最后做任务管理与编排”的顺序推进。

评审全文见[评审](../research/native-coding-harness-review-2026-11/review.md)；它引用的调研报告和简称对照见[资料目录](../research/native-coding-harness-review-2026-11/README.md)。

## 工作规则

- 每条单独开分支、worktree 和 PR。worktree 从 `origin/codex/native-coding-harness-v3` 新建，PR 的目标分支是 `codex/native-coding-harness-v3`，不推送 main。
- 合入前在该条的 worktree 里跑 `corepack pnpm verify`，再等 PR 上的 CI 检查全部通过（目前是 6 项，包括 “Native v3 Linux lifecycle and Electron”），然后用 `gh pr merge <n> --merge --match-head-commit <sha>` 合入。
- PR #238 保持草稿，直到阶段 3 达到发布门槛。
- 付费的真实模型评测先找用户批预算，批准前不调用付费 API。
- 不碰其他会话的 worktree，也不碰主 checkout 里未提交的文件。
- 每个阶段结束，更新一次面试讲稿（当前版本在评审第 8 节）。
- 每条的 PR 同时更新文末的状态表。

## 计划

### 阶段 1：合入与稳固（不花钱，约 1-2 周）

1. **合入 main**：v3 先更新到最新的 main，迁移号改成 42，并兼容已经升到草稿 41 的库。完成标准：verify、三种起点（40、main 的 41、草稿 41）的迁移测试、v3 冒烟测试（`node scripts/native-coding-electron-smoke.mjs --harness-v3`）都通过。
2. **自动重试**：429、503 和连接失败按退避重试，最多 5 次，遵守 `Retry-After`；5xx 最多重试 2 次。402 和 401 单独提示。工具批无效时先让模型重答一次，不直接结束。
3. **只读工具并行**：同一批最多 4 个一起跑，结果按原来的顺序写回。
4. **读文件提速**：每次读文件不再把整棵工作区重新算一遍哈希，按文件大小、修改时间和 inode 缓存。
5. **预算预留**：按实际请求的大小预留，token 上限不再把缓存命中算进去。
6. **DeepSeek 适配**：加一条“漏传思考内容会报 400”的回归测试。旧模型名清理按 2026-11-01 会话中的范围调整交给记忆会话：两个记忆验证脚本默认值暂留，运行时的兼容别名和历史数据保留。

### 阶段 2：完成判定与权限（付费，建议先批 2 轮，每轮约 1-3 美元）

7. **独立验证者**：开工后按已批准的需求写检查，检查冻结后实现者看不到。没通过就退回修，最多修 2 轮，之后停下等人。
8. **系统沙箱设为默认**：macOS 用 Seatbelt，Linux 用 bubblewrap，不可用时退到 Landlock。只能写工作区，默认断网。沙箱起不来就停下，不退到无沙箱模式。
9. **权限规则**：命令前缀规则，按 deny、ask、allow 的顺序判断；三种模式（逐条问；沙箱内按规则放行；无人值守时需要问的一律当拒绝）；权限卡加一个“本任务内允许”按钮；子任务的权限请求冒泡到主任务处理。

阶段 2 完成标准：重跑 r8 那 10 道题，假完成为 0，至少 1 题通过独立验收；沙箱测试在 macOS 和 Linux 都通过；记下每题弹了几次权限。

### 阶段 3：任务管理与编排（付费，31 题 × 3 个执行器跑一轮约 8-10 美元）

10. **计划和任务图**：新增 `update_plan` 工具，计划由宿主保存和校验：最多 12 个节点、不能有环、标完成要附证据。界面显示进度。
11. **委派挂到计划节点上**：只读子任务用分叉的方式继承父任务的上下文，复用缓存前缀。
12. **后台命令完成后主动唤醒模型**，不再轮询。
13. **多 Agent 编排扩到整个任务**：一个主 Agent 加几个登记好的角色，每个角色有自己的系统提示；消息协议带版本号；写入前先审批计划；交付分支始终只有一个写者。

阶段 3 完成标准：31 × 3 对照按独立验收计分，达到发布门槛（至少 30 题、假完成为 0、复杂题比 v2 高 10 个百分点、中位用时不超过 15 分钟、每次独立通过不超过 10 美元），并和单 Agent 比较委派有没有带来收益。

### 穿插做（基本不花钱）

14. **大输出落盘**：工具结果超出上限时，只给开头、结尾和读取方式，不再直接报错。
15. **撤销**：候选仓库每一步都提交，拒绝后能回到指定的修订。
16. **配置**：Skill 目录写进简报；进入子目录时读那里的 AGENTS.md；步数等限额可以配置。
17. **记忆**：合入后给 v3 接上 `memory_search`，这是 ADR 0030（main 上的 `docs/adr/0030-hindsight-project-memory.md`）里留下的一项。
18. **编辑**：`apply_patch` 一次可以改多处；改完跑类型检查，把错误反馈给模型。
19. **补测试**：MCP 经过 v3 工具层的测试、提示注入用例，以及真实触发一次上下文压缩。
20. **无界面入口和录制回放测试**：CI 里不花钱就能做回归。

### 保持现状

循环、四个工作区、预算与缓存（这三项都是 4 分），以及执行前写收据、按收据对账、批准冻结修订。

### 暂不做

用户 hooks、定时任务、自主认领、带邮箱的长期团队、多 Provider 抽象、用模型自动审批、裁剪旧工具结果、读对话来判断是否完成、上传会话日志。原因是要么没有证据说明值得做，要么会破坏缓存或增加注入风险。

## 阶段 1 收尾记录（2026-11-02）

- 第 3 条：收据和一次性授权按调用顺序保存，连续只读工具最多 4 个并发；写操作、命令、控制工具、网络权限请求保持串行。结果按原顺序写回。用户插话后不再启动队列里的读取；取消不追加迟到结果；进程中断后的只读收据可重读。
- 补充定价修复：[#290](https://github.com/erich04/ai-devflow-studio/pull/290) 已合入 main；[#291](https://github.com/erich04/ai-devflow-studio/pull/291) 将它同步进 v3，解决预算函数冲突并保留 #286 的请求字节上界。#292 已包含该同步提交，验证组合后的行为。

- 测试使用模拟模型和隔离目录，没有付费模型调用。这轮不能证明独立验收成功率提高，也不改变第 2、3 阶段的发布门槛。
- 面试讲稿已按第一阶段实现更新，见[评审第 8 节](../research/native-coding-harness-review-2026-11/review.md#8-面试怎么讲)。旧评分、r8 指标和代码行数是初次评审的历史快照，没有重跑评测或重新打分。
