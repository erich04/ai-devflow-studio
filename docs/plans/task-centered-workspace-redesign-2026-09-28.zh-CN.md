# 以开发任务为中心的工作区改造方案

日期：2026-09-28。状态：**设计提案（第 2 版），待评审，尚未实施**。

代码基线：`main` / `bf18e4a`。之后的 `1a8e9a8` 只更新文档与截图，`apps/`、`packages/` 没有变化。本文中的新页面、模块名称、交互和目标数值都是提案，不代表产品已提供。

## 1. 结论

界面乱，主要不是信息多，而是层级错：全局设置、团队连接、流程元数据、诊断信息和“现在要做的事”处在同一层级。另有几处状态结论与可用按钮互相矛盾，削弱了用户对界面的信任。

改造遵循三条原则：

1. **流程优先**：先选开发任务，在任务内完成阅读、讨论、执行、检查和决策。
2. **配置分离**：配置集中管理；任务页只显示实际生效的配置及影响，缺失时就地引导。
3. **导航分层**：全局导航表达工作目的，阶段导航表达进度，材料与执行记录用于追溯。

任务页首屏必须回答三个问题：我在处理什么、现在是什么状态、下一步由谁做什么。结论文字与按钮来自同一份状态投影。

### 1.1 关键决策

评审请先确认这张表。

| 决策 | 采用方案 | 理由 |
| --- | --- | --- |
| 全局主对象 | 开发任务，即 Run 的界面别名，不新建数据对象 | 与现有工作流契约一致 |
| 交付顺序 | 先做桌面首屏切片 S1 并量化验收，再做任务内操作、导航和 Web | 先解决最显眼、风险最低的问题 |
| 六阶段导航 | 保留；子步骤并入阶段项，不单独占行 | 复用现有结构，释放纵向空间 |
| 仅警告的策略 | 审批入口始终可见；建议动作可以作为主动作 | 界面不把建议升级为阻断 |
| 项目讨论 | 保留项目范围会话；空会话默认收起 | 兼容现有会话语义，释放主区约 35% 宽度 |
| 连接与同步 | 团队连接、团队数据更新、结果上传分开显示 | 三者不能互相证明 |
| 用户语言 | 首层写行动和影响；枚举、规则键、ID、哈希放进技术详情 | 降低理解成本，保留追溯能力 |
| 技术路线 | 增量替换呈现层与导航，复用全部写入路径 | 降低版本、权限和发布相关回归风险 |
| 跨端共享呈现模块 | S2 完成后再决定是否下沉到 `packages/shared` | 先证明规则稳定，再抽象 |

若要改变“项目独立会话”“精确交付审批”“数据上云范围”等领域约束，需单独修改 ADR 与契约，不混入本次改造。

## 3. 约束

以下各条在本次改造中不变。

- Run、Node、Artifact、Event 在界面上称为开发任务、步骤、材料、执行记录；存储与身份不变，不新建跨 Run 的“任务”对象。
- 浏览阶段、材料或历史版本只改变查看位置，不改变实际进度和审批对象。
- 界面只解释和预判权限、策略与预算；点击后由 Electron 或 API 的写入路径重新核验。
- 仅警告的策略不能在界面上表现为阻断；强制阻断不能显示为可以通过。
- 项目讨论是项目范围的私有会话；保存为节点提案不等于正式材料；聊天不批准 Gate、不执行代码、不发布。
- Web 只拿脱敏数据；GitHub 交付审批来自签名 Web 会话并绑定精确版本；桌面凭据不能批准自身请求。
- 新增界面偏好只保存经校验的界面状态，按组织和项目分区，不保存凭据、正文或业务状态副本。
- 交付终点是经核实的 Draft PR 和业务验收，不包含合并、部署或回滚。

## 4. 信息架构

### 4.1 桌面端

```text
组织／本地模式 · 项目                              团队连接 · 账户
├─ 任务
│  ├─ 任务列表：待我处理／进行中／受阻／已完成
│  ├─ 团队请求：查看、明确领取、关联到已生成的任务
│  └─ 任务详情：六阶段 → 当前工作／材料与版本／执行记录
├─ 知识：规范、可复用知识、引用来源、记忆管理
├─ 团队：当前授权范围内的项目进度与协作摘要
└─ 设置
   ├─ 本地项目：仓库、测试命令、执行环境
   ├─ 模型与执行方式：提供方、凭据、默认模型、执行器
   ├─ 扩展能力：Skills、MCP
   ├─ 团队连接：配对、连接详情、团队设置入口
   └─ 高级：诊断、脱敏自检、日志、维护
```

知识保留为一级入口，因为查规范、理解代码、核对来源是日常工作。任务页内可以展开相关引用，完整管理再进入知识页。

### 4.2 Web 控制端

```text
组织 · 项目                                        身份 · 数据更新时间
├─ 我的待办：当前项目内需要我处理的 Gate、交付审批、异常
├─ 项目任务：团队请求、开发任务、交付结果、只读进度
├─ 团队：成员、项目健康、费用摘要
└─ 设置：策略、预算、桌面连接、GitHub 仓库绑定
```

第一版待办只覆盖当前选中且已授权的项目，不暗示已实现全组织聚合。没有审批权限的成员看到“等待负责人审批”，不显示无效按钮。

### 4.3 旧入口迁移

| 现有入口 | 新位置 | 说明 |
| --- | --- | --- |
| 工作台 | 任务／任务详情 | 保留 Run、节点、材料定位 |
| Team | 团队 | 保留脱敏协作视图 |
| Knowledge | 知识 | 任务内提供引用预览 |
| Agents 的执行部分 | 当前阶段的工作区 | 复用执行模块和事件订阅 |
| Agents 的模型、凭据、预算 | 设置／模型与执行方式；团队预算跳转 Web 设置 | 每项标明本地或团队作用域 |
| Skills、MCP | 设置／扩展能力 | 启用语义和权限检查不变 |
| 测试 | 测试阶段；命令编辑移到设置／本地项目 | 命令配置与执行结果分开 |
| 诊断、Redaction 自检 | 设置／高级 | 错误提示直接链接到对应诊断 |
| Web 配对、仓库绑定 | Web 设置 | 不常驻任务详情首屏 |
| Web `#human-gate`、`#evidence-chain`、`#agents`、`#runtime` | 对应任务的审批、材料、执行摘要或项目预算 | 旧链接可解析，服务端仍校验权限 |

## 5. 桌面任务工作区

### 5.1 首屏结构与空间预算

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 项目 ▾    [搜索当前项目]          团队连接 ● ▾    ＋ 新建任务    账户 ▾    │ 56
├──────┬───────────────────────────────────────────────────────────────────┤
│ 任务 │ Health API 增加依赖探测 ▾                      本任务用量 · 讨论 ⧉  │ 36
│ 知识 │ ①需求澄清 1/2 ─ ②方案设计 ─ ③开发实现 ─ ④测试 ─ ⑤PR 交付 ─ ⑥业务验收 │ 48
│ 团队 │ 等待你确认需求 v1 · 1 条建议      [运行门禁审查]  [确认需求]  [⋯]    │ 52
│ 设置 │ [当前工作] [材料与版本] [执行记录]                                   │ 40
│      │ 需求正文……                                                          │
```

各行合计约 244px，另留间距余量，因此目标定为 ≤ 280px。规则：

- **顶栏只占一行**：组织或本地模式、项目、搜索、团队连接摘要、新建任务、账户与设置菜单。配对输入放进连接摘要（未绑定时）或设置；Redaction 自检移到设置／高级；主题放进账户菜单。完整本地路径只出现在设置和悬停提示中。
- **取消状态条**：当前 Run 用量并入任务标题行；项目概览并入任务列表；策略与预算只在影响当前决定时出现在状态行；同步并入团队连接摘要。
- **子步骤并入阶段项**，例如「需求澄清 1/2」；展开阶段项时才列出子步骤名称。
- **状态行是唯一的结论位置**：结论、适用对象与版本、一个主动作、最多两个可见次要动作，其余放进「⋯」。节点类型、来源、Run 版本、产物与轨迹计数、策略统计移到执行记录或「详情」展开区。
- **浏览位置与实际进度不同**时，在状态行上方加一行：「正在查看历史阶段 · 返回当前工作」。两者相同时不显示这一行。

### 5.2 三个页签

| 页签 | 内容 | 默认进入 |
| --- | --- | --- |
| 当前工作 | 当前正文、差异或测试结果；直接相关的审查意见与阻碍 | 首次打开任务或切换阶段 |
| 材料与版本 | 当前材料、已确认依据、原始输入、讨论提案、历史版本与来源 | 从引用、搜索或历史链接进入时精确定位 |
| 执行记录 | 操作人、时间、模型或执行器、实际用量、调用结果、诊断入口 | 从错误、费用或运行事件进入时定位 |

现有「概览」与「内容与审查」合并为「当前工作」，「产物与证据」迁入「材料与版本」。两处共用同一个材料阅读模块，不出现两份正文或两套审批按钮。正文使用单一纵向滚动区域，折叠详情内不再嵌套固定高度的滚动面板。

### 5.3 各阶段的主内容与主动作

| 阶段 | 主内容 | 主动作（随状态变化） | 完成依据 |
| --- | --- | --- | --- |
| 需求澄清 | 原始需求、目标、非目标、验收标准、待确认问题、引用 | 生成需求草稿 → 生成修订 → 确认需求 | 绑定明确版本的人工确认；聊天回复不算确认 |
| 方案设计 | 实现思路、影响模块、取舍、测试计划、风险、所依据的需求版本 | 生成方案 → 确认方案 | 绑定设计材料及对应审查的 Gate 结果 |
| 开发实现 | 执行状态、变更范围、待处理的权限请求、差异 | 开始开发 → 处理权限请求 → 按既有方式恢复 | 受控执行、差异和工作树事实 |
| 测试验证 | 当前代码版本的检查结果、未覆盖的验收项、失败原因 | 运行检查 → 查看失败并修复 → 重新验证 | 区分通过、失败、超时、未运行、已过期 |
| PR 交付 | 改动摘要、测试范围、目标仓库／分支／提交、审批与发布进度 | 准备交付 → 查看 Web 审批 → 发布获批版本 → 修订／继续／重试／停止 | 远端提交与 Draft PR 的完成证据 |
| 业务验收 | 验收标准逐项对应证据、交付链接、未验证事项 | 整理验收材料 → 确认验收 | 人工验收记录；测试通过不能替代业务验收 |

**建立任务**时，创建和生成是两个动作。主按钮为「创建任务」，回执为“任务已创建，尚未调用模型”，失败时保留输入。进入需求阶段后，状态行显示将使用的模型、执行方式、配置是否就绪和费用说明，主动作为「生成需求草稿」。团队请求通过「领取并创建任务」使用既有认领契约；重复领取时显示已关联的任务。

返工只在底层已有经过验证的版本化命令时开放入口，不在渲染层修改节点状态来模拟回退。

### 5.4 讨论侧栏

- 没有展开偏好、会话为空时默认收起，只在任务标题行保留「讨论」入口。
- 用户展开后，按组织和项目记住偏好；关闭时保留会话、草稿和阅读位置；切换阶段不强制开关。
- 主区宽度不足以保证正文可读时，改为覆盖式侧栏。阈值的初值为 1100px，在 S1 中按实际布局确定。
- 后台新消息只做提示，不自动展开，不抢焦点。
- 「讨论此材料」会在输入区添加引用卡，标明项目、任务、阶段、材料版本和读取时间。只加引用不发送消息、不产生费用；切换左侧节点不替换引用。
- 「保存为节点提案」先预览目标和内容，结果写明“提案已保存，尚未更新正式需求”。正式生成是否采用了提案，以输入记录为准。

### 5.5 视觉层级

- **字号**：最多 5 级，最小 12px。建议取值：12px 用于辅助信息与标签，14px 用于正文，16px 用于区块标题，20px 用于任务标题，等宽 12px 只用于标识与代码。在 `styles.css` 中定义字号变量，逐步替换现有的分散取值。
- **次要信息**用现有的 `--text-muted`、`--text-faint` 颜色区分，不靠缩小字号。
- **徽章**只表达状态，每个对象最多一个；计数、来源、类型不使用徽章。
- **间距**使用 4、8、12、16、24、32px 的固定阶梯。
- **颜色语义**：普通主动作、警告、阻断、危险操作各有独立样式。可以先把主按钮改为中性色，不以更换品牌色为前提。阻断状态同时给出图标、文字原因和恢复入口，不能只靠颜色表达。
- **验收环境**：1440×900、1280×800、1024×768 三种窗口尺寸，200% 缩放，浅色与深色主题，键盘焦点。

### 5.6 反馈位置

- 配对、保存配置等表单操作失败时，在表单内持续显示原因、已保留的内容和下一步，不只靠短暂浮层。
- 短暂的成功提示放在不遮挡主动作和讨论输入的位置。
- 后台任务的运行或失败状态归属到对应任务；用户在其他页面时，通知带任务名称和定位入口。
- 关闭弹窗或侧栏后，焦点回到触发它的入口。

## 6. 状态、动作与文案规则

### 6.1 状态与动作选择

先确定作用域、事实是否完整、是否在浏览，再按执行状态选择动作。这是呈现规则，不是第二套工作流引擎。

| 条件 | 主结论 | 可提供的动作 |
| --- | --- | --- |
| 无权访问，或对象不属于当前项目 | 当前内容不可访问 | 返回当前项目；不显示其他项目的内容 |
| 必要事实加载中，或版本无法核实 | 正在读取状态／状态待核实 | 刷新；不显示可审批的结论 |
| 浏览历史或未来阶段 | 历史记录／此阶段尚未开始，同时显示实际进度 | 阅读、返回当前工作；不对浏览对象执行推进 |
| 尚未轮到该步骤 | 等待上游完成 | 定位上游；不出现“可以通过” |
| 有进行中的执行 | 正在执行，并说明实际步骤 | 查看进度、停止；权限请求优先展示 |
| 执行失败、中断或恢复待决 | 失败位置与已保留的结果 | 只提供该执行类型支持的恢复动作 |
| 强制证据、必需配置或权限不满足 | 缺少具体条件／等待具体角色 | 一个最相关的补救入口，其余原因可展开 |
| **Gate 可审批，但缺少门禁审查或有其他非阻断建议** | 等待你确认 · 有 N 条建议 | 主动作：运行门禁审查；可见的次要动作：确认，点击后列出未处理的建议再确认 |
| Gate 可审批且没有建议 | 等待你确认 | 主动作：确认 |
| 当前步骤可以执行 | 已就绪，说明执行对象和影响 | 本阶段主动作 |
| 任务已完成 | 已完成，列出交付与验收依据 | 查看交付；后续新工作需显式新建任务 |

角色、例外资格、预算和策略结果都来自既有的权威检查。并发变化导致版本过期时，保留用户已填写的意见，刷新后要求针对新对象重新决定。同一动作进行中时防止重复提交。错误信息说明发生了什么、保留了什么、下一步怎么做，原始诊断放在详情中。

### 6.2 用户文案映射

只改显示，不修改存储值。每条映射都要覆盖加载中、空数据、加载失败、未知状态和权限不足。

| 工程表达 | 首层文案 | 详情中保留 |
| --- | --- | --- |
| `Run`、`Artifact`、`Event` | 开发任务、材料、执行记录 | 原始类型与可复制的标识 |
| `local only`、`no run loaded` | 本地项目；尚无任务或尚未选择任务 | 是否连接团队、对象是否加载 |
| `INDEXED` | 知识索引已更新 | 文档数量与更新时间；索引完成不代表已审查 |
| `LEXICAL` + 匹配分 | 关键词检索 | 命中词与匹配方法；匹配分没有固定满分，不能转写为置信度 |
| `RETRIEVAL_CANDIDATE` | 检索候选，尚未经审查确认 | 这是引用的审查状态，不是 Gate 结论 |
| `missing_agent_review` 等规则键 | 具体原因，如“缺少本阶段要求的 AI 审查” | 规则键、来源、适用版本、是否阻断；无法识别的规则写“待核实” |
| `warn`、`blocked` | 有 N 条建议／审批受阻，并说明原因 | 区分“策略已加载且条件不满足”与“策略加载失败” |
| `ready`、`empty`、`1 events` | 已记录、尚未生成、有 1 条执行记录 | 原始状态值 |
| 任务 UUID、`kh-…` 哈希 | 任务名称、材料标题、版本与来源 | 完整标识与内容哈希；审批所需的版本信息仍在决策区可见 |

### 6.3 测试证据的空态

命令配置、本次执行和工作流进度分别呈现，三者不互相代替。

| 实际情况 | 显示内容 |
| --- | --- |
| 未选择仓库 | 选择本地仓库后再配置或执行测试 |
| 已选仓库，未配置命令 | 配置当前项目的测试命令 |
| 有可用命令，本任务尚无结果 | 当前任务尚未运行测试，并提供执行入口 |
| 正在执行 | 当前命令与执行进度 |
| 执行失败、超时或被跳过 | 实际结果、原因和可用的后续动作 |
| 有历史结果但不适用于当前代码 | 结果对应的版本与过期原因，提示重新验证 |
| 证据读取失败或适用性无法核实 | 明确显示读取失败或待核实，不推断为未运行或已通过 |

工作流还没到测试阶段时，说明当前实际阶段；“命令已保存”或“提前测试通过”都不代表测试阶段已完成。

### 6.4 团队连接的三类状态

| 维度 | 依据 | 用户看到的状态 |
| --- | --- | --- |
| 团队连接 | 当前本地项目的配对记录、有效期、身份 | 本地项目，未连接团队／已连接到某团队项目／需要重新连接 |
| 团队数据更新（云端 → 本地） | 项目、成员快照的读取回执；策略快照单独计算 | 尚未读取／读取中／最近成功时间／读取失败，使用缓存 |
| 结果上传（本地 → 云端） | 当前授权范围内的同步队列与服务端回执 | 暂无待上传／待上传 N 项／上传中／部分失败 |

规则：

- 未连接团队的本地项目：连接显示“本地项目，未连接团队”，上传显示“不适用”，不因 `pairing_required` 终结的记录显示失败（D3）。未绑定时是否还应写入同步队列属于数据路径问题，不在 S1 范围内，S0 核实后单独处理。
- 摘要优先显示需要用户处理的错误，其次是进行中的动作和待完成的数量；展开后三类状态都可见，不能因为一类成功而掩盖另一类失败。
- 没有读取过团队数据时，即使上传队列为空，也不显示笼统的“全部已同步”。
- “最近成功时间”取自对应操作的回执，不用页面刷新时间。“未成功读取”与“成功返回空列表”使用不同文案。
- 切换项目后不沿用旧项目的成功提示、计数或错误。策略受阻、预算未配置不写成连接或网络故障。
- 首版不提供笼统的“同步全部”。用户可以分别选择“更新团队数据”或“查看上传详情”。

### 6.5 配置归属与按需引导

| 设置 | 生效范围 | 在任务中的呈现 |
| --- | --- | --- |
| 仓库与测试命令 | 本地项目 | 显示当前仓库与命令摘要；缺失时直接打开对应设置 |
| 默认模型与执行方式 | 项目默认，各次调用可按既有规则覆盖 | 显示下一次调用将使用的值和费用说明 |
| 模型凭据 | 本机安全存储 | 只显示是否可用，渲染层不读取密钥 |
| Skills、MCP | 既有的本地或项目启用范围 | 显示当前任务实际使用的能力 |
| 配对 | 组织与团队项目 | 连接状态、最近更新时间、异常提示 |
| 策略、预算、GitHub 仓库绑定 | 团队服务端 | 显示适用版本、角色与限制，编辑跳转 Web 设置 |

从任务打开设置时携带返回位置。保存后重新读取实际生效的结果，并返回原任务和阶段；保存成功不会自动执行之前被阻止的付费调用或发布动作。

异常与首次使用：空项目只提供「选择本地项目」；有项目无任务时只提供「新建任务」，有团队请求时再加领取入口；没有可用模型时允许阅读和创建任务，生成前提示配置；离线时标记最后更新时间，不把网络失败显示为零任务；预算不足时说明作用域与缺口并给出申请路径；配对失效时保留本地成果，说明哪些团队动作暂停。

## 8. 验收

### 8.1 S1 验收

- 2.2 的指标在 1440×900 和 1280×800 下全部达到目标；1024×768 下阶段导航完整可见，讨论栏允许以覆盖方式展开。
- 仅警告且缺少门禁审查：同屏可见「运行门禁审查」和确认入口；确认前列出未处理的建议。
- 强制阻断：没有审批按钮；显示具体原因和一个补救入口。
- 还没到 Gate：结论为“等待上游”，不出现“可以通过”。
- 创建任务：只创建一次；回执不说“正在澄清”；失败时保留输入。
- 未连接团队：不显示同步失败；连接摘要写“本地项目，未连接团队”。
- 测试空态：6.3 的七种情况各自显示对应文案。
- 空讨论：不占列；展开后关闭再打开，草稿仍在；后台消息不抢焦点。
- 提示浮层不遮挡主动作和讨论输入。
- 浅色、深色主题和键盘焦点下，主动作、警告、阻断都能分辨。
- 自动化：`corepack pnpm verify`；更新文案断言后运行 `test:electron-smoke` 与 `test:workbench-conversation-electron-smoke`。

| S2 | 门禁审查、编码、测试都在任务内完成，且记录的身份与版本正确；权限请求不被导航隐藏，恢复不会自动授权；修改代码后，旧的测试结果标记为过期；保存聊天提案后只有目标提案成为共享材料，流程不自动推进；设置保存后回到原任务和阅读位置，不自动执行付费或发布动作 |
| S3 | 旧入口和搜索结果定位到正确的项目、任务、材料与页签；知识引用按文档分组，版本、章节与审查关系不丢失；连接详情的三类状态在已绑定未读取、策略已加载但团队数据失败、数据已更新但上传待完成、切换项目或绑定过期等组合下含义都正确 |
| S4 | 需求同时存在原文、提案、v1、v2 时，默认打开正确的材料；阅读 v1 时 v2 待审，不会误批 v1，也不会悄悄批准 v2；审批瞬间版本变化时，写入被拒绝并保留意见 |
| S5 | 无权限或数据滞后时不泄露对象、说明数据时效，不显示虚假的空列表或可审批状态；材料或绑定变化后，旧审批失效，桌面与 Web 状态一致；修订、继续、重试、停止按既有契约工作，不重复发布 |
| S6 | Draft PR 与业务验收各有依据，不宣称已合并或已部署；长内容、窄窗口、200% 缩放下主要操作与正文都可到达，页面无横向溢出 |

### 8.3 验证分层

- **呈现规则**：在状态投影的单元测试中覆盖真实的状态组合和版本冲突。
- **交互**：组件测试覆盖页签切换、焦点、主动作和历史阅读。
- **执行**：用既有的 Electron 冒烟测试验证主进程、IPC、SQLite 和执行记录，不用渲染预览替代。
- **用户路径**：配对、拉取和关键操作都通过真实界面完成并断言回执。直接调用 IPC 准备的数据只能验证布局。
- **可用性**：邀请 3–5 位未参与实现的人完成同一个小任务，记录找到下一步所用的时间、离开任务页的次数、误读状态或版本的次数，并与 S0 基线对比。样本只用于发现问题，不作为统计结论。

## 9. 后续批次的设计要点

S4、S5 与技术落地的细节在对应批次开始前单独评审，这里只记录已确定的要点。

### 9.1 材料与版本（S4）

- 材料分为当前待处理、已确认依据、原始输入与参考、讨论提案、历史记录。标签至少包含类型、版本标识、状态和更新时间；没有正式修订号时显示实际记录时间，不伪造 v1、v2。
- 默认阅读顺序：有显式链接时打开该材料；阶段待审时打开待审材料；已完成阶段打开与审批记录绑定的材料；尚无正式材料时显示原始输入和生成入口。不能用数组第一项或最新更新时间推断“已生效”。
- 阅读历史版本时明确提示，确认按钮不能指向历史版本，也不能悄悄确认另一个版本。
- 复用 [`clarification.ts`](../../packages/shared/src/clarification.ts) 与 [`GateMaterialReader`](../../apps/desktop/src/components/GateMaterialReader.tsx)，不维护两套需求版本选择器。设计等阶段先统一阅读与来源标识，完整修订能力另行立项。

### 9.2 Web 审查与跨端交接（S5）

- 待办行显示任务名称、待处理事项、请求方、材料版本、更新时间和一个「查看」入口。需求确认、方案评审、交付审批、业务验收分别呈现，不统称为“通过”。
- 交付审批首屏显示目标仓库、分支、预期提交、改动文件、验证范围和请求修订号；长标识提供缩写、完整查看与复制。
- 保持脱敏范围；需要原始差异时，提示到有权限的本地环境查看，不自动上传补丁。
- 跨端链接只使用已有、可验证的路由参数。若尚不支持“打开桌面上的指定任务”，第一版提供任务名称和定位说明，不放置无效按钮。
- 旧的 `projectId + runId` 链接仍直接打开该任务；`view=team`、`view=settings` 仍可解析。

### 9.3 技术落地

- 呈现模块的输入是已限定作用域的权威事实和浏览上下文，输出是状态说明、材料选择、适用依据和动作描述。它不授予权限、不产生副作用、不生成新的 Run 状态。桌面端和 Web 端各自用适配层提供事实；Web 缺失的信息显式标记为不可用。
- 优先扩展现有的 [`buildNodeInspectorViewModel`](../../apps/desktop/src/app/node-inspector-view-model.ts)、[`workflow-context-projection.ts`](../../packages/shared/src/workflow-context-projection.ts) 与编码动作投影。React 布局、焦点、滚动和中文文案留在各端。
- 导航上下文包括作用域、任务、阶段、页签、可选材料和返回入口，与聊天会话身份分开保存。切换前后重新校验对象归属；应用重启后恢复合法的浏览位置，找不到对象时回到当前项目的任务列表。
