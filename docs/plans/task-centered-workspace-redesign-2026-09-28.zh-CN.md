# 以开发任务为中心的工作区改造方案

日期：2026-09-28。状态：**设计方案（第 17 版），已确认；S0–S6 已全部完成**。确认：erich04，2026-09-28。S0 结果见[基线报告](../validation/workspace-redesign-s0-baseline-20260928.md)，S1–S6 结果见 [S1 实施报告](../validation/workspace-redesign-s1-20260928.md)、[S2 实施报告](../validation/workspace-redesign-s2-20260928.md)、[S3 实施报告](../validation/workspace-redesign-s3-20260928.md)、[S4 实施报告](../validation/workspace-redesign-s4-20260928.md)、[S5 实施报告](../validation/workspace-redesign-s5-20260928.md)、[S6 实施报告](../validation/workspace-redesign-s6-20260928.md)。

代码基线：`main` / `bf18e4a`。之后到 `0518870` 的提交只改文档与截图，`apps/`、`packages/` 没有变化。起草时，本文中的新页面、模块名称、交互和目标数值都是计划；实际交付以第 7 节各批次的“实施结果”和对应实施报告为准。

## 1. 结论

界面乱，主要不是信息多，而是层级错：全局设置、团队连接、流程元数据、诊断信息和“现在要做的事”处在同一层级。另有几处状态结论与可用按钮互相矛盾，削弱了用户对界面的信任。

改造遵循三条原则：

1. **流程优先**：先选开发任务，在任务内完成阅读、讨论、执行、检查和决策。
2. **配置分离**：配置集中管理；任务页只显示实际生效的配置及影响，缺失时就地引导。
3. **导航分层**：全局导航表达工作目的，阶段导航表达进度，材料与执行记录用于追溯。

任务页首屏必须回答三个问题：我在处理什么、现在是什么状态、下一步由谁做什么。结论文字与按钮来自同一份状态投影。

### 1.1 关键决策

本表已于 2026-09-28 确认。改变其中任何一项，先修订本文。

| 决策 | 采用方案 | 理由 |
| --- | --- | --- |
| 全局主对象 | 开发任务，即 Run 的界面别名，不新建数据对象 | 与现有工作流契约一致 |
| 交付顺序 | 先做桌面首屏切片 S1 并量化验收，再做任务内操作、导航和 Web | 先解决最显眼、风险最低的问题 |
| 六阶段导航 | 保留；子步骤并入阶段项，不单独占行 | 复用现有结构，释放纵向空间 |
| 仅警告的策略 | 是当前步骤、审批对象可确定、用户有权限、没有强制阻断，四项同时满足时审批入口可见；只有确实缺少门禁审查时，才以运行审查为主动作 | 界面不把建议升级为阻断，也不让用户重复无效的审查 |
| 方案评审的版本绑定 | S1 只显示所审材料的标题和生成时间；定义设计材料版本并修改审批契约放到 S4 | 契约改动超出 S1 范围；显示信息只帮助辨认，不能替代版本保护 |
| 关键操作与决策信息 | 停止、取消、重要拒绝，以及影响决定的版本、角色、阻碍、未知费用和数据时效始终可见 | 优先级高于控件数量等数字目标 |
| 项目讨论 | 保留项目范围会话；空会话默认收起 | 兼容现有会话语义，释放主区约 35% 宽度 |
| 连接与同步 | 团队连接、团队数据更新、结果上传分开显示；重新配对前确认影响 | 三者不能互相证明；重新配对会撤销进行中的交付 |
| 用户语言 | 首层写行动和影响；枚举、规则键、ID、哈希放进技术详情 | 降低理解成本，保留追溯能力 |
| 技术路线 | 增量替换呈现层与导航，复用全部写入路径 | 降低版本、权限和发布相关回归风险 |
| 跨端共享呈现模块 | 开发中按实际复用情况决定是否下沉到 `packages/shared`，最迟在 S5 开始前定下 | 先看到真实复用再抽象；Web 端只依赖 `packages/shared`，引用不到桌面端模块 |

若要改变“项目独立会话”“精确交付审批”“数据上云范围”等领域约束，需单独修改 ADR 与契约，不混入本次改造。

测量方法：以内容区左上角为原点。控件统计视口内可见、未被滚动区域裁掉的 button、带 href 的链接、tab、input、select、textarea、summary 元素。字号以文本节点为单位，只计位于视口内且可见的文本，混合内容元素中的文本也计入。测量前等待全局提示浮层消失（浮层至少显示 8 秒，其文字会多计一次「需求确认 Gate」）。三档内容区尺寸由 S0 固定为 1440×742、1280×742、1024×742：纵向目标是绝对像素，所以三档只改宽度。主进程窗口的最小尺寸是 1180×760（[`main.ts`](../../apps/desktop/electron/main.ts)），1024 档由测量脚本临时放开最小尺寸得到，不改产品配置；用户放大页面时会得到同样的 CSS 宽度，例如 1440 宽的窗口放大到约 140%。改前改后必须在同一尺寸下对比。测量脚本是 [`scripts/workspace-baseline.mts`](../../scripts/workspace-baseline.mts)，自检见 `--self-check`。

| 拉取后团队数据仍为空 | 不为空。经正常绑定表单连接后拉取成功，团队快照有 1 个项目、4 名成员、1 个任务（演示种子数据）；本地任务不在其中，原因是 X1 | `team-paired` | 高（内存演示 API） |
| D3 终止记录的错误码 | 没有任何凭据时为 `pairing_required`；其他本地项目已配对时为 `scope_mismatch`；两种都没有团队目标、`recovery` 为 `none` | `team-unpaired`、`upload-target-other-project` | 高 |
| A 未绑定期间的记录在 B 已配对时被处理 | 以 `scope_mismatch` 终止；之后连接 A 时不会自动重排。但同一任务下一次写入时，入队合并会把它重新置为待上传，随后上传成功；一次性记录（测试证据、审查）仍需手动重试 | `upload-target-other-project` 的后续检查 | 高 |
| 凭据过期时的错误码 | `unauthorized`，团队目标保留，`recovery` 为 `none`，重新配对不会自动重排。S0 以撤销令牌代替过期：API 对两者都返回空会话。渲染层只按本地记录的 `expiresAt` 判断过期，服务端失效的凭据仍显示为已连接（X3） | `upload-credential-invalid`；[`team-repository.ts`](../../apps/api/src/repositories/team-repository.ts) 的 `resolveDesktopTokenSession` | 中高 |
| 同一团队项目重新配对是否撤销交付 | 会撤销，且没有任何确认 | `team-existing-credential` 的后续检查；新增单元测试 | 高 |
| 撤销后 API 侧的交付请求 | 桌面端不通知 API；API 上的请求保持原状态，只在之后有人操作且已过期时拒绝。离线没有交付请求，未运行确认 | 代码阅读：[`github-delivery-processor.ts`](../../apps/desktop/electron/github-delivery-processor.ts) 跳过已撤销意图；API 交付路由没有撤销入口 | 中 |
| `githubDeliveryIntents` 是否含其他项目 | 含。`loadState` 不带条件列出全部交付意图，渲染层原样保存，只在选择检查器对象时按任务过滤 | 代码阅读：[`local-store.ts`](../../apps/desktop/electron/local-store.ts) 的 `loadState` 与 `listGitHubDeliveryIntents`；未运行确认 | 高 |

## 3. 约束

以下各条在本次改造中不变。

- Run、Node、Artifact、Event 在界面上称为开发任务、步骤、材料、执行记录；存储与身份不变，不新建跨 Run 的“任务”对象。
- 浏览阶段、材料或历史版本只改变查看位置，不改变实际进度和审批对象。
- 界面只解释和预判权限、策略与预算；点击后由 Electron 或 API 的写入路径重新核验。
- 仅警告的策略不能在界面上表现为阻断；强制阻断不能显示为可以通过。
- 项目讨论是项目范围的私有会话；保存为节点提案不等于正式材料；聊天不批准 Gate、不执行代码、不发布。
- Web 只拿脱敏数据；GitHub 交付审批来自签名 Web 会话并绑定精确版本；桌面凭据不能批准自身请求。
- 新增界面偏好只保存经校验的界面状态，按组织和项目分区，不保存凭据、正文或业务状态副本。
- 交付终点是经核实的 Draft PR 和业务验收，不包含合并、部署或回滚。
- 同步范围隔离（`scope_mismatch`）与重新配对时撤销进行中交付的既有行为不变，界面只如实展示。

以下两条是布局约束，优先级高于 2.2 节的数字目标和 5.1 节“最多两个可见次要动作”的规则：

- 停止、取消和重要的拒绝操作始终可见，不收进「⋯」或折叠区。
- 影响当前决定的版本、角色、阻碍、未知费用和数据时效留在首层，不能为了简洁一并折叠。

依据：[领域术语](../../CONTEXT.md)、[产品基线](../product/prd/current-product-prd.md)、[会话 ADR](../adr/0022-workbench-conversation-harness.md)。

## 5. 桌面任务工作区

### 5.1 首屏结构与空间预算

S1 完成后的任务页：

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 项目 ▾    [搜索当前项目]           团队连接 ● ▾    ◐    ＋ 新建任务      │ 56
├──────┬───────────────────────────────────────────────────────────────────┤
│ 导航 │ Health API 增加依赖探测 ▾                      本任务用量 · 讨论 ⧉  │ 36
│      │ ①需求澄清 1/2 ─ ②方案设计 ─ ③开发实现 ─ ④测试 ─ ⑤PR 交付 ─ ⑥业务验收 │ 48
│      │ 等待你确认需求 v1 · 尚未运行 AI 审查 [运行门禁审查] [确认需求 v1] [⋯] │ 52
│      │ [当前工作] [材料与版本] [执行记录]                                   │ 40
│      │ 需求正文……                                                          │
```

各行合计 232px：状态行底部约 192px，留出间距后目标为 ≤ 240px；首个正文区块目标为 ≤ 280px。左侧导航在 S1 保持现有 8 个入口，S3 收为任务、知识、团队、设置。

示意图的页签行和「运行门禁审查」按钮画的是 S2 的形态。S1 期间保留现有四个页签（概览、内容与审查、产物与证据、执行记录），按钮写「去 Agents 运行门禁审查」（7.1 节），各行高度不变。

规则：

- **顶栏只占一行，S1 共 5 个控件**：项目、搜索、团队连接摘要、主题图标、新建任务。配对输入、「更新团队数据」及其说明放进团队连接弹层；Redaction 自检移到现有诊断页；主题在 S3 移进设置。完整本地路径只出现在悬停提示和项目菜单中。
- **取消状态条**：当前 Run 用量并入任务标题行；项目概览并入项目与任务菜单；策略与预算只在影响当前决定时出现在状态行；同步并入团队连接摘要。
- **子步骤并入阶段项**，例如「需求澄清 1/2」；展开阶段项时才列出子步骤名称。
- **状态行是唯一的结论位置**：结论、适用对象与版本、一个主动作、最多两个可见次要动作，其余放进「⋯」。停止、取消和重要的拒绝操作不放进「⋯」，影响决定的信息不移出首层（第 3 节）。节点类型、来源、Run 版本、产物与轨迹计数、策略统计移到执行记录或「详情」展开区。
- **浏览位置与实际进度不同**时，在状态行上方加一行：「正在查看历史阶段 · 返回当前工作」。两者相同时不显示这一行。

### 5.2 三个页签

| 页签 | 内容 | 默认进入 |
| --- | --- | --- |
| 当前工作 | 当前正文、差异或测试结果；直接相关的审查意见与阻碍 | 首次打开任务或切换阶段 |
| 材料与版本 | 当前材料、已确认依据、原始输入、讨论提案、历史版本与来源 | 从引用、搜索或历史链接进入时精确定位 |
| 执行记录 | 操作人、时间、模型或执行器、实际用量、调用结果、诊断入口 | 从错误、费用或运行事件进入时定位 |

现有「概览」与「内容与审查」合并为「当前工作」，「产物与证据」迁入「材料与版本」。两处共用同一个材料阅读模块，不出现两份正文或两套审批按钮。正文使用单一纵向滚动区域，折叠详情内不再嵌套固定高度的滚动面板。

### 5.3 各阶段的主内容与主动作

| 阶段 | 主内容 | 主动作（随状态变化） | 完成依据 |
| --- | --- | --- | --- |
| 需求澄清 | 原始需求、目标、非目标、验收标准、待确认问题、引用 | 生成需求草稿 → 生成修订 → 确认需求 vN | 绑定明确版本的人工确认；聊天回复不算确认 |
| 方案设计 | 实现思路、影响模块、取舍、测试计划、风险、所依据的需求版本 | 生成方案 → 确认方案 | 绑定设计材料及对应审查的 Gate 结果 |
| 开发实现 | 执行状态、变更范围、待处理的权限请求、差异 | 开始开发 → 处理权限请求 → 按既有方式恢复 | 受控执行、差异和工作树事实 |
| 测试验证 | 当前代码版本的检查结果、未覆盖的验收项、失败原因 | 运行检查 → 查看失败并修复 → 重新验证 | 区分通过、失败、超时、未运行、已过期 |
| PR 交付 | 改动摘要、测试范围、目标仓库／分支／提交、审批与发布进度 | 准备交付 → 查看 Web 审批 → 发布获批版本 → 修订／继续／重试／停止 | 远端提交与 Draft PR 的完成证据 |
| 业务验收 | 验收标准逐项对应证据、交付链接、未验证事项 | 整理验收材料 → 确认验收 | 人工验收记录；测试通过不能替代业务验收 |

需求阶段的确认按钮写明版本号；方案阶段在 S4 之前只显示材料标题与生成时间，见 6.2 节。

**建立任务**时，创建和生成是两个动作。主按钮为「创建任务」，回执为“任务已创建，尚未调用模型”，失败时保留输入。进入需求阶段后，状态行显示将使用的模型、执行方式、配置是否就绪和费用说明，主动作为「生成需求草稿」。团队请求通过「领取并创建任务」使用既有认领契约；重复领取时显示已关联的任务。

返工只在底层已有经过验证的版本化命令时开放入口，不在渲染层修改节点状态来模拟回退。

### 5.4 讨论侧栏

- 没有展开偏好、会话为空时默认收起，只在任务标题行保留「讨论」入口。
- 用户展开后，按组织和项目记住偏好；关闭时保留会话、草稿和阅读位置；切换阶段不强制开关。
- 主区宽度不足以保证正文可读时，改为覆盖式侧栏。阈值的初值为 1100px，在 S1 中按实际布局确定。
- 后台新消息只做提示，不自动展开，不抢焦点。
- 「讨论此材料」会在输入区添加引用卡，标明项目、任务、阶段、材料版本和读取时间。只加引用不发送消息、不产生费用；切换左侧节点不替换引用。
- 「保存为节点提案」先预览目标和内容，结果写明“提案已保存，尚未更新正式需求”。正式生成是否采用了提案，以输入记录为准。

### 5.5 视觉层级

- **字号**：最多 5 级，最小 12px。建议取值：12px 用于辅助信息与标签，14px 用于正文，16px 用于区块标题，20px 用于任务标题，等宽 12px 只用于标识与代码。在 `styles.css` 中定义字号变量，逐步替换现有的分散取值。
- **次要信息**用现有的 `--text-muted`、`--text-faint` 颜色区分，不靠缩小字号。
- **徽章**只表达状态，每个对象最多一个；计数、来源、类型不使用徽章。
- **间距**使用 4、8、12、16、24、32px 的固定阶梯。
- **颜色语义**：普通主动作、警告、阻断、危险操作各有独立样式。可以先把主按钮改为中性色，不以更换品牌色为前提。阻断状态同时给出图标、文字原因和恢复入口，不能只靠颜色表达。
- **验收环境**：S0 确定的三档内容区尺寸，浅色与深色主题，键盘焦点。第 11 版起不做 200% 缩放验证。

### 5.6 反馈位置

- 配对、保存配置等表单操作失败时，在表单内持续显示原因、已保留的内容和下一步，不只靠短暂浮层。
- 短暂的成功提示放在不遮挡主动作和讨论输入的位置。
- 后台任务的运行或失败状态归属到对应任务；用户在其他页面时，通知带任务名称和定位入口。
- 重新配对的确认在团队连接弹层内完成；取消后凭据与交付都不变。
- 关闭弹窗或侧栏后，焦点回到触发它的入口。

## 6. 状态、动作与文案规则

### 6.1 状态与动作选择

先确定作用域、事实是否完整、是否在浏览，再按执行状态选择动作。这是呈现规则，不是第二套工作流引擎。

表中“Gate 可审批”指四项同时满足：是实际当前步骤、审批对象可确定、用户有权限、没有强制阻断。任一项不满足时，按表中前面的行处理。

| 条件 | 主结论 | 可提供的动作 |
| --- | --- | --- |
| 无权访问，或对象不属于当前项目 | 当前内容不可访问 | 返回当前项目；不显示其他项目的内容 |
| 必要事实加载中，或审批对象、版本无法核实 | 正在读取状态／状态待核实 | 刷新；不显示可审批的结论 |
| 浏览历史或未来阶段 | 历史记录／此阶段尚未开始，同时显示实际进度 | 阅读、返回当前工作；不对浏览对象执行推进 |
| 尚未轮到该步骤 | 等待上游完成 | 定位上游；不出现“可以通过” |
| 有进行中的执行 | 正在执行，并说明实际步骤 | 查看进度、停止（始终可见）；权限请求优先展示 |
| 执行失败、中断或恢复待决 | 失败位置与已保留的结果 | 只提供该执行类型支持的恢复动作 |
| 强制证据、必需配置或权限不满足 | 缺少具体条件／等待具体角色 | 一个最相关的补救入口，其余原因可展开 |
| Gate 可审批，缺少门禁审查（策略仅警告） | 等待你确认需求 vN · 尚未运行 AI 审查 | 主动作：运行门禁审查。可见次要动作：确认需求 vN；点击后在原位置提醒一次“尚未运行 AI 审查，本次确认针对需求 vN”，再次点击才提交 |
| Gate 可审批，已有审查，只剩非阻断建议 | 等待你确认需求 vN · 有 N 条建议 | 主动作：确认需求 vN。建议逐条列在当前工作区，不额外提醒 |
| Gate 可审批，没有建议 | 等待你确认需求 vN | 主动作：确认需求 vN |
| 当前步骤可以执行 | 已就绪，说明执行对象和影响 | 本阶段主动作 |
| 任务已完成 | 已完成，列出交付与验收依据 | 查看交付；后续新工作需显式新建任务 |

表中以需求确认 Gate 为例；方案评审 Gate 的按钮写「确认方案」，其他 Gate 按各自名称，规则相同。

角色、例外资格、预算和策略结果都来自既有的权威检查。并发变化导致版本过期时，保留用户已填写的意见，刷新后要求针对新对象重新决定。同一动作进行中时防止重复提交。错误信息说明发生了什么、保留了什么、下一步怎么做，原始诊断放在详情中。

### 6.2 审批对象与版本

- **需求确认 Gate**：状态行和确认按钮写明待确认的版本号，如「确认需求 v2」。阅读历史版本时，按钮仍指向待确认版本并写明其版本号；历史提示旁提供「返回待确认版本」。写入层继续由主进程比对材料标识、修订号和内容摘要，过期、缺失或不符即拒绝；S1 为此补回归测试（V3）。
- **方案评审 Gate**：S4 之前按钮写「确认方案」，状态行显示所审材料的标题和生成时间。这只帮助用户辨认，不能替代版本一致性保护；缺口见 V2 与 9.1 节。
- **其他 Gate**：沿用现有写入校验，S1 不改动。

| 工程表达 | 首层文案 | 详情中保留 |

### 6.4 测试证据的空态

命令配置、本次执行和工作流进度分别呈现，三者不互相代替。

| 实际情况 | 显示内容 |
| --- | --- |
| 未选择仓库 | 选择本地仓库后再配置或执行测试 |
| 已选仓库，未配置命令 | 配置当前项目的测试命令 |
| 有可用命令，本任务尚无结果 | 当前任务尚未运行测试，并提供执行入口 |
| 正在执行 | 当前命令与执行进度 |
| 执行失败、超时或被跳过 | 实际结果、原因和可用的后续动作 |
| 有历史结果但不适用于当前代码 | 结果对应的版本与过期原因，提示重新验证 |
| 证据读取失败或适用性无法核实 | 明确显示读取失败或待核实，不推断为未运行或已通过 |

工作流还没到测试阶段时，说明当前实际阶段；“命令已保存”或“提前测试通过”都不代表测试阶段已完成。测试只能在任务处于测试节点时执行（X6），此前执行入口应说明原因，而不是可点击后才提示。

S0 发现现有测试证据不记录所测代码的提交（X6），无法判断结果是否过期。S1 对这类证据只能显示对应的执行时间，并按“适用性无法核实”处理，不显示“仍然有效”，也不显示“已过期”。“已过期”一行要等证据记录提交号后才能实现，属于写入路径改动，另行处理。

后续：加固批次 H3 已为新证据记录所测工作树的指纹，并显示“结果对应当前代码”或“已过期”；旧证据仍按“适用性无法核实”处理。见[加固批次](post-redesign-hardening-2026-09-30.zh-CN.md#h3)。

### 6.5 团队连接的三类状态

| 维度 | 依据 | 用户看到的状态 |
| --- | --- | --- |
| 团队连接 | 当前本地项目的配对记录、有效期、身份 | 本地项目，未连接团队／已连接到某团队项目／需要重新连接 |
| 团队数据更新（云端 → 本地） | 项目、成员快照的读取回执；策略快照单独计算 | 尚未读取／读取中／最近成功时间／读取失败，使用缓存 |
| 结果上传（本地 → 云端） | 当前项目的同步记录与服务端回执 | 当前未启用团队上传／正在尝试上传 N 项／有 N 条记录未上传／部分失败 |

**结果上传的判断**结合四项：当前项目的绑定状态、记录的团队目标（`organizationId`、`teamProjectId`）、处理状态、错误码。以本地项目 A 为当前项目：

| 情况 | 用户看到的表达 | 连接后会怎样 |
| --- | --- | --- |
| A 未连接团队，记录还没有团队目标 | 当前未启用团队上传 | 连接 A 后，以 `pairing_required` 终止的记录自动重排并尝试上传；以 `scope_mismatch` 终止的不会自动重排，可手动重试。任务在连接前已调用过模型时，重排后的上传会以 `conflict` 失败（X1，S6 之后已修复），按失败原因显示，不显示“已上传” |
| 刚完成绑定，旧记录已重排 | 正在尝试上传 N 条 | 收到成功回执才显示“已上传”；失败时按失败原因显示 |
| 记录的目标是团队项目 X，当前凭据属于其他本地项目 B | A 有 N 条记录未上传（目标：X） | 把 A 重新连接到 X 后需要手动重试；重新配对会替换 B 的连接，并撤销进行中的交付请求 |
| 记录的目标是 X，当前没有凭据 | 需要重新连接到 X，有 N 条记录未上传 | 连接到 X 后手动重试；此时没有现有连接会被替换，也没有交付会被撤销 |
| 原团队目标已无法恢复（A 已改绑到 Y） | N 条记录属于 X，无法上传到当前团队项目 | 不提供重试，只说明原因 |

凭据过期或在服务端被撤销时，本地凭据仍在，上传以 `unauthorized` 终止，保留原团队目标，重新配对后不会自动重排（S0 实测）。桌面端只按本地记录的过期时间判断“配对已过期”，服务端撤销的凭据仍会显示为已连接（X3）。因此出现 `unauthorized` 时，连接状态也显示“需要重新连接”，不能只看本地过期时间；重新连接后这些记录需要手动重试。

规则：

- 配对成功后自动重排的只有同时满足以下条件的记录：属于当前本地项目、团队目标为空、已终止、错误码为 `pairing_required`。重排只代表恢复处理，网络、权限或服务端校验仍可能失败；收到成功回执才显示“已上传”。
- `recovery: 'none'` 不代表不能恢复：现有的手动重试接受任何已终止的记录，并保留记录原有的团队目标。另外，任务下一次写入时，入队合并会把该任务的 `run-summary` 记录重新置为待上传（S0 实测），所以任务摘要不一定需要手动重试；测试证据、审查等一次性记录仍需手动重试。
- 记录已有团队目标时，手动重试要求本地项目、组织、团队项目三者都与当前凭据一致，否则会再次以 `scope_mismatch` 终止。原目标已无法恢复时不显示重试按钮。
- 摘要优先显示需要用户处理的错误，其次是进行中的动作和待完成的数量；展开后三类状态都可见，不能因为一类成功而掩盖另一类失败。
- 没有读取过团队数据时，即使上传队列为空，也不显示笼统的“全部已同步”。
- “最近成功时间”取自对应操作的回执，不用页面刷新时间。“未成功读取”与“成功返回空列表”使用不同文案。
- 切换项目后不沿用旧项目的成功提示、计数或错误。策略受阻、预算未配置不写成连接或网络故障。
- 首版不提供笼统的“同步全部”。用户在团队连接弹层中分别选择「更新团队数据」或「查看上传详情」。

**重新配对的确认**：当前已有凭据时，提交配对码前在团队连接弹层内确认，列出：

1. 会被替换的连接：本地项目、组织、团队项目、身份；
2. 会被撤销的进行中交付请求：状态为 `approval_required`、`approved`、`publishing_branch`、`branch_published`、`creating_pr`、`recovery_required` 的交付意图，不限当前项目；
3. 撤销后的影响：需要新建交付尝试并重新取得 Web 审批。

首次配对（没有现有凭据）不弹确认；取消后凭据与交付都不变。重新配对到同一团队项目同样需要确认，因为同样会撤销交付（P1）。数据来自渲染层已有的配对信息与 `githubDeliveryIntents`；S0 核实后者包含所有本地项目的交付意图，确认框直接按上述六种状态筛选列出，不需要补充查询。这是现有行为，S1 只负责如实展示，不改撤销逻辑。

### 6.6 配置归属与按需引导

| 设置 | 生效范围 | 在任务中的呈现 |
| --- | --- | --- |
| 仓库与测试命令 | 本地项目 | 显示当前仓库与命令摘要；缺失时直接打开对应设置 |
| 默认模型与执行方式 | 项目默认，各次调用可按既有规则覆盖 | 显示下一次调用将使用的值和费用说明 |
| 模型凭据 | 本机安全存储 | 只显示是否可用，渲染层不读取密钥 |
| Skills、MCP | 既有的本地或项目启用范围 | 显示当前任务实际使用的能力 |
| 配对 | 组织与团队项目 | 连接状态、最近更新时间、异常提示 |
| 策略、预算、GitHub 仓库绑定 | 团队服务端 | 显示适用版本、角色与限制，编辑跳转 Web 设置 |

从任务打开设置时携带返回位置。保存后重新读取实际生效的结果，并返回原任务和阶段；保存成功不会自动执行之前被阻止的付费调用或发布动作。

异常与首次使用：空项目只提供「选择本地项目」；有项目无任务时只提供「新建任务」，有团队请求时再加领取入口；没有可用模型时允许阅读和创建任务，生成前提示配置；离线时标记最后更新时间，不把网络失败显示为零任务；预算不足时说明作用域与缺口并给出申请路径；配对失效时保留本地成果，说明哪些团队动作暂停。

| S2 | 门禁审查、编码、测试都在任务内完成，且记录的身份与版本正确；权限请求不被导航隐藏，恢复不会自动授权；代码改动在看到精确差异后才能批准；修改代码后，旧的测试结果不显示为仍然有效（按“适用性无法核实”显示；标记“已过期”等测试证据记录提交号后另行实现）；同一内容在三个页签中只出现一次；保存聊天提案后只有目标提案成为共享材料，流程不自动推进；设置保存后回到原任务和阅读位置，不自动执行付费或发布动作 |
| S3 | 视口内可交互控件在三档内容区常规场景下达到 2.2 节的 S3 目标；旧入口和搜索结果定位到正确的项目、任务、材料与页签；知识引用按文档分组，版本、章节与审查关系不丢失；连接详情的三类状态在已绑定未读取、策略已加载但团队数据失败、数据已更新但上传待完成、切换项目或绑定过期等组合下含义都正确，上传的五种情况与 6.5 节一致 |

### 8.3 验证分层

- **呈现规则**：在状态投影的单元测试中覆盖真实的状态组合和版本冲突。
- **交互**：组件测试覆盖页签切换、焦点、主动作和历史阅读。
- **执行**：用既有的 Electron 冒烟测试验证主进程、IPC、SQLite 和执行记录，不用渲染预览替代。
- **用户路径**：配对、拉取和关键操作都通过真实界面完成并断言回执。直接调用 IPC 准备的数据只能验证布局。
- **可用性**：在 S6 邀请 3–5 位未参与实现的人完成同一个小任务，记录找到下一步所用的时间、离开任务页的次数、误读状态或版本的次数。样本只用于发现问题，不作为统计结论，所以不在改前另做一轮用户测试；改前改后的对比以 2.2 节的首屏指标和 S0 截图为准。

## 9. 后续批次的设计要点

S4、S5 与技术落地的细节在对应批次开始前单独评审，这里只记录已确定的要点。

### 9.1 材料与版本（S4）

- 材料分为当前待处理、已确认依据、原始输入与参考、讨论提案、历史记录。标签至少包含类型、版本标识、状态和更新时间；没有正式修订号时显示实际记录时间，不伪造 v1、v2。
- 默认阅读顺序：有显式链接时打开该材料；阶段待审时打开待审材料；已完成阶段打开与审批记录绑定的材料；尚无正式材料时显示原始输入和生成入口。不能用数组第一项或最新更新时间推断“已生效”。
- 阅读历史版本时明确提示，确认按钮不能指向历史版本，也不能悄悄确认另一个版本。
- 已知缺口（V2，已在 S4 解决）：起草时，方案评审的审批不绑定用户看到的版本。`approveGate` 只接收 `runId`、`nodeId` 和需求阶段的可选版本；主进程使用的 `expectedRunUpdatedAt` 是它自己刚读取的 Run，只能防止并发写入。S4 定义了设计材料的版本标识并修改了审批契约（7.4 节）；S1 显示的标题与时间只用于辨认，不能替代这项保护。
- 复用 [`clarification.ts`](../../packages/shared/src/clarification.ts) 与 [`GateMaterialReader`](../../apps/desktop/src/components/GateMaterialReader.tsx)，不维护两套需求版本选择器。设计等阶段先统一阅读与来源标识，完整修订能力另行立项。

### 9.2 Web 审查与跨端交接（S5）

- 待办行显示任务名称、待处理事项、请求方、材料版本、更新时间和一个「查看」入口。需求确认、方案评审、交付审批、业务验收分别呈现，不统称为“通过”。
- 交付审批首屏显示目标仓库、分支、预期提交、改动文件、验证范围和请求修订号；长标识提供缩写、完整查看与复制。
- 保持脱敏范围；需要原始差异时，提示到有权限的本地环境查看，不自动上传补丁。
- 跨端链接只使用已有、可验证的路由参数。若尚不支持“打开桌面上的指定任务”，第一版提供任务名称和定位说明，不放置无效按钮。
- 旧的 `projectId + runId` 链接仍直接打开该任务；`view=team`、`view=settings` 仍可解析。

### 9.3 技术落地

- 呈现模块的输入是已限定作用域的权威事实和浏览上下文，输出是状态说明、材料选择、适用依据和动作描述。它不授予权限、不产生副作用、不生成新的 Run 状态。桌面端和 Web 端各自用适配层提供事实；Web 缺失的信息显式标记为不可用。
- 优先扩展现有的 [`buildNodeInspectorViewModel`](../../apps/desktop/src/app/node-inspector-view-model.ts)、[`workflow-context-projection.ts`](../../packages/shared/src/workflow-context-projection.ts) 与编码动作投影。React 布局、焦点、滚动和中文文案留在各端。
- 状态投影目前只依赖 `packages/shared` 与桌面端的纯函数模块，不引用 React 或 Electron。新增规则保持这一点，之后按 1.1 节决定下沉时，不需要先拆除界面依赖。
- 导航上下文包括作用域、任务、阶段、页签、可选材料和返回入口，与聊天会话身份分开保存。切换前后重新校验对象归属；应用重启后恢复合法的浏览位置，找不到对象时回到当前项目的任务列表。
