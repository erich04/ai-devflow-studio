# DevFlow Studio v0.8.1 发布签署

<a id="summary"></a>

## 摘要

v0.8.1 签署 v0.8 策略感知交付、冒烟加固 PR #2 及发布计划 PR #3，不新增运行时能力。它验证已提交状态、将包元数据对齐 0.8.1、用 Git 标签记录发布点、明确清理旧分支并建立 v0.9 计划。

## 发布决定

- v0.8.0 标签已在 a63cce0，保留为历史功能/用户指南标签，不移动或重写。

- 运行时已提前实现，本文只约束验证、版本、标签与本地分支清理。

PR #3（devflow-v0.8.1-release-v0.9-planning）新增 v0.9 计划及候选验证中发现的冒烟加固，仍属于签署工作。

### 人工验收清单

对照 v0.8 指南和截图，优先人工点击；电脑控制可选，不稳定时回到人工。

2026-06-19/20 已用电脑控制读取 AI DevFlow Studio 真实窗口，确认工作台、本地项目、选中“架构 Gate”、blocked_policy_unavailable、策略来源、原因和处理计划。但点击仍报 noWindowsAvailable，以下人工操作待完成。`corepack pnpm test:e2e` 和 `corepack pnpm test:electron-smoke` 自动化覆盖可重复点击路径，不能替代该标签的最终人工验收。

- [ ] 工作台：选项目、创建 Run、选 Gate。
- [ ] Gate 约束：阻断/警告、策略来源、原因、处理计划。
- [ ] Agent 审查：运行、查看轨迹、用量及仅警告建议。
- [ ] 编码重试：处理入口 → 人工 Retry Coding → 权限批准 → diff → 测试证据。
- [ ] 测试页：命令、退出码、耗时、脱敏状态。
- [ ] Web 团队台：脱敏策略、处理建议和重试摘要。

本次 Retry Coding 预期使用确定性模拟引擎，足以验证 v0.8.1 交付流程；真实 OpenCode 修复留给 v0.9，不混淆证据。

<a id="release-steps-after-verification-passes"></a>

## 验证通过后的发布步骤

1. 将 root、@ai-devflow/shared、desktop、api、web、worker 共六份 package.json 对齐 0.8.1。
2. 提交 `chore: release v0.8.1`。
3. 创建附注标签：`git tag -a v0.8.1 -m "Release v0.8.1: policy-aware delivery signoff"`。
4. 运行 `corepack pnpm release:status` 确认代码/CI 门禁。当时可保留待人工验收；人工完成后再执行 `DEVFLOW_RELEASE_WALKTHROUGH=passed corepack pnpm release:status -- --strict` 验证严格门禁。
5. 本地旧分支 devflow-v0.2-final-v0.3-start、devflow-v0.8-policy-aware-delivery 仅安全删除，使用 -d 拒绝未合并内容，不用 -D 强制。
6. 未明确批准前保留远程旧分支。

用户按指南完成真实点击之前，不能把人工验收标为通过。
