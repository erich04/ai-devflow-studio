restart the complete matrix. Only the four evidence files may differ between `C` and `S`.

The order is mandatory.

1. Push `S` to the existing PR branch.
2. Require ordinary Verify to pass on `S`; it confirms evidence-only changes did not disturb the

3. Manually dispatch the Release workflow against branch/ref `S`.
4. Require the pre-tag run to pass, including:

   - `release:status -- --mode=pre-tag`;
   - Windows, Postgres, Docker, and Docker lifecycle jobs;
   - Desktop artifact build and packaged smoke;
   - successful upload of non-release workflow artifacts.

5. Present `C`, `S`, local gate summary, CI URLs, Computer Use result, paid-attempt outcome, and
   pre-tag Release result for the final release go/no-go. Do not create or push a tag before explicit
   go-ahead.
6. Merge the PR without rewriting `C` or `S`:

   - no squash merge;
   - no rebase merge;
   - fast-forward is preferred when available;
   - otherwise use a normal merge commit, confirm `S` is an ancestor of `origin/main`, and confirm
     the merge tree is identical to `S`.

7. Keep the release branch until publication succeeds.
8. Confirm no `v1.4.0` local or remote tag exists.
9. Create an annotated local tag that points exactly to `S`:

```bash

```

10. From a clean checkout whose HEAD is `S`, and with the local tag present, run:

```bash

```

11. Push the tag only after tagged status passes.
12. Wait for the tag-triggered Release workflow and verify:

   - workflow head SHA is `S`;
   - tagged status passes;
   - GitHub Release `v1.4.0` exists;
   - Desktop archive and integrity manifest exist;
   - Web, API, and Worker artifacts exist.

not be hidden by moving, deleting, or force-pushing the published tag. Stop the release claim and
