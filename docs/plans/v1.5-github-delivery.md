# V1.5 GitHub Delivery Implementation Plan

Lifecycle: Execution in progress

Product contract: `docs/product/prd/v1.5-github-delivery-prd.md`

Authority decision: `docs/adr/0013-github-app-delivery-authority.md`

Roadmap position: Final planned 1.x feature milestone; 2.x implementation remains blocked until
Slice 7 passes.

## Working Rules

- Build one vertical behavior at a time with a failing public test, minimum implementation, focused
  regression, documentation, and a git commit.
- Preserve the V1.4 local-first, authentication, redaction, budget, policy, and Gate boundaries.
- Never use a real GitHub repository from default CI.
- Never place App private keys or installation access tokens in source, fixtures, SQLite, Postgres,
  renderer state, logs, Artifacts, or evidence files.
- Retain the managed worktree until delivery reaches a durable safe state.
- Do not begin V2.0 product code while any V1.5 slice or the 1.x completion gate remains open.

## Slice 1 — Delivery Intent

User outcome: the current PR node can prepare an exact, reviewable delivery candidate without any
remote write.

- Add shared Delivery Intent, status, approval, attempt, and outcome types.
- Give each intent a stable delivery-series key and positive attempt number; derive the remote
  idempotency key from that exact series and attempt.
- Resolve the latest completed Coding Agent run and active managed worktree for the canonical Run.
- Create or verify one local commit in the managed worktree.
- Bind Project repository/base, namespaced head branch, expected commit, Run/node/version, PR
  Delivery Package digest, changed paths, and passing Test Evidence.
- Persist the intent atomically in SQLite and expose a read-only preview through validated IPC.
- Fail closed on dirty-after-commit, missing evidence, stale workspace, unsafe repository/ref, or
  mismatched scope.

Verification: shared contract tests, disposable git repository tests, LocalStore migration/restart,
IPC parser tests, Desktop preview component test.

## Slice 2 — Durable Approval

User outcome: publication cannot begin until a lead/owner separately approves the exact redacted
Delivery Request through an authenticated Web session.

- Upload a redacted Delivery Request and add immutable session-Cookie approval bound to the
  canonical intent digest.
- Require live lead/owner role; Desktop bearer authority cannot approve its own request.
- Invalidate approval on any repository, branch, commit, Run/evidence version, or Artifact change.
- Add monotonic transition guards. A pre-publication material change creates a new immutable local
  intent revision in the same series/attempt, increments API `intentRevision`, and invalidates the
  previous approval.
- Add Web approval UX and Desktop decision status with clear remote-write language and no
  prechecked/implicit action.
- Record redacted audit events without paths, patches, git output, or credentials.

Verification: approval replay/staleness tests, duplicate IPC tests, restart recovery, renderer
interaction test proving preview and approval are distinct actions.

## Slice 3 — Repository-Scoped GitHub App Credential

User outcome: an owner can bind/revoke GitHub Delivery for one Project, and approved Desktop can
obtain one short-lived least-privilege token without seeing App secrets.

- Add Postgres migration and seed/Postgres repository contract for installation binding/revocation.
- Add owner-only Web/API configure and revoke paths.
- Add GitHub App JWT and installation-token client with strict parsing and injected fetch.
- Require paired Desktop bearer scope plus exact approved intent metadata before token issuance.
- Restrict Desktop issuance to one repository, `contents: write`, and <= one hour. Keep
  `pull_requests: write` inside the API process. For Draft lookup and creation, mint an API-held,
  repository-scoped token with exactly `Contents: read + Pull requests: write`, because GitHub must
  read the approved base and head refs while creating the Draft.
- Reserve a durable non-secret quarantine marker before provider mint. Treat the grant finalizer's
  active-binding CAS as the issuance linearization point and return the in-memory token to Desktop
  only after that CAS succeeds; the token is never persisted.
- If binding revocation wins after provider mint, never return the token and revoke it through an
  exact `204` provider response. When revocation cannot be confirmed, retain the marker and return
  only `credential_revocation_pending`, never `binding_inactive`, until pre-POST credential absence
  or exact-`204` provider revocation is durably confirmed. The unresolved marker must not be
  cleared by elapsed time because a client
  timeout does not prove when GitHub completed an already accepted mint request.
- Return token only to Desktop main; never include it in Team snapshots or renderer IPC results.
- Preserve the exact provider `expires_at` independently from the local-effective expiry. Recover a
  durably issued-but-lost response only after a no-mint, exact-installation GitHub App read supplies a
  strict provider `Date` at least two seconds later. Treat the one-second maximum forward lead of
  that GitHub `Date` clock relative to token-expiry enforcement as an explicit trusted-provider
  assumption; any absent, invalid, redirected, early, or mismatched observation remains blocked.

Verification: seed/Postgres parity, auth/role/project negative paths, token narrowing, expiry,
revocation, malformed response, sanitized-error, and secret-absence tests. Defer provider mint across
binding revocation and verify the issuance linearization point, exact `204` compensation, no token
return or persistence, indefinite pending quarantine after uncertain compensation, and identical
credential-absence-or-revocation confirmation clearance in both repositories.

## Slice 4 — Idempotent Branch Publication

User outcome: Desktop publishes exactly the approved commit to exactly the approved branch without
force-push and can reconcile an ambiguous result.

- Add a trusted git publication service with an injected command runner/credential helper seam.
- Verify clean worktree, expected HEAD, repository remote, base ancestry, and approved intent.
- Push one expected commit ref to one namespaced branch; do not publish other refs.
- Before retry, read the remote ref. Exact expected commit is success; any other commit is a typed
  conflict requiring operator recovery.
- Bound time, cancellation, output capture, and credential lifetime; redact all returned evidence.
- Persist `publishing_branch` -> `branch_published` atomically and recover after restart.

Verification: local bare-remote tracer, duplicate click, timeout-after-success reconciliation,
non-fast-forward conflict, no-force/no-tags assertions, restart recovery, token/output redaction.

## Slice 5 — Draft Pull Request

User outcome: the approved PR Delivery Package creates exactly one real Draft pull request bound to
the published commit.

- Add strict GitHub REST client for exact head/base lookup and Draft creation.
- Have the API independently read the remote branch head and require the approved expected commit
  before Draft creation.
- Reconcile an existing matching Draft before create/retry.
- Treat a `403` or `422` with one canonical bounded `Retry-After` header as recoverable
  `github_rate_limited`; persist only the derived provider retry not-before, reconcile by exact
  marker first, block another create before that boundary, and never retain the provider header or
  body.
- Reject a matching branch with the wrong expected commit or an incompatible existing pull request.
- Persist pull-request number, safe URL, Draft state, head/base, expected commit, and timestamp.
- Advance the PR Workflow node only after durable branch and Draft evidence exists.
- Require that evidence in Acceptance.

Verification: fake-fetch REST tests, API status taxonomy, ambiguous create recovery, duplicate
prevention, Workflow/Acceptance contract tests, Desktop link rendering.

## Slice 6 — Recovery, Revocation, And Operator UX

User outcome: failures and restarts always present one safe next action, and credential revocation
blocks a new delivery.

- Add distinct explicit actions: Revise for a pre-publication material change, Resume for the same
  `recovery_required` attempt, and Retry only after `failed`/`revoked`. Retry creates the next
  attempt/request/key only after the exact remote predecessor is proven terminal to the current
  pairing claimant; a missing, ambiguous, or non-terminal predecessor fails closed. After that
  proof, rebind creates a new series at attempt one. A rotated claimant creates and claims a new
  Work Request/Run instead of taking over the old Run; completed never reopens.
- Enforce at most one non-terminal attempt for a Run/PR target and never reuse an approval from an
  older intent revision or attempt.
- When the immediately prior same-series attempt is terminal `failed/pull_request_failed` after an
  exact verified publication, let the separately approved next attempt atomically adopt that
  publication by source id. It proceeds directly to Draft reconciliation with no new credential,
  git push, or remote-head verification; every immutable binding/run/workspace/ref/SHA/evidence
  field must match and all missing or ambiguous history fails closed.
- Add cancellation before remote write and between bounded phases. Stop durably enters
  `recovery_required`: before first submission, explicit Resume submits the same immutable attempt;
  after submission, explicit Resume reconciles the existing request. Background scheduling performs
  neither action.
- Persist `failed`/`revoked` only from an exact remote terminal snapshot or binding convergence;
  non-terminal provider, transport, expiry, and unknown errors park in `recovery_required`.
- Surface typed redacted outcomes in Desktop and non-secret configuration status in Web.
- Add a packaged Desktop **Verify credential revocation** action for one completed intent. Renderer
  input is only the exact local intent CAS; Electron main derives the remote request and uses the
  encrypted paired authority. Only `binding_inactive` after every overlapping non-secret quarantine
  marker has a durable pre-POST credential-absence or exact-`204` revocation confirmation is a
  passing check. `credential_revocation_pending` remains a safe,
  operator-recheckable non-passing result without a time-based escape hatch; the renderer never
  receives the Desktop Bearer or credential response, and an unexpected success performs no
  publisher/git/PR action and fails closed.
- Add operator documentation for App setup, repository installation, Project binding, revocation,
  retry, conflict recovery, and worktree cleanup.
- Confirm no remote merge/close/delete action exists.

Verification: fault-injection matrix, cold-start recovery, Stop before/after first submission,
same-series terminal Retry, non-terminal Retry rejection, rebind attempt-one, revoked-before-token
and revoked-before-retry, revoke-during-mint exact `204` compensation, uncertain-compensation
`credential_revocation_pending`, credential-absence-or-revocation confirmation clearance,
cross-attempt verified publication adoption with zero duplicate credential/push, audit/redaction scan, and operator
guide contract test. A normally issued or consumed token whose issuance linearization point preceded
revocation is not a post-revocation new issuance; the passing proof does not claim all such older
credentials are already invalid.

## Slice 7 — 1.x Completion Gate

User outcome: a non-maintainer can complete the full governed delivery story without ad hoc
maintainer intervention.

For this gate, non-maintainer is a procedural role: an independent operator who did not author or
modify the frozen candidate and who uses only the documented Web and packaged Desktop surfaces after
pre-run sandbox setup. Shell, direct HTTP, SQL, GitHub CLI, source/evidence edits, undocumented state
repair, or a maintainer-provided workaround during the run disqualifies the result.

- Run the complete deterministic local matrix and exact-SHA CI.
- Package Desktop and perform a fresh isolated Web/API/Postgres/Desktop walkthrough.
- Use a separately authorized GitHub sandbox repository for one candidate-bound Draft PR walkthrough.
- Prove one Work Request, one canonical Run, one expected commit, one approved branch publication,
  one Draft pull request, Acceptance, restart recovery, and credential revocation.
- Record only redacted metadata; do not retain tokens, local paths, raw patches, stdout, or stderr.
- Resolve all P0/P1 findings in the core path.
- Update Roadmap current truth and mark 1.x complete only after every gate passes.

2.x implementation remains blocked until this slice is complete and committed.
