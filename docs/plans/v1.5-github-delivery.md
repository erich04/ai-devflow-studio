# V1.5 GitHub 交付实施计划

生命周期：实施中

产品契约：`docs/product/prd/v1.5-github-delivery-prd.md`

权限决策：`docs/adr/0013-github-app-delivery-authority.md`

路线图位置：1.x 最后一个计划中的功能里程碑；第 7 批通过前，2.x 实施保持阻断。

<a id="working-rules"></a>

## 工作规则

- 每次实现一个端到端行为，依次完成公开行为失败测试、最小实现、针对性回归、文档和 Git 提交。
- 保留 V1.4 的本地优先、认证、脱敏、预算、策略和 Gate 边界。
- 默认 CI 绝不使用真实 GitHub 仓库。
- App 私钥与安装访问令牌绝不进入源码、测试样例、SQLite、Postgres、渲染器状态、日志、产物或证据文件。
- 交付达到持久化的安全状态前，保留受管工作树。
- V1.5 任一批次或 1.x 完成门禁未完成时，不得开始 V2.0 产品代码。

<a id="slice-1--delivery-intent"></a>

## 第 1 批：交付请求

用户结果：当前 PR 节点能准备精确、可审查的交付候选，不产生远端写入。

- 添加共享的交付请求、状态、批准、尝试和结果类型。
- 每个请求具有稳定的交付系列键和正整数尝试号，远端幂等键由该精确系列与尝试推导。
- 为正式 Run 解析最新完成的编码 Agent 运行及活动受管工作树。
- 在受管工作树中创建或验证一个本地提交。
- 绑定项目仓库/基础分支、带命名空间的发布分支、预期提交、Run/节点/版本、PR 交付包摘要、变更路径和通过的测试证据。
- 在 SQLite 中原子持久化请求，通过经过验证的 IPC 提供只读预览。
- 提交后仍脏、证据缺失、工作区过期、仓库/引用不安全或范围不匹配时，均拒绝继续。

验证：共享契约测试、一次性 Git 仓库测试、本地存储迁移/重启、IPC 解析测试及桌面预览组件测试。

<a id="slice-2--durable-approval"></a>

## 第 2 批：持久化批准

用户结果：lead/owner 通过已认证 Web 会话单独批准精确、脱敏的交付请求后，才可发布。

- 上传脱敏交付请求，并添加绑定正式请求摘要、不可变的会话 Cookie 批准。
- 要求当前有效 lead/owner 角色；桌面 Bearer 权限不能批准自己的请求。
- 仓库、分支、提交、Run/证据版本或产物任一变化，均使批准失效。
- 增加单调状态转换保护。发布前材料变化，在同一系列/尝试内创建新的不可变本地请求修订版，增加 API `intentRevision` 并使旧批准失效。
- Web 提供批准界面，桌面显示决定状态；清楚说明远端写入，不预选确认项或隐式执行。
- 记录脱敏审计事件，不包含路径、补丁、Git 输出或凭据。

验证：批准重放/过期测试、重复 IPC、重启恢复，以及证明预览和批准是两个独立动作的渲染器交互测试。

<a id="slice-3--repository-scoped-github-app-credential"></a>

## 第 3 批：限定仓库的 GitHub App 凭据

用户结果：owner 可为一个项目绑定/撤销 GitHub 交付，已获批准的桌面端可取得一个短期、最小权限令牌，而不会接触 App 密钥。

- 增加 Postgres 迁移以及种子/Postgres 仓库实现共有的安装绑定/撤销契约。
- 提供仅 owner 可用的 Web/API 配置与撤销路径。
- 增加 GitHub App JWT 和安装令牌客户端，严格解析并注入 fetch。
- 签发令牌前要求配对桌面 Bearer 的项目范围，以及精确、已批准的请求元数据。
- 桌面令牌限单仓库、`contents: write`、不超过一小时。`pull_requests: write` 留在 API 进程。Draft 查询与创建时，API 持有的仓库令牌精确限定为 `Contents: read + Pull requests: write`，以读取已批准的基础和发布引用。
- 服务商签发前，先持久化非敏感隔离标记。凭据授予终结器对有效绑定的 CAS 是签发线性化点；只有 CAS 成功才将内存令牌交给桌面端，令牌从不持久化。
- 服务商签发后若绑定撤销先胜出，绝不返回令牌，并通过服务商精确 `204` 响应撤销它。无法确认撤销时保留标记，只返回 `credential_revocation_pending`，不得返回 `binding_inactive`；必须等到 POST 前凭据不存在或精确 `204` 服务商撤销得到持久确认。未解决标记不得因时间流逝而清除，因为客户端超时不能证明 GitHub 何时完成已接收的签发请求。
- 令牌只返回桌面主进程，绝不加入团队快照或渲染器 IPC 结果。
- 单独保留服务商精确 `expires_at`，与本地有效期区分。对“已持久签发但响应丢失”的恢复，必须先执行不签发令牌、精确匹配安装的 GitHub App 读取，并取得至少晚于原始到期时间两秒的严格服务商 `Date`。显式信任假设是该 GitHub 时钟最多比令牌到期执行时钟快一秒；缺失、无效、重定向、过早或不匹配的观察均继续阻断。

验证：种子/Postgres 一致性、认证/角色/项目否定路径、权限收窄、到期、撤销、畸形响应、脱敏错误和秘密不存在测试。延迟服务商签发以跨越绑定撤销，验证签发线性化点、精确 `204` 补偿、不返回/持久化令牌、不确定补偿后的无限期隔离，以及两个仓库实现中一致的“凭据不存在或撤销确认”清除规则。

<a id="slice-4--idempotent-branch-publication"></a>

## 第 4 批：幂等分支发布

用户结果：桌面端只把精确批准的提交发布到精确批准的分支，不强制推送，并能对账不确定结果。

- 增加可信 Git 发布服务，注入命令执行器和凭据辅助程序接口。
- 验证干净工作树、预期 HEAD、远端仓库、基础分支祖先关系和已批准请求。
- 扫描确切的出站 Git 对象，包括中间提交、元数据、文本/二进制对象和被 attributes 隐藏的对象。在请求任何 GitHub 凭据前原子持久化不含秘密的扫描回执；扫描不完整时拒绝继续，不签发令牌。
- 只把一个预期提交引用推送到一个命名空间分支，不发布其他引用。
- 重试前先读取远端引用；精确预期提交视为成功，其他提交视为需要操作员恢复的明确冲突。
- 限制耗时、取消、输出捕获及凭据生命周期，所有返回证据均脱敏。
- 原子持久化 `publishing_branch` → `branch_published`，支持重启恢复。

验证：本地裸仓库远端、重复点击、成功后超时对账、非快进冲突、禁止强推/标签断言、重启恢复和令牌/输出脱敏。

<a id="slice-5--draft-pull-request"></a>

## 第 5 批：Draft PR

用户结果：已批准的 PR 交付包创建且仅创建一个真实 Draft PR，绑定已发布提交。

- 增加严格的 GitHub REST 客户端，按精确 head/base 查询并创建 Draft。
- 请求 PR 写入权限前，单独扫描精确 PR 标题和正文。证据脱敏和 Git 对象扫描回执不授权这一独立的出站文本通道。
- API 独立读取远端分支头，确认其等于已批准的预期提交后才创建 Draft。
- 创建/重试前，先对账已存在的匹配 Draft。
- 携带一个合法、有界 `Retry-After` 的 `403`/`422` 归类为可恢复的 `github_rate_limited`；仅持久化推导出的最早重试时间，先按精确标记对账，到达该时间边界前禁止再次创建，绝不保留服务商响应头或正文。
- 分支匹配但预期提交错误，或已存在不兼容 PR 时拒绝继续。
- 持久化 PR 编号、安全 URL、Draft 状态、head/base、预期提交和时间戳。
- 只有分支与 Draft 证据持久化后，才推进 PR 工作流节点。
- 业务验收必须要求这些证据。

验证：模拟 fetch REST 测试、API 状态分类、不确定创建结果恢复、重复防护、工作流/业务验收契约和桌面链接呈现。

<a id="slice-6--recovery-revocation-and-operator-ux"></a>

## 第 6 批：恢复、撤销与操作体验

用户结果：失败或重启后始终有一个安全的下一步，凭据撤销能阻止新交付。

- 分开提供显式动作：Revise 修订发布前材料；Resume 恢复同一 `recovery_required` 尝试；Retry 仅用于 `failed`/`revoked`。重试前，当前配对认领者必须证明精确远端前序尝试已经终止，才能创建下一个尝试/请求/键；前序缺失、不确定或未终止时拒绝。完成该证明后，重新绑定从新系列的第一次尝试开始。认领者轮换后须创建并认领新工作请求/Run，不能接管旧 Run；已完成请求绝不重开。
- 同一 Run/PR 目标至多存在一个非终态尝试，绝不复用旧修订版或旧尝试的批准。
- 同系列紧邻前一次尝试在精确发布已核验后以 `failed/pull_request_failed` 终止时，单独获批的新尝试可按源发布 ID 原子复用该发布证据，直接进入 Draft 对账，不再取凭据、推送或验证远端分支头。所有不可变绑定/Run/工作区/引用/SHA/证据字段须完全匹配，缺失或不确定历史一律拒绝。
- 支持远端写入前及有界阶段间取消。Stop 持久进入 `recovery_required`；首次提交前的显式 Resume 提交同一不可变尝试，提交后的 Resume 先对账既有请求。后台调度不执行这两种恢复动作。
- 只有精确远端终态快照或绑定状态收敛才能持久化 `failed`/`revoked`；非终态服务商错误、传输错误、到期和未知结果停在 `recovery_required`。
- 桌面显示有类型的脱敏结果，Web 显示非敏感配置状态。
- 确切的出站 Git 对象或 PR 标题和正文命中凭据时，均返回 `content_scan_blocked`。操作员不得恢复（Resume）或覆盖；只能创建新的 Work Request/Run，在干净的 Coding Agent 工作空间重新实现并测试。Git 内容阻断在推送前，PR 文本阻断可能在发布已核验后；旧请求不再写远端，但不能据此声称远端分支不存在。
- 为一个已完成请求提供打包桌面端 **Verify credential revocation**（验证凭据撤销）。渲染器仅传精确本地请求 CAS；主进程推导远端请求并使用加密配对权限。所有重叠非敏感隔离标记持久确认 POST 前凭据不存在或精确 `204` 撤销后，`binding_inactive` 才算通过。`credential_revocation_pending` 是可由操作员重新检查的安全未通过状态，没有基于时间的绕过方式。渲染器始终收不到桌面 Bearer 或凭据响应；意外成功不得执行发布器/Git/PR 动作，必须拒绝继续。
- 补充 App 配置、仓库安装、项目绑定、撤销、重试、冲突恢复和工作树清理文档。
- 确认不存在远端合并/关闭/删除动作。

验证：故障注入矩阵、冷启动、首次提交前后 Stop、同系列终态 Retry、拒绝非终态 Retry、重新绑定从首次尝试开始、取令牌/重试前撤销、签发期间撤销的精确 `204` 补偿、不确定补偿的 `credential_revocation_pending`、凭据不存在或撤销确认清除、跨尝试复用已核验发布且不重复凭据/推送、审计脱敏扫描和操作指南契约。撤销前已越过签发线性化点且正常签发或消费的令牌，不属于撤销后新签发；通过证明不声称所有旧凭据都已失效。

<a id="slice-7--1x-completion-gate"></a>

## 第 7 批：1.x 完成门禁

用户结果：非维护者无需临时维护者介入，就能完成受治理的完整交付流程。

这里的非维护者是操作规程角色：未编写或修改冻结候选的独立操作员，在演练前完成沙箱准备后，只使用文档中的 Web 与打包桌面界面。演练中使用命令行、直接 HTTP、SQL、GitHub CLI、修改源码/证据、未记录的状态修复或维护者提供的临时绕过方案，均使结果失效。

- 运行完整确定性本地矩阵和精确 SHA CI。
- 打包桌面端，执行全新隔离 Web/API/Postgres/桌面演练。
- 使用单独获授权的 GitHub 沙箱仓库，完成绑定候选的一次 Draft PR 演练。
- 证明一条工作请求、一个正式 Run、一个预期提交、一次已批准分支发布、一个 Draft PR、业务验收、重启恢复和凭据撤销。
- 只记录脱敏元数据，不保留令牌、本地路径、原始补丁、标准输出或错误输出。
- 解决核心路径全部 P0/P1 问题。
- 所有门禁通过后才更新路线图当前事实，并标记 1.x 完成。

本批次完成并提交前，2.x 实施保持阻断。

<a id="commit-sequence"></a>

## 提交顺序

1. `docs: define v1.5 GitHub delivery contract`（定义交付契约）
2. `feat: add durable GitHub delivery intent`（持久化交付请求）
3. `feat: require exact delivery approval`（要求精确批准）
4. `feat: add project-scoped GitHub App credentials`（限定项目凭据）
5. `feat: publish approved delivery branches`（发布已批准分支）
6. `feat: create idempotent GitHub draft pull requests`（幂等创建 Draft PR）
7. `feat: add GitHub delivery recovery and operator UX`（恢复与操作体验）
8. `docs: close v1.5 and the 1.x completion gate`（记录 V1.5 与 1.x 验收完成）
