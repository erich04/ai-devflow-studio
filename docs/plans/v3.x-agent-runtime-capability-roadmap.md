# V3.x Agent Runtime Capability Roadmap

Status: Draft for review; not yet promoted into `docs/roadmap.md`

Date: 2026-08-26

Baseline: AI DevFlow Studio 2.2.0 candidate at `4ddd754`

## Purpose

V3.x should turn DevFlow's strong Workflow and execution-governance foundation into a practical,
general Coding Agent. The target is not to copy Claude Code screen by screen. The target is to build
the same essential capability layers while keeping DevFlow's existing advantages: explicit scope,
permissions, human Gates, evidence, budgets, managed worktrees, restart safety, and redacted Team
projection.

The source comparison found that DevFlow already has a strong control plane, but its model-driven
data plane is incomplete. This draft deliberately chooses the following product order:

```text
V3.0 reasoning foundation
  -> V3.1 native coding tools
  -> V3.2 Skills and MCP extensions
  -> V3.3 Context and Memory intelligence
  -> V3.4 real Multi-Agent execution
  -> V3.5 headless Runtime productization
  -> V3.6 Agent workbench surface and V3.x closeout
```

This order does not silently treat the existing Workflow or fixed V2.2 DAG as an Agent task system.
Session TaskProjection is added to the V3.0 foundation; a durable Background Manager becomes a
V3.4 prerequisite. Schedule/Cron, Goal/Monitor, notification Channels, and open-ended background
automation are explicitly deferred. A timer must never call a Provider directly.

## Current Release Boundary

V2.0, V2.1, and V2.2 feature milestones are complete and pushed to the remote candidate branch.
Formal `v2.2.0` signoff is still open: the release-only evidence commit, annotated tag, and published
release do not yet exist. V3.x planning can continue now, but V3 implementation should start only
after formal V2.2 closeout, unless the Roadmap explicitly records an exception.

## V3.0 Dependency

The separately authored V3.0 Markdown was not present in the active checkout, local branches, or
the searched workbench paths during this review. This document therefore does not replace or
rewrite V3.0.

The V3.1+ sequence assumes that V3.0 delivers these P0 foundations identified by the source
comparison:

1. an append-only, replayable Session Event Ledger;
2. a streaming Provider Runtime with typed retry, cancellation, usage, and fallback events;
3. a model-driven General Agent Loop inside the existing bounded Agent Runtime;
4. Context Budget and Compact with safe resume and tool request/result pairing;
5. versioned `PromptSection` and Context Assembler contracts with a stable-prefix policy and token
   budget, even if advanced retrieval quality comes later;
6. host-port contracts for persistence, Provider, Tool, permission, credentials, workspace, clock,
   events, and policy, with Electron main as the first adapter;
7. a session-local TaskProjection for the Agent's visible plan and progress, separate from
   deterministic Workflow Nodes and the V2.2 Coordination DAG;
8. budgeted per-turn injection of the existing V2.1 Durable Memory and Knowledge Citations, without
   creating a second Memory store.

Before V3.1 implementation begins, the real V3.0 document must be linked and checked against these
dependencies. Any missing foundation stays in V3.0; it must not be silently moved into a later
version.

Session `fork` and `rewind` mean creating a new Ledger branch from an earlier event. They never
delete original events or undo an already accepted file, Git, process, Tool, or MCP side effect.
Those effects require a compensating action or human recovery.

## Evidence Basis

This proposal is grounded in the 2026-08-25 Claude Code comparison at the same `4ddd754` source
baseline. The following code facts determine the version order:

| Existing asset | Current limit | V3.x treatment |
| --- | --- | --- |
| Shared Agent Runtime state machine | Strong bounds/checkpoints, but the general Desktop path is effectively one step | Evolve it into the single Loop kernel |
| Native Coding Executor | Fixed plan/read/edit/test/one-repair flow | Replace the product path with the General Loop; retain compatibility evidence |
| Native Tool registry | Six narrow Tool families with strong grant/audit controls | Extend the registry in V3.1; do not create another Tool runtime |
| Provider path | Primarily one structured `/chat/completions` request | V3.0 streaming/retry/fallback contract |
| Local MCP | Trusted stdio contract, narrow product wiring | V3.2 product lifecycle, then separately governed remote transport |
| V2.1 Memory | Strong promotion/revision/expiry/tombstone governance | Inject in V3.0 and improve quality in V3.3; keep the same authority model |
| V2.2 Coordination | Strong fixed DAG/lease/budget control plane | Attach real shared-Loop Specialists in V3.4 |

The comparison's broader work-orchestration findings are handled explicitly: TaskProjection is a
V3.0 dependency, Background Manager is V3.4 Slice 1, and scheduler/monitor/channel automation is
deferred rather than being mislabeled as Workflow or Multi-Agent functionality.

## V3.x Product Contract

At the end of V3.x, one developer should be able to give DevFlow a repository goal and receive a
reviewable result from a DevFlow-owned Agent that can:

- continue a multi-turn session, resume after restart, fork, rewind, and compact safely;
- stream model output and repeatedly choose authorized tools from real environment feedback;
- search, read, patch, run bounded commands and tests, inspect Git state, and recover without
  repeating accepted side effects;
- load governed Skills, Hooks, Commands, and MCP capabilities on demand;
- use scoped project knowledge and durable Memory in each relevant turn;
- delegate bounded work to Specialists that run the same Agent Loop;
- run through Electron or a headless host without changing its core semantics;
- expose files, diagnostics, terminal output, diffs, sessions, permissions, and evidence in one
  coherent developer surface.

Agent success still cannot approve a Gate, publish a branch, open or merge a pull request, change
policy, or widen its own authority.

## V3.1 — Safe Native Coding Tool Platform

### Outcome

The General Agent Loop can complete ordinary repository repair tasks through DevFlow-owned tools,
instead of relying on a fixed read/edit/test plan or delegating the work to OpenCode.

### Delivery slices

1. Freeze versioned Tool contracts and a deterministic coding-task evaluation set.
2. Add repository glob/search, bounded multi-file read, patch/edit, file create/delete, and Git
   status/diff tools.
3. Add a foreground-only governed process runner for allowlisted project commands, with streamed
   output, timeout, cancellation, output spill, a clean environment, and managed-worktree
   containment. Long-lived or detached processes wait for the V3.4 Background Manager.
4. Route every request, result, permission, retry, usage record, and side-effect receipt through the
   V3.0 Ledger and existing capability-grant audit.
5. Keep OpenCode as a compatibility executor and measure the same tasks on both executors.

### Completion gate

- A DevFlow-owned Agent completes a multi-file `search -> read -> patch -> test -> inspect diff`
  task with at least three model-driven Tool turns.
- Permission rejection, process timeout, cancellation, malformed input, oversized output, and
  restart recovery all fail safely.
- Resume repeats zero accepted writes or commands.
- A model cannot execute an unregistered command, escape the managed worktree, or expand its Tool
  grant.
- Native/OpenCode results use the same terminal result, diff, Test Evidence, and cleanup contract.
- The frozen default evaluation is deterministic and makes no paid Provider call.

### Deferred

Remote shell, arbitrary system administration, package publishing, deployment, and unrestricted
network access remain outside V3.1.

## V3.2 — Governed Skills And MCP Extension Runtime

### Outcome

Capabilities can be added without hard-coding every workflow into Electron main, while all loaded
content and executable authority remain versioned, inspectable, and policy-bound.

### Delivery slices

1. Define a `SkillPackage`: a versioned manifest plus `SKILL.md`, with optional scripts, assets,
   templates, and references. Record digest, origin, dependencies, permissions, and compatibility.
2. Add a Skill loader with built-in, Team, project, and user scopes; deterministic precedence;
   explicit enablement; update review; and rollback.
3. Add versioned Commands and lifecycle Hooks. Hooks may observe or request an action, but cannot
   bypass the same capability and Gate checks as a model-selected Tool.
4. Add Tool Search and lazy schema loading, then feed Skill and MCP discovery through it so the
   model sees only relevant definitions.
5. Complete the trusted local stdio MCP lifecycle first: connection health, restart, reconnect,
   capability refresh, and `list_changed`, while retaining exact installation authority.
6. Treat remote Streamable HTTP, OAuth, resources, and prompts as a separately frozen V3.2 slice.
   It requires a new ADR for network, credential, callback, refresh, and Team/local authority before
   implementation; without that ADR, V3.2 cannot claim remote MCP parity.
7. Persist the exact discovered capability set needed for resume and Compact rehydration.
8. Add supply-chain checks for package origin, executable digest, dependency lock, environment
   allowlist, secret access, and version rollback.

### Completion gate

- A new local Skill can be installed, reviewed, enabled, discovered, used, disabled, and rolled back
  without changing application code.
- A local MCP connection can disconnect, restart, refresh its Tool list, and resume a session without
  duplicating a non-idempotent call.
- Remote MCP completion is accepted only after the dedicated ADR and its HTTP/OAuth negative-path
  matrix pass; otherwise the capability is recorded as deferred rather than implied.
- Compact and restart restore the exact enabled Skill/MCP versions or stop on a mismatch.
- Project or Team metadata cannot directly choose an executable, credential, cwd, or secret value.
- Renderer and Team projections expose status and safe provenance, not raw secrets or private tool
  results.

### Deferred

An open public marketplace and automatic execution of unreviewed third-party packages remain out of
scope.

## V3.3 — Context And Memory Quality

### Outcome

The V3.0 Context Assembler becomes measurably useful: each model turn receives the smallest relevant
context assembled from session history, project rules, retrieval, Skills, MCP state, TaskProjection,
and durable Memory. DevFlow can learn across sessions without treating generated summaries as facts.

### Delivery slices

1. Evolve the V3.0 Context Assembler with measured section budgets, relevance selection, stable
   prefix reuse, and overflow diagnostics.
2. Improve the existing per-turn Knowledge and Durable Memory injection with source, scope, version,
   freshness, confidence, and utility provenance.
3. Add turn/session-boundary Memory extraction, deduplication, conflict handling, expiry, human or
   policy promotion, and negative feedback.
4. Complete three-stage context reduction: result spill/snip, deterministic microcompact, and
   semantic compact with a durable boundary.
5. Rehydrate project instructions, plan, enabled Skills, MCP instructions, discovered Tools,
   citations, and active Memory after Compact.
6. Add quality and cost evaluation for retrieval relevance, citation faithfulness, Memory utility,
   compact retention, cache reuse, and context-overflow recovery.

### Completion gate

- A long session crosses at least two Compact boundaries and still completes the task with no orphan
  Tool request/result pair.
- Resume and fork reproduce the selected session branch while rewind preserves original facts.
- Required project constraints and active permissions survive Compact; stale or deleted Memory does
  not reappear.
- Long-term Memory improves a frozen cross-session scenario set against numeric quality and cost
  floors defined in the V3.3 PRD, without scope leaks or unsupported claims.
- Original Ledger events remain the audit source; summaries and retrieved Memory remain derived
  context.

### Deferred

Unreviewed self-modifying system prompts and automatic promotion of sensitive Memory remain out of
scope.

## V3.4 — Real Governed Multi-Agent Execution

### Outcome

The V2.2 Supervisor, DAG, lease, budget, retry, and tenancy control plane drives real Specialists.
Every Specialist uses the same V3 Agent Loop, Provider, Ledger, Context, Tool, Skill, and MCP
contracts as the primary Agent.

### Delivery slices

1. Add a durable Background Task Manager with explicit ownership, foreground/background transition,
   status, result notification, cancellation, restart recovery, and no timer-to-Provider shortcut.
2. Replace fixed Specialist result generation with the shared General Agent Loop.
3. Add bounded model-assisted task decomposition that compiles into the existing validated DAG;
   runtime policy still enforces maximum Agents, depth, concurrency, retry, cost, and wall time.
4. Give each Specialist an isolated session branch, context budget, Tool grant, transcript, and
   managed worktree or read-only snapshot.
5. Add durable mailbox, join, result notification, cancellation, and supervisor synthesis.
6. Add conflict detection and deterministic merge/review rules for work produced in parallel.
7. Project only redacted team-level progress and evidence; raw specialist prompts, source, and
   outputs stay local.

### Completion gate

- One bounded task is decomposed into at least two useful Specialist tasks, executed concurrently,
  joined, and synthesized into one reviewable result.
- Restart resumes every Agent from its own consistent Ledger/checkpoint and repeats zero accepted
  external effects.
- Parent cancellation terminalizes child Runtimes, process work, leases, and pending permissions.
- Cross-Agent scope, capability, workspace, session, and Memory access attempts fail closed.
- Multi-Agent quality gain and cost/latency overhead are measured against the single-Agent baseline;
  Multi-Agent is used only where the frozen evaluation shows value.

### Deferred

Open-ended swarms, uncontrolled recursive delegation, and remote untrusted executors remain outside
V3.4.

## V3.5 — Headless Runtime Productization

### Outcome

The host-port contracts frozen in V3.0 become a supported second host. Electron remains one trusted
host, but the same core can also run through a local headless interface for automation, testing, and
future integrations.

### Delivery slices

1. Stabilize the existing host-port compatibility and versioning rules based on V3.0–V3.4 usage.
2. Verify that host-independent Loop, Session, Context, Compact, Tool selection, and orchestration
   remain in shared Runtime packages rather than Electron orchestration files.
3. Keep Electron adapters over the existing SQLite, credential, worktree, Tool, MCP, Workflow, and
   Policy services, and add equivalent local headless adapters.
4. Add a local headless CLI/API with start, attach, stream, pause, resume, fork, rewind, cancel, and
   export commands.
5. Version the public request/event/session formats and add backward-compatible migration tests.
6. Run the same conformance suite against Electron and headless hosts.

### Completion gate

- The same deterministic session produces equivalent ordered Runtime events and terminal results in
  Electron and headless hosts.
- No business decision depends directly on Electron IPC or renderer types.
- Credentials, paths, Tool execution, and persistence remain host-owned adapters; the shared core
  cannot access them without an explicit port.
- A headless session can be interrupted and resumed without a running renderer.
- Headless productization introduces no duplicate Runtime state machine or parallel source of truth.

### Deferred

Hosted SaaS execution, public remote control, and multi-tenant provider credential custody remain
outside V3.5.

## V3.6 — Agent Workbench Surface And V3.x Closeout

### Outcome

The Runtime capabilities become understandable and efficient for daily development, and the V3.x
claim is closed with candidate-bound Runtime evaluation rather than being blocked by the breadth of
an embedded IDE.

### Delivery slices

1. Add repository tree, full-text search, changed-file navigation, and bounded file context.
2. Add integrated process/terminal output views and a versioned diagnostics adapter; an embedded
   editor or broad LSP client is not required for the V3.x Runtime claim.
3. Add inline diff with partial accept/reject, compensating undo where safe, and exact Evidence
   linkage.
4. Add session timeline, fork/rewind/Compact markers, permissions, Agent/subagent status, Tool/MCP
   health, token/cost budgets, and failure remediation.
5. Freeze a V3.x capability evaluation that covers single Agent, long session, Tools, Skills, MCP,
   Memory, Multi-Agent, headless parity, and developer walkthroughs.
6. Run full unit, integration, migration, Electron, packaged, headless, cross-platform, security,
   deterministic evaluator, and explicitly bounded real-provider gates before tagging.

### Completion gate

- A new user can open a repository, start or resume a governed Agent session, inspect streamed work,
  answer permissions, review available diagnostics and diff, run tests, and hand the result back to
  Workflow.
- The packaged Desktop and headless host pass the same Runtime conformance suite.
- The frozen evaluation records quality, recovery, cost, latency, human intervention, isolation,
  redaction, and repeated-side-effect metrics.
- No V3.x completion claim is made until the exact candidate, immutable evidence, tag, and published
  artifacts agree.

### Deferred

An embedded editor, full LSP language matrix, debugger, extension marketplace, remote collaborative
editing, and feature-for-feature Claude Code UI parity require a separately approved future charter.

## Cross-Version Engineering Rules

- Do not create a second Agent Runtime. Evolve the shared Runtime kernel and make Desktop, Native
  Coding, and Specialists use it through adapters.
- Evolve existing assets instead of creating parallel products: Session Ledger extends Agent
  Trajectory; V3.1 extends `native-tools`; V3.3 extends the ADR 0018 Memory lifecycle; V3.4 plugs the
  shared Loop into the ADR 0019 Coordination DAG; headless execution uses the same kernel.
- Keep Workflow, Gate, Policy, Evidence, and publication authority outside the Agent Loop.
- Treat Session Ledger as durable fact, Checkpoint as resumable Runtime state, Compact as a derived
  context projection, and Git commit as repository history.
- Persist observable inputs, decisions, tool actions, results, usage, and stop reasons; do not store
  hidden provider reasoning.
- Default CI stays deterministic and no-cost. Real-provider tests are explicit, bounded, and
  candidate-bound.
- Every side effect requires idempotency or an explicit ambiguous-result stop and human recovery.
- Every version begins with a frozen contract/evaluation slice and ends with candidate-bound
  evidence.
- Preserve V2.x data, migrations, local privacy, Team redaction, and OpenCode compatibility until a
  separately approved removal plan exists.
- Keep Schedule/Cron, Goal/Monitor, notification Channels, open-ended background automation, and
  timer-triggered Provider execution outside V3.x unless a later Roadmap promotion defines their
  authority, persistence, budget, and cancellation contracts.
