# DevFlow Studio V1.4: Pilot Trust Boundary PRD

Status: In development

Released baseline: `v1.3.0`

Milestone owner: DevFlow Studio maintainers

## Product Outcome

V1.4 turns the V1.3 request-to-delivery loop into a trustworthy external-pilot boundary. A team
must be able to run real providers and team workflows without silently bypassing authentication,
budget, evidence, redaction, or recovery controls when a dependency is missing or unavailable.

V1.4 remains a self-hosted pilot. It does not turn DevFlow into a public SaaS product or an
autonomous delivery bot.

## Release Musts

1. **Paid runtime trust:** real paid provider calls fail closed when the authoritative budget
   context is missing, invalid, unauthenticated, out of scope, or unavailable. Fake and verified
   no-cost paths remain explicit and deterministic.
2. **Authentication trust:** networked Team writes use signed session Cookies or paired Desktop
   Bearer Tokens. Unsigned identity headers remain limited to an explicit local demo/test mode and
   cannot be enabled by the pilot deployment contract.
3. **Durable remote sync:** canonical Run, Test, Review, and Coding summary work survives restart,
   uses bounded backoff, exposes operator recovery state, and preserves the V1.3 child-first and
   canonical-Run ownership invariants.
4. **Repository knowledge:** real repository Markdown indexing feeds Electron Gate, Knowledge
   Review, and Coding context. API Review uses only a separately authorized server-side or approved
   redacted knowledge source; local repository content is not uploaded implicitly.
5. **Web management closure:** authenticated users can create a work request, select a Run,
   create Desktop pairing codes, and submit role-checked Gate actions without creating a second
   workflow state machine.
6. **Reproducible pilot lifecycle:** unsigned Electron/Web/API pilot bundles have an explicit
   configuration contract and automated fresh-deploy, data-preserving upgrade, and bounded rollback
   smoke coverage.

The durable outbox is a V1.4 release requirement. It was already promised by the current README,
baseline PRD, backend data-source matrix, and V1.3 closeout plan; it is not deferred again.

## Paid Runtime Decision Contract

The decision is made before a real provider is initialized or invoked. A rejected decision must
leave understandable, redacted, persistent evidence and must not leave a managed worktree behind.

| Runtime mode | Required result |
| --- | --- |
| Explicit fake provider or trusted estimated cost `<= 0` | Allow as a no-cost path; do not describe it as budget-approved paid usage. |
| Real paid runtime with no budget guard | Block as `unavailable`. |
| Real paid runtime without a Local Project to Team Project binding | Block and direct the operator to pair the project. |
| Team-bound paid runtime with timeout, network failure, 401/403, 5xx, or malformed response | Block as `unavailable`; retain local state. |
| Team-bound paid runtime with no saved policy | Block and direct a lead to configure a policy. |
| Team-bound paid runtime with an explicitly saved `enabled: false` policy | Allow as an authenticated administrative decision and keep it distinct from missing/unavailable state. |
| Enabled policy within limit | Allow as `allowed` or `warning`. |
| Enabled policy over limit without a valid approval | Block as `requires_lead_approval`. |
| Enabled policy over limit with matching, unexpired approval | Allow as `approved_over_budget`. |

A budget approval is valid only for its exact project, provider, requester, additional-cost ceiling,
role, status, and expiry window. A TypeScript type assertion is not response validation; Desktop
must reject malformed budget decisions at runtime.

Release-only real-provider smoke remains a separate, explicitly authorized signoff operation. It
does not create an application-runtime bypass.

## Authentication Contract

- Production and pilot browser requests cannot construct identity from unsigned headers.
- Desktop Team writes require the paired project's Bearer Token and immutable project binding.
- Demo headers require the explicit development flag, a loopback-only deployment contract, and no
  browser `Origin`.
- Authentication, membership, role, scope, and decision failures are distinguishable in audit-safe
  output without leaking Cookies, Bearer Tokens, API keys, or provider credentials.

The V1.3 implementation already defaults unsigned headers off and rejects them for browser origins.
V1.4 validates this boundary in pilot configuration and closes remaining negative paths instead of
rewriting working authentication code without evidence.

## Durable Sync Contract

- The outbox stores entity identifiers and operation metadata, never raw provider prompts, stdout,
  stderr, patches, credentials, or a serialized upload payload.
- The sender rebuilds the redacted summary from canonical LocalStore state at send time.
- A stable idempotency key prevents duplicate logical work.
- Retryable failures use capped backoff; authentication, scope, immutable-ID conflicts, and other
  terminal failures become operator-visible without infinite retry.
- Restart resumes pending work. Re-pairing cannot send an old job into a different Team Project.
- Child evidence still uploads first. Only the exact canonical-Run-missing response may cause one
  canonical Run upload followed by one child retry.
- A lossy remote summary never replaces richer local state or advances the local workflow.

## Repository Knowledge Contract

- Git-managed Markdown remains the source of truth.
- Electron main owns repository path resolution, file access, indexing, limits, and symlink/path
  escape protection; renderer inputs cannot select arbitrary privileged files.
- Knowledge References include source path, section, strategy, score, and content hash.
- Retrieval references inform humans and Agents but do not themselves satisfy Governance Checks or
  approve Gates.
- API Review cannot obtain raw Desktop repository content through an implicit sync side channel.

## Web Authority Contract

The Team service owns Work Requests and collaboration commands; Desktop continues to own private
local repository execution and the canonical full-fidelity local Run.

- Web request intake creates a versioned Work Request, not a fabricated local Run.
- A Desktop explicitly claims a request and creates/binds the canonical local Run.
- Web Gate actions are authenticated, role-checked command requests with expected Run/policy
  versions. They cannot directly mutate a lossy Run summary or bypass local evidence checks.
- Explicit Run selection is stable and project-scoped.
- Pairing code creation is visible in the current Web shell and never exposes an existing token.

The exact Work Request and Gate command ownership model requires an ADR before those write paths are
implemented.

## Pilot Package Contract

V1.4 pilot packages mean reproducible, unsigned artifacts and containers with documented inputs,
health checks, migrations, and lifecycle smoke tests. They do not mean:

- signed/notarized installers;
- auto-update;
- managed cloud deployment;
- public distribution infrastructure.

Rollback support must state the schema compatibility window. A rollback test cannot claim safety
if the prior application cannot read the upgraded schema.

## Non-Goals

- Real GitHub push, pull-request creation, merge, or branch publication (V1.5).
- Public SaaS, billing, enterprise SSO, hosted multi-tenancy, or managed provider credentials.
- Real MCP execution, multi-Agent orchestration, or vector/full-RAG retrieval.
- Repository watcher, in-app Markdown editor, or implicit remote knowledge synchronization.
- Full multi-Desktop conflict resolution and collaboration hardening (V1.7).
- Signed installers, notarization, auto-update, or real Windows installer signoff.

## Release Acceptance

V1.4 is complete only when every Release Must has committed evidence against one candidate SHA:

- paid Coding and Knowledge Review providers are never invoked after missing, invalid, unavailable,
  unauthenticated, or out-of-scope decisions;
- budget approval scope and response validation negative tests pass;
- unsigned-header and pilot configuration negative tests pass;
- outbox restart, dedupe, backoff, terminal-error, manual-retry, and re-pairing isolation tests pass;
- one repository knowledge snapshot is used consistently by Gate, Review, and Coding without raw
  repository upload;
- Web request, selection, pairing, and Gate command flows pass authenticated role/scope tests;
- fresh deploy, upgrade with retained data, and declared rollback window pass;
- default verification remains deterministic and no-cost; any paid signoff is separately approved.

Package version alignment and release evidence are performed at candidate formation, not at the
start of development.
