# DevFlow Studio V1.5：GitHub 交付需求

生命周期：已实现；发布/签收待完成

路线图位置：1.x 最后一个计划中的功能里程碑

里程碑负责人：DevFlow Studio 维护者

<a id="problem-statement"></a>

## 问题陈述

V1.4 已能把经过身份验证的工作请求转成一个正式本地 Run，在受管工作树中实现、归档测试证据并生成脱敏 PR 交付包，但还不能把成果发布到 GitHub。PR 节点仅生成供人阅读的交接文本，无法证明要交付哪个本地提交、授权远端写入、发布分支或创建真实 PR。

因此 1.x 的受治理交付流程没有闭环。操作员必须离开 DevFlow，手工找回预期提交与分支、寻找凭据、推送并创建 PR。这可能误选仓库或过期工作树、绕过已记录证据、泄露过宽凭据、重复创建 PR，或在失败后让本地 Run 无法解释发生了什么。

<a id="solution"></a>

## 解决方案

V1.5 在现有本地优先权限模型上增加有界的 GitHub 交付。桌面主进程从正式受管工作树、预期提交、团队项目仓库绑定、当前 Run 版本和 PR 交付包推导不可变交付请求。在任何远端写入前，提交精确的脱敏请求，由 lead/owner 通过已认证 Web 会话明确批准。

批准后，API 签发仅限一个仓库、只有 Contents 写入权限的短期 GitHub App 安装令牌。桌面主进程只在内存持有令牌，将预期提交发布到批准分支，禁止强制推送。API 独立核对远端分支头，再创建且仅创建一个 Draft PR。持久交付状态记录每次转换，支持安全重试、重启恢复、凭据撤销及可审计的操作指引。GitHub 不成为正式本地 Run 的状态权威，V1.5 绝不合并 PR。

PR 交付包仍是交接产物，提供 Draft PR 标题、正文、证据引用和审查上下文；代码发布来源只有受管工作树和预期提交。

<a id="user-stories"></a>

## 用户故事

1. 开发者只能从当前正式 Run 已完成的编码 Agent 运行和活动受管工作树准备交付请求，防止发布过期或无关工作区。
2. 开发者在批准远端写入前，可看到精确团队项目、`owner/repository`、基础分支、发布分支、预期提交、Run 版本、证据版本和 PR 标题。
3. 开发者通过可信桌面主进程操作，从受管工作树创建预期本地提交，把变更路径和测试证据绑定到请求。
4. lead/owner 必须通过签名 Web 会话，对精确交付请求作出明确人工批准，随后才可发布分支或创建 Draft PR。
5. 发布前若工作树、预期提交、仓库绑定、分支、Run 版本或 PR 交付包变化，必须创建新的不可变本地请求修订版。同一尝试的材料修订增加 API `intentRevision`，使全部旧批准失效并要求重新审查。
6. 团队 owner 可把一个团队项目绑定到一个 GitHub App 安装和一个仓库，无需改变仅用于身份验证的 OAuth 会话。
7. 团队 owner 可看到交付凭据已配置、不可用、过期或已撤销状态，而不会看到私钥或安装令牌。
8. 操作员可撤销项目交付绑定，使新安装令牌无法越过签发线性化点并返回给该项目。若签发与撤销重叠，系统必须确认服务商凭据不存在或已撤销，否则报告不可绕过的待确认状态，不得声称撤销已证明。
9. 桌面只能凭配对项目的 Bearer 权限及已批准的精确请求申请令牌。
10. 桌面收到的安装令牌仅限一个仓库、`Contents: write`，有效期不超过一小时。
11. 安全审查者可确认 App 私钥留在 API 进程，安装令牌留在桌面主进程内存；二者不进入渲染器、SQLite、日志、产物、远端摘要或测试样例。
12. 远端仓库、安装、基础分支、受管工作树、预期提交、批准、凭据范围或证据绑定缺失/过期时，发布必须拒绝继续。
13. 系统拒绝交付命名空间以外的分支名，绝不强制推送、删除、重写或静默替换现有远端分支。
14. 推送结果不确定后重试，先检查远端分支；精确预期提交视为成功，不再执行第二次逻辑交付。
15. 桌面报告发布后，API 必须独立确认远端分支头等于批准的预期提交，随后才可创建 Draft PR。
16. Draft PR 响应不确定后重试，先按精确仓库、发布分支、基础分支和预期提交查询，再决定是否创建。
17. 同一尝试内的重复点击、渲染器重试、进程重启和重复 IPC 保持幂等，不得产生第二次分支发布或 Draft PR。
18. 处于 `approval_required`、`publishing_branch`、`creating_pr` 或 `recovery_required` 的交付，应提供明确的恢复动作。
19. 成功交付必须先记录远端分支、预期提交、PR 编号、Draft URL、创建时间和脱敏审计事件，Run 才可进入业务验收。
20. 审查者可从 PR 节点打开真实 Draft PR，将其记录的分支头与本地请求对照。
21. 业务验收者可核对同一正式 Run 内通过的测试证据、已批准请求、精确远端提交和 Draft PR。
22. 审查者可拒绝业务验收，而不会合并、关闭或修改 GitHub PR。
23. 操作员可通过有类型的脱敏结果区分认证、授权、安装、仓库、非快进、GitHub 校验、限流、超时和本地持久化失败。
24. 失败或被拒绝的交付可显式重试为下一次尝试，使用新请求及幂等键。已完成交付不可重试，终态请求绝不重开或覆盖。同系列紧邻前次尝试若已核验精确分支、仅在创建 Draft 时失败，新批准尝试复用其发布证据，不再次取凭据或推送。
25. 项目 owner 可依文档完成“工作请求 → 本地 Run → 实现 → 测试证据 → 明确批准 → GitHub Draft PR → 业务验收”，无需临时维护者介入。
26. 发布审查者通过确定性模拟 GitHub、本地 Git 远端、API/Postgres 集成、Electron 冒烟及单独授权的 GitHub 沙箱演练核验 1.x 完成门禁；默认 CI 绝不写真实仓库。

<a id="implementation-decisions"></a>

## 实施决策

1. **源码执行仍以本地为权威。** 桌面 SQLite 拥有完整交付请求、本地尝试和结果；Postgres 拥有脱敏远端请求、签名 Web 决定、团队项目安装绑定、凭据授予元数据与协作审计。GitHub 拥有已发布分支和 PR，不拥有工作流状态。
2. **GitHub App 认证与身份 OAuth 分开。** 现有 OAuth App 保留 `read:user user:email`，身份初始化后丢弃访问令牌，不扩大到仓库写权限。
3. **API 持有 App 私钥。** 由自托管配置提供，绝不存入 Postgres 或通过 API 返回。
4. **桌面使用临时 Contents 令牌。** API 为单仓库签发仅 `contents: write` 的令牌，一小时内到期，只由 Electron 主进程在活动尝试期间持有。API 创建 PR 使用单独 App 权限，该权限不离开 API 进程。
5. **项目安装绑定是非敏感元数据。** 组织、项目、仓库、安装 ID、配置状态、创建者、更新时间和撤销时间可持久化审计，私钥和令牌值不可。
6. **当前受管工作树是发布来源。** 请求必须解析已完成编码运行的 `managedWorkspaceId`、活动工作区、分支、基础分支、变更路径和通过的测试证据。
7. **必须存在本地预期提交。** 主进程在受管工作树中创建/验证一个提交并记录完整 SHA；该提交之后出现脏状态会使发布失效。
8. **PR 交付包仅为元数据。** 当前标题/正文/证据版本参与请求摘要；交付包不能选择仓库、分支、工作树或凭据。
9. **批准是远端、精确且不可变的。** 有效 lead/owner 通过会话 Cookie 批准脱敏请求。批准绑定请求摘要、项目、仓库、base/head、预期提交、Run/节点/版本、证据版本、批准者和时间，不能授权修改后的请求；桌面 Bearer 不能批准自身请求。
10. **发布具有持久状态机。** 状态为 `approval_required`、`approved`、`publishing_branch`、`branch_published`、`creating_pr`、`completed`、`failed`、`recovery_required`、`revoked`。`completed`/`failed`/`revoked` 是不可回退的终态。本地 `failed`/`revoked` 仅能镜像精确远端终态请求或绑定收敛；没有此证明的服务商、传输、到期或未知结果进入 `recovery_required`。只有显式 Resume 才恢复同一尝试。首次提交前 Stop 可通过 Resume 提交同一不可变尝试；提交后 Stop 的恢复先对账既有请求。
11. **交付系列、尝试和修订具有独立身份。** 稳定 `deliverySeriesKey` 由组织、团队/本地项目、Run、PR 节点、绑定 ID/版本和受管工作区推导。发布前材料变化在同一系列/尝试中创建新的不可变本地请求；API 修订同一请求、增加 `intentRevision` 并使旧批准失效。只有前次为 `failed`/`revoked` 时才可显式重试；桌面必须通过当前配对认领者观察到唯一精确远端前序处于匹配终态，再增加 `deliveryAttempt` 并生成新请求/幂等键。远端权威缺失、不确定或非终态时拒绝；认领者轮换须创建并认领新请求/Run，不能接管旧 Run。相同证明后，仓库重新绑定从新系列第一次尝试开始；同一 Run/PR 目标最多一个非终态尝试。后续尝试仅可复用紧邻前次、终态为 `failed/pull_request_failed` 的已核验发布，所有不可变系列字段及摘要须匹配；复用发布不包含本次凭据授予，记录精确源发布 ID。
12. **分支发布无破坏性。** 首版只推送一个精确提交引用到一个命名空间发布分支，不推送标签、全部引用或合并提交，不强制推送。
13. **API 独立核验发布。** 桌面报告安全发布结果；API 读取 GitHub 分支，只有其头等于批准的预期提交才推进。
14. **不确定远端结果先对账再重试。** 精确远端提交或匹配 Draft 可接受；冲突进入 `recovery_required`。终态 Draft 失败后的新批准尝试，先复用精确已核验发布，再对账 Draft，不产生第二次 Contents 凭据或分支推送。
15. **渲染器无特权。** 它可通过经验证 IPC 请求预览、显式修订发布前请求、重试符合条件的终态尝试、恢复并显示远端决定，不能选择尝试号、文件路径、远端 URL、凭据、原始 Git 参数或任意 GitHub 请求体。
16. **GitHub 响应严格按白名单解析。** 仅标识符、状态、Draft 标记、安全 URL、head/base 和 SHA 可持久化；原始响应头/正文不保存。GitHub `403`/`422` 携带单个合法有界 `Retry-After` 时归类为可恢复的 `github_rate_limited`；API 仅保存推导的最早重试时间。下次显式 Resume 先按精确标记对账，时间边界前不得创建。原始服务商响应头和正文绝不持久化。
17. **业务验收要求 GitHub 交付证据。** 项目启用 V1.5 交付后，仅有 PR 交接产物不能完成业务验收。
18. **凭据返回前完成签发线性化。** 预留授予时，在服务商签发前持久化非敏感隔离标记。授予终结器对有效绑定的 CAS 是签发线性化点，只有成功才将内存令牌所有权移交桌面。绑定撤销若赢得竞争，令牌绝不返回，API 通过服务商精确 `204` 撤销补偿。崩溃、超时或非 `204` 补偿使标记保持未解决；端点返回 `credential_revocation_pending`，直到 POST 前凭据不存在或精确 `204` 服务商撤销得到持久确认，才可返回 `binding_inactive` 作为通过证明。未解决的已撤销标记不得因时间流逝而清除：客户端超时和令牌寿命计算不能证明 GitHub 何时完成已接受的签发请求。标记不含令牌，安装令牌从不持久化。撤销前越过线性化点并正常签发或消费的令牌不属于撤销后新签发，证明不声称所有旧凭据都已失效。
19. **恢复已签发但响应丢失的凭据。** 精确保留服务商 `expires_at`，与较短的本地有效期区分。只有不签发令牌、使用 App JWT 认证的 `api.github.com` 安装读取返回一个严格 `Date`，且至少晚于原始到期时间两秒时，才可替换凭据。这是显式服务商信任假设，不是 RFC 保证：GitHub 响应时钟至多领先令牌到期执行时钟一秒，且已过期令牌不会重新有效。缺失、畸形、过早、重定向或不匹配观察无限期拒绝继续；本地和数据库时钟不能授权此恢复。

GitHub App 认证遵循官方安装令牌模型：可限定仓库及权限，一小时后到期。Draft PR 通过 REST PR 端点创建，显式提供 head、base、title、body 和 `draft: true`。

<a id="testing-decisions"></a>

## 测试决策

1. 每个端到端批次采用先失败后通过的验证方式，从公开行为失败开始，以针对性测试和相关集成边界验证结束。
2. 共享领域测试覆盖请求规范化、摘要稳定、批准失效、状态单调、安全仓库/引用解析和错误脱敏。
3. 本地存储测试覆盖迁移、不可变历史、单个活动 Run/PR 目标、系列/尝试身份、CAS 修订替换、重启恢复、终态不回退及凭据值不存在。
4. Git 测试使用一次性本地裸远端及受管工作树，验证精确提交发布、非快进冲突、禁止强推/标签和不确定结果对账。
5. GitHub 客户端注入 `fetch`，无网络验证权限收窄、严格解析、Draft 创建/查重、401/403/404/409/422/429/5xx、超时、畸形 JSON、脱敏错误、规范 `Retry-After` 恢复和精确 `204` 安装令牌撤销。
6. API 仓库契约同时覆盖种子和 Postgres：项目绑定、角色/范围、撤销、审计、桌面 Bearer 签发、签发前非敏感隔离标记、一致的“凭据不存在或撤销确认”清除、精确跨尝试复用已核验发布。
7. IPC 拒绝意外字段，证明渲染器不能选择路径、仓库、令牌值、Git 标志或任意 REST 载荷。
8. 桌面组件验证精确预览，`approval_required` 与发布前 `approved` 均可显式 Revise，修订材料发布前必须获得新的独立批准。
9. E2E/Electron 使用模拟 GitHub 与本地远端，覆盖推送和创建 PR 之间重启、终态 Draft 失败后复用发布证据，以及仅一次凭据支持的分支推送。
10. 默认 `verify` 不产生费用或外部写入。真实 GitHub 演练须单独授权、限沙箱、绑定候选、单一目的，并在不合并的情况下清理。
11. 扫描持久状态、渲染器数据、日志、产物和远端投影，确认没有私钥、安装令牌、本地绝对路径、Git 原始输出或授权请求头。
12. 1.x 完成测试记录独立非维护者执行到业务验收，并通过文档化打包桌面动作证明撤销阻止新交付凭据。环境准备后，操作员不得编写/修改候选或证据，不使用命令行、直接 HTTP、SQL、GitHub CLI、秘密读取或未记录的维护者状态修复完成流程。
13. 竞争测试延迟签发以跨越绑定撤销，要求有效绑定 CAS 为签发线性化点。证明撤销胜出时令牌不返回，精确 `204` 补偿清除标记，不确定补偿只返回 `credential_revocation_pending` 且无时间绕过，标记和持久投影不含令牌。只有持久的 POST 前凭据不存在确认或精确 `204` 撤销确认，才允许后续精确 `binding_inactive` 证明。

<a id="out-of-scope"></a>

## 不在范围内

- 合并/自动合并 PR、删除分支、强制推送、重写历史或发布标签。
- 管理 GitHub Actions、部署、创建 Release、自动操作 Issue、指定审查者、评论、标签或修改项目看板。
- V1.5 首批不支持基于 fork 或跨仓库的 PR。
- 多个源提交、堆叠 PR、分支更新机器人或自动 rebase。
- 复用或扩大身份 OAuth 令牌用于交付。
- 持久化安装令牌或把令牌返回给 Web/渲染器。
- 托管多租户凭据保管、计费、企业 SSO 或公共 SaaS 管理。
- V2 Agent 运行时、MCP 执行、记忆、RAG、多 Agent 编排或执行器路由。

<a id="further-notes"></a>

## 补充说明

- GitHub 安装令牌是传输凭据，不是交付批准。
- GitHub 比较 URL 或 PR 交付包不能证明远端分支存在。
- 工作树不是安全沙箱，现有命令、权限、预算、脱敏及人工 Gate 控制仍是必须条件。
- V1.5 完成计划中的 1.x 功能线。完整 1.x 门禁通过并记录到路线图前，2.x 实施保持阻断。
- 官方参考：[生成安装访问令牌](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)。
- 官方参考：[创建 PR](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request)。
