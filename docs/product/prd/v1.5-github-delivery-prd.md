# DevFlow Studio V1.5: GitHub Delivery PRD

Lifecycle: Implemented; release/signoff pending

Roadmap position: Final planned 1.x feature milestone

Milestone owner: DevFlow Studio maintainers

## Problem Statement

V1.4 can turn an authenticated Work Request into one canonical local Run, execute implementation in
a managed worktree, archive Test Evidence, and create a redacted PR Delivery Package. It cannot
publish that work to GitHub. The current PR node produces human-readable handoff text only; it does
not prove which local commit should be delivered, authorize a remote write, publish a branch, or
create a real pull request.

That gap prevents the 1.x product line from completing its governed delivery story. An operator must
leave DevFlow, manually reconstruct the intended commit and branch, find suitable credentials, push
the branch, and create a pull request. Those manual steps can select the wrong repository or stale
worktree, bypass the recorded evidence, leak a broad credential, create duplicate pull requests, or
leave the local Run unable to explain what happened after a failure.

## Solution

V1.5 adds a bounded GitHub Delivery capability around the existing local-first authority model.
Desktop main derives an immutable Delivery Intent from the canonical managed worktree, its expected
commit, the Team Project repository binding, the current Run version, and the PR Delivery Package.
It submits a redacted, exact Delivery Request for explicit lead/owner approval through an
authenticated Web session before any remote write.

After approval, the API issues a short-lived, one-repository GitHub App installation access token
with only Contents write authority. Desktop main holds the token only in memory and publishes the
expected commit to the approved branch without force-push. The API independently verifies the
remote branch head, then creates exactly one Draft pull request. Durable delivery state records
every transition and supports safe retry, restart recovery, credential revocation, and audit-safe
operator guidance. GitHub never becomes the authority for the canonical local Run, and V1.5 never
merges a pull request.

The PR Delivery Package remains a handoff Artifact. It supplies the Draft pull-request title, body,
evidence references, and review context; the managed worktree and expected commit are the only code
publication source.

## User Stories

1. As a developer, I can prepare a Delivery Intent only from the current canonical Run's completed
   Coding Agent run and active managed worktree so a stale or unrelated workspace cannot be
   published.
2. As a developer, I can see the exact Team Project, `owner/repository`, base branch, publication
   branch, expected commit, Run version, evidence version, and PR title before I approve a remote
   write.
3. As a developer, I can create an expected local commit from the managed worktree through a trusted
   Desktop main-process operation, with changed paths and Test Evidence bound into the intent.
4. As a lead or owner, I must give explicit human approval through a signed Web session to the exact
   Delivery Request before branch publication or Draft pull-request creation can begin.
5. As a developer, changing the worktree, expected commit, repository binding, branch, Run version,
   or PR Delivery Package before publication creates a new immutable local intent revision. A
   material revision of the same attempt increments the API `intentRevision`, invalidates every
   older approval, and requires a new review.
6. As a team owner, I can bind one Team Project to one GitHub App installation and one repository
   without changing the identity-only GitHub OAuth session.
7. As a team owner, I can see whether delivery credentials are configured, unavailable, expired, or
   revoked without seeing a private key or installation access token.
8. As an operator, I can revoke the Project's GitHub Delivery binding so no new installation access
   token can cross the issuance linearization point and be returned for that Project. If a provider
   mint overlaps revocation, DevFlow either confirms provider credential absence or revocation, or
   reports a non-bypassable pending state instead of claiming revocation proof.
9. As Desktop, I can request a token only with the paired Project's Bearer authority and an approved,
   exact Delivery Intent.
10. As Desktop, I receive a GitHub App installation access token restricted to one repository and
    only `Contents: write` for no more than one hour.
11. As a security reviewer, I can verify that the GitHub App private key remains in the API process,
    the installation access token remains in Desktop main memory, and neither reaches the renderer,
    SQLite, logs, Artifacts, remote summaries, or test fixtures.
12. As a developer, publication fails closed when the repository remote, installation, base branch,
    managed worktree, expected commit, approval, credential scope, or evidence binding is missing or
    stale.
13. As a developer, DevFlow rejects branch names outside its bounded delivery namespace and never
    force-pushes, deletes, rewrites, or silently replaces an existing remote branch.
14. As a developer, a retry after an ambiguous push checks the remote branch first and treats the
    exact expected commit as success rather than pushing a second logical delivery.
15. As the API, after Desktop reports publication I independently verify the remote head equals the
    approved expected commit before any Draft pull request can be created.
16. As a developer, a retry after an ambiguous Draft pull-request response searches by exact
    repository, head branch, base branch, and expected commit before attempting creation again.
17. As a developer, repeated clicks, renderer retries, process restart, and duplicate IPC delivery
    within one delivery attempt remain idempotent and cannot create a second branch publication or
    Draft pull request.
18. As a developer, I can recover a delivery in `approval_required`, `publishing_branch`,
    `creating_pr`, or `recovery_required` state with an explicit next action.
19. As a developer, successful delivery records the remote branch, expected commit, pull-request
    number, Draft URL, creation time, and redacted audit events before the Run can proceed to
    Acceptance.
20. As a reviewer, I can open the real Draft pull request from the PR node and compare its recorded
    head commit to the local Delivery Intent.
21. As an Acceptance reviewer, I can verify that the same canonical Run contains passing Test
    Evidence, an approved Delivery Intent, an exact remote commit, and a Draft pull request.
22. As a reviewer, I can reject Acceptance without merging, closing, or mutating the GitHub pull
    request.
23. As an operator, I can distinguish authentication, authorization, installation, repository,
    non-fast-forward, GitHub validation, rate-limit, timeout, and local persistence failures through
    redacted typed outcomes.
24. As an operator, I can explicitly retry a failed or rejected delivery as a new attempt with a new
    request and idempotency key. A completed delivery cannot be retried, and no terminal request is
    ever reopened or overwritten.
25. As a project owner, I can complete the documented Work Request -> local Run -> implementation ->
    Test Evidence -> explicit approval -> GitHub Draft pull request -> Acceptance path without ad hoc
    maintainer intervention.
26. As a release reviewer, I can verify the 1.x completion gate with deterministic fake-GitHub tests,
    local git remotes, API/Postgres integration, Electron smoke, and an explicitly authorized
    GitHub sandbox walkthrough; default CI never writes to a real repository.

## Implementation Decisions

1. **Authority remains local-first for source execution.** Desktop SQLite owns the full Delivery
   Intent, local attempt, and outcome. Postgres owns the redacted Delivery Request, signed Web
   decision, Team Project installation binding, credential-grant metadata, and collaboration audit.
   GitHub owns the published branch and pull request, not Workflow state.
2. **GitHub App authentication is separate from identity OAuth.** The existing OAuth App retains
   `read:user user:email` and discards its access token after identity bootstrap. It is not widened
   for repository writes.
3. **The API owns the GitHub App private key.** It is supplied through self-hosted operator
   configuration and is never stored in Postgres or returned by an API.
4. **Desktop uses an ephemeral Contents token.** The API mints a token for one repository with only
   `contents: write`. The token expires within one hour and is held only by Electron main for the
   active attempt. API-side pull-request creation uses separate App authority that never leaves the
   API process.
5. **Project installation binding is non-secret metadata.** The organization, Project, repository,
   installation id, configuration state, creator, update time, and revocation time are durable and
   auditable. Private-key and token values are not.
6. **The current managed worktree is the publication source.** A Delivery Intent must resolve the
   completed Coding Agent run's `managedWorkspaceId`, active workspace, branch, base branch, changed
   paths, and passing Test Evidence.
7. **A local expected commit is mandatory.** Desktop main creates or validates one commit in the
   managed worktree and records its full SHA. Dirty state after that commit invalidates publication.
8. **The PR Delivery Package is metadata only.** Its current title/body/evidence version is hashed
   into the intent. It cannot select a repository, branch, worktree, or credential.
9. **Approval is immutable, remote, and exact.** A live lead/owner signs the redacted Delivery
   Request through a session Cookie. Approval binds an intent digest plus Project, repository, base,
   head, expected commit, Run/node/version, evidence version, approver, and timestamp. It cannot
   authorize a modified intent, and Desktop bearer authority cannot approve its own request.
10. **Publication has a durable state machine.** The durable states are `approval_required`,
    `approved`, `publishing_branch`, `branch_published`, `creating_pr`, `completed`, `failed`,
    `recovery_required`, and `revoked`. `completed`, `failed`, and `revoked` are terminal and never
    regress. Local `failed`/`revoked` may only mirror an exact remote terminal request or binding
    convergence; a provider, transport, expiry, or unknown result without that proof becomes
    `recovery_required`. `recovery_required` resumes the same attempt only through an explicit
    Resume action. A Stop before first submission may Resume by submitting that same immutable
    attempt for approval; a Stop after submission reconciles its existing request first.
11. **Delivery series, attempt, and revision have separate identities.** A stable
    `deliverySeriesKey` derives from organization, Team Project, local Project, Run, PR node,
    repository-binding id/version, and managed workspace. A material change before publication
    creates a new immutable local intent in the same series and attempt; the API revises the same
    request, increments `intentRevision`, and invalidates the older approval. An explicit retry is
    permitted only after the prior attempt is `failed` or `revoked`; Desktop must first observe the
    one exact remote predecessor in the matching terminal state using the current pairing claimant.
    It then
    increments `deliveryAttempt` and derives a new request/idempotency key. Missing, ambiguous, or
    non-terminal remote authority fails closed; a rotated claimant must create and claim a new Work
    Request/Run instead of taking over the old Run. After the same proof, a repository rebind starts
    a new series at attempt one, while at most one non-terminal attempt may exist for a Run/PR target.
12. **Branch publication is non-destructive.** The first implementation pushes one exact commit ref
    to one namespaced head branch. It does not push tags, all refs, merge commits, or use force.
13. **The API verifies publication independently.** Desktop reports a safe publication result; the
    API reads the GitHub branch and advances only when its head equals the approved expected commit.
14. **Ambiguous remote results are reconciled before retry.** An exact remote commit or matching
    Draft pull request is accepted; conflicting remote state becomes `recovery_required`.
15. **The renderer is unprivileged.** It can request preview, explicitly revise a pre-publication
    intent, explicitly retry an eligible terminal attempt, resume recovery, and display remote
    decisions through validated IPC. It cannot choose an attempt number, filesystem path, remote
    URL, credential, raw git arguments, or arbitrary GitHub request body.
16. **GitHub API responses are parsed through strict allowlists.** Only identifiers, state, Draft
    flag, safe URLs, head/base refs, and commit SHAs become durable evidence. Raw headers and bodies
    are not persisted.
17. **Acceptance requires GitHub Delivery evidence.** A Run cannot complete Acceptance from a PR
    handoff Artifact alone once V1.5 delivery is enabled for its Project.
18. **Credential issuance is linearized before return.** Reserving a grant creates a durable
    non-secret quarantine marker before the provider mint begins. The grant finalizer's
    active-binding CAS is the issuance linearization point: only its success transfers ownership of
    the in-memory token to Desktop. If binding revocation wins that race, the minted token is never
    returned and the API compensates through provider revocation with an exact `204`. A crash,
    timeout, or non-`204` compensation leaves the marker unresolved; the credential endpoint returns
    `credential_revocation_pending` and can never return `binding_inactive` as passing proof until
    pre-POST credential absence or exact-`204` provider revocation is durably confirmed. An
    unresolved revoked marker must not be cleared by
    elapsed time: client timeouts and token-lifetime arithmetic do not prove when GitHub completed an
    already accepted mint request. The marker contains no token, and installation access tokens are
    never persisted. A token that crossed the linearization point before revocation and was normally
    issued or consumed is not a post-revocation new issuance; revocation proof does not claim that
    every older credential has already become invalid.
19. Response-loss recovery for a durably issued credential retains the exact provider `expires_at`
    separately from the shorter local-effective expiry. It may replace that credential only after a
    no-mint, App-JWT-authenticated `api.github.com` installation read returns one strict provider
    `Date` at least two seconds after the raw expiry. This rule adopts an explicit trusted-provider
    assumption—not an RFC guarantee—that GitHub's response `Date` never leads the clock used to
    enforce installation-token expiry by more than one second and that an expired token cannot
    become valid again. Missing, malformed, early, redirected, or mismatched observations remain
    fail-closed indefinitely; local and database clocks never authorize this recovery.

The GitHub App authentication contract follows GitHub's documented installation-token model:
installation tokens can be narrowed to selected repositories and permissions and expire after one
hour. Draft pull requests are created through the REST pull-request endpoint with explicit head,
base, title, body, and `draft: true`.

## Testing Decisions

1. Use vertical RED -> GREEN tracer bullets. Each slice begins with one public-behavior failure and
   ends with focused tests plus the relevant integration seam.
2. Shared domain tests cover Delivery Intent canonicalization, digest stability, approval
   invalidation, state monotonicity, safe repository/ref parsing, and error redaction.
3. LocalStore tests cover schema migration, immutable intent history, one active Run/PR target,
   series/attempt identity, CAS-style revision replacement, restart recovery, no terminal
   regression, and absence of credential values.
4. Git tests use disposable local bare remotes and managed worktrees. They assert exact commit
   publication, non-fast-forward conflict behavior, no force-push, no tag publication, and
   reconciliation after an ambiguous result.
5. GitHub client tests inject `fetch`; they cover installation token narrowing, strict response
   parsing, Draft creation, duplicate lookup, 401/403/404/409/422/429/5xx, timeout, malformed JSON,
   sanitized errors, and exact `204` installation-token revocation without network access.
6. API repository-contract tests run against seed and Postgres implementations for Project binding,
   role/scope checks, revocation, audit, Desktop bearer token issuance, the pre-mint non-secret
   quarantine marker, and identical credential-absence-or-revocation confirmation clearance.
7. IPC tests reject unexpected fields and prove the renderer cannot select paths, repositories,
   token values, git flags, or arbitrary REST payloads.
8. Desktop component tests prove the operator sees an exact preview, can explicitly Revise in both
   `approval_required` and pre-publication `approved`, and must obtain a fresh distinct approval
   before publication of revised material.
9. E2E and Electron smoke use fake GitHub and local git remotes. They cover restart between push and
   PR creation and verify exactly one logical delivery.
10. Default `verify` remains no-cost and performs no external writes. Any real GitHub walkthrough is
    separately authorized, sandbox-repository scoped, candidate bound, single purpose, and cleaned
    up without merge.
11. Security assertions scan durable state, renderer data, logs, Artifacts, and remote projections
    for private keys, installation tokens, local absolute paths, raw git output, and authorization
    headers.
12. The 1.x completion test records one independent non-maintainer operator path through Acceptance
    and proves revocation blocks a new delivery credential through a documented packaged Desktop
    action. After pre-run setup, that operator does not author or modify the candidate/evidence and
    does not use shell, direct HTTP, SQL, GitHub CLI, secret access, or undocumented maintainer state
    repair to complete the path.
13. Race tests defer provider mint across binding revocation and require the active-binding CAS to
    be the issuance linearization point. They prove the token is never returned when revocation wins,
    exact `204` compensation clears the marker, uncertain compensation returns only
    `credential_revocation_pending` without a time-based escape hatch, and neither the marker nor any
    durable projection contains a token. Tests prove only a durable pre-POST credential-absence
    confirmation or exact-`204` provider-revocation confirmation permits the later exact
    `binding_inactive` proof.

## Out of Scope

- Pull-request merge, auto-merge, branch deletion, force-push, history rewrite, or tag publication.
- GitHub Actions administration, deployment, release creation, issue automation, reviewer
  assignment, comments, labels, or project-board mutation.
- Fork-based or cross-repository pull requests in the first V1.5 slice.
- Multiple source commits, stacked pull requests, branch update bots, or automatic rebase.
- Reusing or expanding the identity OAuth token for GitHub Delivery.
- Persisting installation access tokens or returning them to Web/renderer code.
- Hosted multi-tenant credential custody, billing, enterprise SSO, or public SaaS administration.
- V2 Agent Runtime, MCP execution, Memory, RAG, Multi-Agent orchestration, or executor routing.

## Further Notes

- GitHub installation tokens are a transport credential, not Delivery Approval.
- A GitHub compare URL or PR Delivery Package is not proof that a branch exists remotely.
- A worktree is not a security sandbox. Existing command, permission, budget, redaction, and human
  Gate controls remain mandatory.
- V1.5 closes the planned 1.x feature line. 2.x implementation remains blocked until the complete
  1.x gate passes and the Roadmap records that result.
