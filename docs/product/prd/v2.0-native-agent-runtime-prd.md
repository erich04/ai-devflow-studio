# V2.0 Native Agent Runtime Foundation PRD

Status: Approved for implementation; completed by candidate-bound V2.0 evidence

Date: 2026-08-12

Roadmap position: First 2.x milestone after the released V1.5/1.x completion gate

## Summary

V2.0 adds a bounded first-party Agent loop to DevFlow Studio. It can observe governed Context, choose
from explicitly granted native Tool, local MCP, and Coding Executor capabilities, evaluate results,
checkpoint, resume, and stop with a deterministic reason. It remains inside the existing Workflow,
policy, budget, Evidence, and human Gate authority model.

V2.0 also evolves the existing OpenCode adapter into one governed Coding Executor contract and adds
one deliberately narrow DevFlow-owned Coding Agent behind that same contract. It does not replace
OpenCode or claim feature parity.

## Problem

The released 1.x product has two useful but different model paths:

- Knowledge Review is a bounded single-call operation with a durable result and trace.
- OpenCode is an external coding engine behind a managed adapter and permission relay.

Neither is a DevFlow-owned iterative runtime. DevFlow cannot yet choose an approved Tool based on an
observation, persist a portable checkpoint, resume an exact trajectory, execute a trusted local MCP
Tool, compare native and delegated coding through one result contract, or evaluate those behaviors
against a versioned scenario dataset.

## Users And Jobs

### Developer

- Start an Agent only from an eligible Workflow Node and understand its scope and limits.
- See what capability is being requested, approve or reject sensitive actions, cancel safely, and
  resume an exact checkpoint after interruption.
- Compare native and OpenCode execution through consistent events, diff/test Evidence, and stop
  reasons without exposing local source or credentials to Team state.

### Lead Or Reviewer

- Inspect the redacted trajectory, policy/budget decisions, Tool and permission timeline, evaluation,
  and Evidence before approving the next Gate.
- Distinguish a successful Agent task from accepted Workflow Evidence and from delivery authority.

### Local Operator

- Install and enable a trusted local MCP server without allowing Team metadata or a model prompt to
  choose an executable, arguments, cwd, or secret environment.
- Diagnose lifecycle, schema, timeout, cancellation, and audit failures without raw secret leakage.

## Product Principles

1. Workflow and human Gate authority remain outside the Agent loop.
2. A capability must exist before the model can select it; text is never authority.
3. Every continuation is bounded, versioned, cancellable, checkpointed, and observable.
4. Trajectory means observable events and evidence, not hidden reasoning.
5. Local source, raw outputs, credentials, and complete runtime state remain in Desktop.
6. Native and delegated coding use one governed contract.
7. Default verification is deterministic and no-cost.

## Functional Requirements

### FR1 — Runtime Start And Scope

- Start is accepted only for an eligible current Run/Node with exact versions, Local Project binding,
  authoritative policy/budget context, and an explicit capability set.
- The start request records maximum steps, deadline, Tool-call count, result-size limits, and
  cost/token budget. System/policy maxima cannot be raised by renderer input.
- Only one active continuation may own a checkpoint version.

### FR2 — Bounded Agent Loop

- The runtime performs observe → decide → act → validate → evaluate → checkpoint.
- One iteration creates at most one external action.
- The stable terminal reasons are `success`, `failure`, `cancelled`, `timeout`, `step_limit`,
  `budget_exhausted`, and `policy_denied`.
- Reaching any bound stops before another provider, Tool, MCP, or executor action.
- Agent success never advances a Workflow Node directly.

### FR3 — Trajectory And Checkpoint

- Persist ordered allowlisted events with monotonic sequence and checkpoint versions.
- Persist fixed bounded decision summaries and digests, not hidden reasoning or provider scratchpads.
- Atomically commit accepted result references, counters, trajectory event, and checkpoint.
- Resume revalidates Workflow/Node version, policy, capability-set digest, Local Project, deadline,
  remaining budget, and executor/install availability.
- Stale, terminal, expired, mismatched, or concurrently consumed checkpoints fail closed.

### FR4 — Native Tools

- Electron main owns a versioned native Tool registry.
- The initial accepted Tools are narrowly scoped repository reads, bounded workspace file edits,
  saved-test execution, and deterministic evaluation helpers required by the scenario dataset.
- Every Tool has strict schemas, permission/side-effect class, deadline, cancellation, size cap,
  idempotency posture, and audit/redaction rules.
- An opaque ToolCapabilityGrant is required immediately before execution.

### FR5 — Trusted Local MCP

- A developer can explicitly create a trusted local MCP installation with verified executable,
  fixed args, local `stdio` transport, environment-name allowlist, deadlines, identity, and version.
- Team `McpServerDefinition` remains display/catalog metadata and cannot create or execute a process.
- Discovery validates protocol/server identity and Tool schemas but does not grant calls.
- A runtime may call an MCP Tool only through an exact ToolCapabilityGrant.
- Timeout, cancel, crash, malformed schema/message, duplicate Tool identity, unexpected output, and
  shutdown have typed fail-closed outcomes.

### FR6 — Coding Executor Contract

- Executors advertise stable identity/version, availability, and capabilities before selection.
- OpenCode is wrapped behind the new contract without replacing its proven HTTP transport.
- The native Coding Agent uses only accepted native Tools in a managed worktree, runs the saved test
  command, performs a bounded repair loop, and stops deterministically.
- Both executors emit comparable event families and the same terminal result contract: stop reason,
  checkpoint, changed relative paths, redacted diff reference, Test Evidence references, usage/cost,
  and cleanup.
- Neither executor can publish, merge, approve a Gate, select a broader workspace, or issue its own
  capabilities.

### FR7 — Permission, Cancellation, And Recovery

- Permission requests identify Tool/executor, bounded operation summary, permission class, scope,
  and expiry. No response before expiry is a denial.
- Approve-once covers one exact request; it cannot authorize a later different call.
- Cancellation is idempotent, persists before propagation, and fences late commits.
- Checkpoint and resume prove an interrupted deterministic scenario continues without repeating the
  last accepted non-idempotent action.

### FR8 — Evidence, UX, And Team Projection

- Desktop shows lifecycle, current step, active capability, permission state, consumed/remaining
  bounds, checkpoint, evaluation, terminal reason, executor identity, Evidence, and cleanup.
- Local SQLite stores the complete allowlisted trajectory and references to private local results.
- API/Postgres stores only a strict redacted Agent Runtime summary and audit metadata.
- Team-visible data contains no raw prompt, source, patch, stdout, stderr, credential, environment,
  executable path, cwd, or absolute local path.

## Evaluation Contract

V2.0 ships with a versioned scenario dataset. Each scenario fixes the starting repository/Context,
allowed capabilities, deterministic provider decisions where applicable, expected Tool/Executor
events, bounds, terminal result, Evidence, and cleanup outcome.

The baseline measures quality, cost, latency, human intervention, recovery, and isolation. At
minimum it covers:

1. a no-side-effect native Tool task that succeeds;
2. a native coding repair with one approved edit and passing saved test;
3. the equivalent governed coding task through OpenCode contract fixtures;
4. a trusted fixture MCP discovery and Tool call;
5. checkpoint and resume after an injected interruption;
6. cancellation during Tool and executor work;
7. exact step, time, Tool-call, and budget exhaustion;
8. malformed Tool/MCP schema and oversized result rejection;
9. stale Workflow, checkpoint, capability, policy, and Local Project rejection; and
10. cross-organization, project, user, session, and Local Project negative paths.

Default verification is deterministic and no-cost. Any real OpenCode/provider signoff is explicit,
single-scenario, budget-bounded, secret-safe, and recorded separately from default CI.

## V2.0 Completion Gate

V2.0 is complete only when:

- the versioned scenario dataset passes on a clean candidate across shared, Desktop, Team/Postgres,
  packaged Desktop, and cross-platform gates;
- one DevFlow-owned Agent completes accepted native Tool and local MCP scenarios, resumes from an
  exact checkpoint, and stops deterministically;
- the same Runtime completes governed coding through OpenCode and the native executor with contract
  parity for events, cancellation, Evidence, terminal result, and cleanup;
- all bound, stale-version, permission, ambiguous-result, restart, and tenant/scope negative paths
  fail closed;
- trajectory and Team projections pass secret/path/source/output redaction scans; and
- benchmark evidence records quality, cost, latency, intervention, recovery, and isolation results.

Completion evidence: candidate `dfc74831552a0e8910529420c6383b6474e8a12c` passed all 15 frozen
no-cost scenarios, native/OpenCode executor parity, zero-leak scans, exact-SHA Verify attempt 1 on
all five required jobs, and exclusive Desktop artifact verification. The immutable structured
records are `docs/releases/v2.0.0/agent-runtime-evaluation.json` and
`docs/releases/v2.0.0/required-gates.json`.

## Non-Goals

- Public SaaS, hosted shared-infrastructure multi-tenancy, billing, enterprise SSO, or managed
  provider credentials.
- V2.1 hybrid/vector retrieval, reranking, or Agent Memory.
- V2.2 supervisor/specialist Multi-Agent coordination or task graphs.
- Remote MCP transports, arbitrary Team-authored process commands, unrestricted shell, or a general
  plugin marketplace.
- OpenCode feature parity for the native Coding Agent.
- Autonomous Gate approval, branch publication, pull-request creation, merge, deployment, or policy
  changes.
- Persisting or displaying hidden reasoning or provider-private internal traces.
