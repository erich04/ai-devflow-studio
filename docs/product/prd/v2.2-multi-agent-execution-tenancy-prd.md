# V2.2 Multi-Agent And Execution Tenancy PRD

Status: Approved for implementation

Date: 2026-08-13

Roadmap position: Active final planned 2.x milestone after completed V2.1

## Summary

V2.2 lets DevFlow coordinate one bounded Supervisor Agent and a small fixed set of Specialist Agents
inside the existing Agent Runtime, Tool, Coding Executor, Context, Memory, Workflow, and Gate
boundaries. It adds dependency-aware decomposition, evidence-based handoff and join, shared resource
bounds, cancellation/recovery, and exact execution tenancy. Completion requires measurable gains over
the frozen V2.0 single-Agent baseline, not merely multiple model calls.

## Problem

Some governed engineering tasks benefit from independent contract, test, diagnosis, or implementation
work that can later be joined. The current runtime executes one Agent at a time. Simply telling one
Agent to “use sub-agents,” or counting external executor internals, does not provide DevFlow-owned
scope, cost, termination, evidence, failure attribution, or tenant isolation.

Unbounded delegation also creates concrete risk: Specialists may amplify authority, race a shared
workspace, leak Context between users/projects, repeat ambiguous effects after restart, or consume a
budget without a deterministic stop. V2.2 must improve selected outcomes while making those failure
modes explicit and testable.

## Users And Jobs

### Developer

- Start one bounded coordination plan for an eligible running task and see its exact graph and bounds.
- Understand which Specialist owns each task, what Context and capabilities it received, and which
  result or failure it handed back.
- Cancel the whole session once and know cancellation reaches every child and mutable resource.

### Lead Or Reviewer

- Compare Multi-Agent quality, cost, latency, intervention, and recovery with the V2.0 single-Agent
  baseline on the same frozen scenarios.
- Inspect redacted task, handoff, failure-attribution, and bound-consumption metadata without reading
  local source or hidden reasoning.
- Verify that no Agent changed Workflow, Gate, publication, credential, or tenant authority.

### Local Operator

- Diagnose a blocked dependency, failed Specialist, stale lease, or ambiguous effect without editing
  SQLite or replaying a side effect.
- Restart Desktop and recover the exact coordination version with zero repeated accepted handoffs,
  Tool calls, mutable writes, or child Runtimes.

## Product Principles

1. Coordination attenuates existing authority; it never creates authority.
2. One Supervisor and a fixed small Specialist set is a product feature; an open swarm is not.
3. The task graph, budgets, capabilities, and tenancy identity are data contracts, not prompt advice.
4. Parallel reads may be useful; mutable resources remain single-writer.
5. Handoffs carry Evidence and digests, not hidden reasoning or raw repository content.
6. The V2.0 single-Agent path remains executable and is the comparison baseline.
7. Default evaluation remains deterministic and no-cost.

## Functional Requirements

### FR1 — Bounded Coordination Session

- Bind one Coordination Session to exact organization/project/user/session, Local Project, Run/Node
  versions, Supervisor runtime, Context/capability digests, deadline, and shared bounds.
- Permit one Supervisor Agent and at most four Specialist Agents, with no recursive delegation.
- Enforce hard graph, edge, concurrency, retry, handoff, Tool-call, token, cost, result-size, and time
  bounds; lower authoritative policy limits win.
- Reject unknown fields, noncanonical IDs/timestamps, stale versions, wider scopes, and invalid bounds.

### FR2 — Dependency-Aware Agent Task Graph

- Validate one versioned directed acyclic graph before specialist side effects.
- Require unique task/edge IDs, existing dependency targets, bounded fan-out, accepted roles, explicit
  capability/Context/resource needs, and deterministic tie-breaking among ready tasks.
- Progress each task monotonically; dependencies must succeed before a dependent node becomes ready.
- Reject cycles, model-created graph mutation, completed-node rewrite, duplicate ownership, and hidden
  or disconnected execution.

### FR3 — Supervisor And Specialist Authority

- Only Electron main may issue opaque Specialist authority after current Workflow/policy/pairing and
  Supervisor ownership pass.
- A Specialist receives the intersection of Supervisor authority and exact task needs. Capabilities,
  Context, resources, deadline, and budget can only narrow.
- No specialist can create another Agent, widen its own role, transfer a Tool grant, or use another
  task's runtime/checkpoint/resource handle.
- Supervisor and Specialists cannot advance Workflow State, accept Evidence, approve a Gate,
  publish, merge, mint credentials, or bypass the existing delivery contract.

### FR4 — Handoff, Join, And Failure Attribution

- Bind each handoff to exact source/target task and runtime versions, tenancy, result/Evidence/Context
  digests, sequence, and bounded allowlisted summary.
- Accept one handoff identity idempotently; reject conflicting replay, stale dependency, wrong target,
  foreign scope, unaccepted result, and oversized metadata.
- Join only accepted dependency results. Preserve the exact source of failure, cancellation, timeout,
  budget exhaustion, policy denial, Tool/Executor error, or invalid result.
- Recovery is explicit and bounded. It cannot silently replace a Specialist or repeat a non-idempotent
  effect.

### FR5 — Shared Budgets And Resource Arbitration

- Deduct every Specialist allocation and observed use from one authoritative Coordination Session
  budget; total child use cannot exceed the parent.
- Bind mutable resources to one main-owned single-writer lease with exact task, capability, resource
  digest, version, deadline, and tenancy.
- Permit concurrent read-only work only when each capability and resource scope independently allows
  it. V2.2 never permits concurrent edits to the same managed workspace.
- Expired, cancelled, stale, mismatched, or released leases cannot commit a result.

### FR6 — Cancellation, Checkpoint, And Restart

- Parent cancellation propagates to every ready/running child, Tool/MCP/Executor, handoff, and writer
  lease and remains monotonic across late events.
- Atomically persist graph/task state, shared counters, accepted handoffs, leases, Specialist runtime
  references, and safe trajectory metadata.
- Resume by exact optimistic concurrency after revalidating authority, Context, capabilities, tenancy,
  deadline, policy, and resource state.
- Cold restart repeats zero accepted Specialist starts, handoffs, Tool effects, mutable writes, or
  terminal events. Ambiguous effects remain blocked for their existing reconciliation contract.

### FR7 — Execution Tenancy And Placement

- Bind every coordination object to the exact organization/project/user/session/Local Project,
  Run/Node, coordination, task, and Agent identity.
- Reject cross-scope inputs before data lookup or provider/Tool side effects without revealing item
  existence, counts, or timing distinctions.
- Desktop schema 28 is the first durable Coordination Session slice. Team schema 19 later stores only
  strict redacted lifecycle, task-count, failure, quality, cost, latency, and intervention metadata.
- API/Postgres/Web cannot create, resume, cancel, reassign, or mutate local coordination, graph,
  capabilities, handoffs, or resources.

### FR8 — UX And Evaluation

- Desktop shows graph state, Supervisor/Specialist roles, dependency readiness, bounds, resource
  ownership, handoffs, failure attribution, cancellation, and recovery without hidden reasoning.
- Web remains read-only and receives no source, prompt, patch, stdout/stderr, credential, local path,
  scope session, opaque capability, Context body, or Memory statement.
- Run the identical frozen scenario inputs through the V2.0 single-Agent baseline and V2.2 candidate.
- V2.2 exits only when Multi-Agent measurably improves selected task outcomes over the frozen V2.0 single-Agent baseline
  across quality, cost, latency, and human intervention while recording zero authority, isolation, termination, or replay violations.

## Evaluation Contract

The versioned fixture is `scripts/fixtures/v2.2-multi-agent-evaluation.json`. It fixes the graph and
tenancy bounds, roles, scenarios, baseline observations, candidate expectations, and metric floors.
The default runner removes provider credentials and uses deterministic Supervisor/Specialist
decisions, Tools, clocks, and failure injection.

The completion gate requires:

- at least `0.25` aggregate selected-task improvement over the exact single-Agent baseline;
- no additional human intervention and bounded frozen cost/latency multipliers;
- correct dependency join, cycle rejection, failure attribution, shared-budget exhaustion, and
  cancellation propagation;
- zero authority, isolation, termination, replay, redaction, source, path, raw-output, or paid-call
  violations;
- the full single-Agent baseline remains executable and unchanged; and
- local, retained migration, real Postgres, Docker, packaged Desktop, Windows, macOS, restart, and
  clean direct-child completion evidence gates pass.

## Non-Goals

- Open-ended swarms, recursive delegation, dynamic marketplace membership, or arbitrary role creation.
- Public SaaS, hosted shared execution, managed Kubernetes workers, remote desktops, or enterprise
  tenant provisioning.
- Treating external OpenCode internals as DevFlow-owned coordination.
- Concurrent edits to one workspace, implicit merge conflict resolution, or Agent-owned Git history.
- New Workflow, Gate, Evidence acceptance, GitHub delivery, credential, or policy authority.
- New remote MCP transports or arbitrary Team-supplied executables.
- A general chat room, social Agent network, or hidden long-lived background workforce.
- There is no automatic V2.3; completing V2.2 closes the finite accepted 2.x sequence.
