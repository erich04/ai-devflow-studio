## 缓存证据与限制

使用生产 NativeCodingLoop，固定合成索引与工具定义；旧布局控制仅把运行时状态放回历史 system prompt，**不代表运行旧产品版本**。顺序是旧 A → 修复 A → 修复 B → 旧 B，每组最多四次调用，比较热轮次时排除第一条请求。

| 布局/顺序 | 协议 | 热轮次缓存命中率 | 解释 |
| --- | --- | ---: | --- |
| 旧 A | 失败 | 0%（不纳入有效配对） | 首轮读一次后，模型连续返回“等下一轮”，由 no_progress 停止 |
| 修复 A | 通过 | 89.77% | system/tool 前缀 hash 稳定；四次实际读取 |
| 修复 B | 通过 | 88.30% | system/tool 前缀 hash 稳定；四次实际读取 |
| 旧 B | 通过 | 0% | 四次实际读取；动态 system 前缀变化 |

仅 B 形成有效配对；两次修复布局都观察到了热缓存命中。模型生成轨迹与服务端缓存状态不可完全固定，因此不据此给出生产环境“节省百分比”，也不把无效控制组补跑成通过记录。16 次探针调用全部计费进总账，合计保守估价 0.07195736 元。
