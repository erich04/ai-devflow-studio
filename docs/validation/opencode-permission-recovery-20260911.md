## 实现

1. 执行授权通过后，精确识别的本地只读命令可自动继续：
   `pwd`、策略支持的简单 `git status` 形式，以及 `git branch --show-current`。
   其他受支持的 Shell 命令仍需审批；写文件权限继续使用原审批机制。
2. 命令先经过策略检查。不支持的请求直接收到原因和修正说明，不显示一个批准后仍必然失败的审批。
   同一会话最多提供三次修正机会；工具次数和实际执行时限继续约束运行，决定写入脱敏轨迹。
3. OpenCode 工具审批过期后，保持 `waiting_permission` 并记录暂停信息，保留会话和工作区。
   “重新核验并请求审批”核验原工作流版本、原会话的待审批请求、Git 边界和工作区差异，
   创建新的本地审批 ID，保留过期决定。它不会批准执行，也不会新建 Run 或启动 Provider。
   新审批仍指向同一个 OpenCode 请求，实际批准前再次核验；文件或请求发生变化会停止执行并保留工作区。
   工作流在核验期间变化时，由存储层原子检查阻止写入新的审批。
4. 同一 project / Workflow Run / 开发节点默认三次尝试。
   达到上限后显示累计次数，由用户明确“授权追加一次尝试”。
   授权绑定当时累计次数和可信用户，在持久化预留 Run 时再次核验；
   第四次使用后，重放“已有三次”的授权无法获得第五次机会。
   历史记录、其他审批和预算约束均保留。

## 限制与接入后的验证

- 恢复只适用于仍存活的原 OpenCode 会话。Desktop 重启后的工具会话仍按原恢复规则终止，
  保留工作区；不会偷偷重新调用 Provider。缺少原需求版本的旧 Run 也不能直接恢复审批。
- Execution Authorization、最终 Change Acceptance、依赖安装审批保持原过期规则。
  本次改变的是 OpenCode 工具审批等待：等待时间不计入适配器的实际执行时限。
- 侧边交接时尚未完成真实 Provider 的整条需求、设计、实施、测试、云端交付验收。
  主任务接入本分支并构建后，应在真实 DeepSeek/OpenCode 运行中验证：
  普通读取、一次不支持命令的反馈修正、过期后恢复、同一需求的第 4 次明确授权，
  然后继续正式测试、最终验收和 Draft PR 交付。每一步应保留真实调用与交付证据。
- 对已耗尽三次的旧需求，可以使用明确的追加尝试入口；
  无需重置历史计数来验证这一条路径。是否成功仍以真实运行结果为准。
