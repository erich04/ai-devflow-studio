# 项目记忆完整验证（2026-10-29）

在一个合成 Todo 项目上，用真实 DeepSeek 调用验证 ADR 0030 项目记忆的记录压缩和召回的全部入口，共花费 0.6878 美元（预算 2 美元）。这次验证发现并修复了两个问题：召回在 bank 变大后超时（#270），Native v2 压缩历史后不再附带记忆（#272）。修复后 97 项检查中 95 项通过。没有通过的两项中，一项是召回排序的局限，一项是检查脚本自身的问题，详见下文。

## 方法

- 脚本：`scripts/project-memory-full-validation.mts`，数据在 `scripts/project-memory-full-fixtures.mts`。阶段依次为 seed、consolidate、recall、pages、agents、review、capture、lifecycle、clear。后面的阶段可以对同一个工作目录和 bank 重跑，不必重新抽取。
- 环境：macOS，Hindsight 1.0.0（固定镜像，2 个 CPU），DevFlow 的记忆中继，本地 LocalStore。项目未配对团队项目，记忆归本地主体所有。花费记在单独的账本 `out/project-memory-validation/ledger-full.json` 中，上限 2 美元。
- 模型：Hindsight 的抽取和归纳用 `deepseek-v4-flash`；编码、阶段 Agent、Gate 评审和讨论用 `deepseek-flash`，Thinking 设为 low。
- 数据：模拟 30 天内的 53 份文档，共 113 KB，按时间先后写入：
  - 1 份旧版记忆，10 条。
  - 21 天的真实 Git 提交，共 37 个，另有一个 30 天以外的提交、一个 `--no-ff` 合并和两个当天的提交。
  - 16 段讨论，其中一段 57 KB 的长讨论。
  - 8 次 Coding Run，其中一次有 420 条活动。
  - 7 份文档：已批准的澄清、设计、验收各一类，以及 2 份 Gate 评审结果。
- 被多次改变的决定：撤销窗口 5→10→15 秒；分页 20→50 条；同步重试 3→5 次；答复语言中文→英文；日期显示从固定格式改为 7 天内显示相对时间；批量删除从不支持撤销改为可撤销最近一次。
- 运行过程：第一次运行在等待 Hindsight 时卡住，原因是检查脚本把 Hindsight 排在 6 小时后的知识页刷新算成了未完成的工作。修正脚本后从 consolidate 续跑，之后找到并修复了召回超时（#270）和压缩后不带记忆（#272），再从 recall、agents、review 依次续跑到 clear。抽取只做了一次。另做了三次小实验：Native 答复语言、阶段 Agent 的 JSON 失败率、召回参数。

## 记录压缩

| 层次 | 结果 |
|---|---|
| 采集时裁剪 | 57,554 字节的长讨论写成 47,098 字节，保留最新的 121 条消息，丢掉最早的 19 条（最早的方案没有进入记忆，最终结论进入了）。420 条活动的 Coding Run 写成 48,125 字节，保留最新的活动，并标出“earlier activity omitted”。3,000 条旧版记忆只保留最新的部分，并注明省略的条数。 |
| Hindsight 归纳 | 首批 53 份文档抽出 210 条事实（world 170 条，experience 40 条），归纳成 108 条观察，31 条观察来自多条事实，最多一条来自 16 条。验证结束前共有 417 条事实、152 条观察，平均每条观察 2.4 个来源，最多 27 个。撤销窗口那条观察由 8 条事实归纳而成，随着决定变化改写了 5 次，现在的文本是“已从 5 秒改为 10 秒……又改为 15 秒，原因是……”。6 个被改变过的决定都有观察写的是最新值，没有一条观察只写旧值。闲聊（“谢谢，今天先到这里”）抽出 0 条。 |
| 会话压缩 | 让历史超过人为调小的输入上限。Native v2 第 2–4 轮各压缩一次，结构化讨论在第 3 轮压缩。第 4 轮问第 1 轮说过的发布日期，两种协议都从滚动摘要里答出了 11 月 3 日。 |
| 编码简报 | 36,557 字节的材料压成 4,316 字节，上限 24,000 字节。8 条召回的记忆全部完整保留，大段 CI 日志改成摘要。 |
| 知识页 | 四页都写成（2.3–4.1 K 字符），包含预期内容和 5 个后期决定（撤销窗口 15 秒、重试 5 次、分页 50 条、批量可撤销最近一次、7 天内显示相对时间）。 |

## 召回

召回速度和命中率（25 个问题，每个问题分别按编码、阶段、讨论的预算召回）：

| | 修复前 | #270 之后 |
|---|---|---|
| 延迟 p50 / p95 / 最大 | 8.9 s / 12.3 s / 14.6 s | 42 ms / 93 ms / 566 ms |
| 命中：编码简报 / 阶段 Agent / 讨论栏 | 92% / 84% / 84% | 100% / 100% / 96% |
| MRR | 0.61 | 0.81 |
| 调参之后另写的 20 个问题（含英文问题）：命中，按同样三个预算 | 65% / 65% / 55% | 100% / 85% / 85% |

修复前，Hindsight 的英文交叉编码器要在 CPU 上重排约 300 个候选（trace 显示检索用 0.1 秒，重排用 21.5 秒），桌面端召回 5 秒就超时。当时验证脚本把召回超时放宽到了 20 秒，召回仍多次降级为空，例如压缩场景四轮讨论的回执都是 0 条发送、0 条省略。按桌面端的 5 秒超时，每次都会超时，记忆被静默丢掉。修复后脚本改用桌面端自己的超时。

各入口的情况（#270 和 #272 之后）：

- 编码简报和真实 Native v2 编码：任务是“把归档撤销时长设成和删除撤销相同的时长（以最后商定的为准）”。三次运行都写成 `ARCHIVE_UNDO_WINDOW_MS = 15000`，宿主运行的测试通过，每次约 0.2 美分。仓库里没有这个值，只有记忆里有。
- 阶段 Agent：澄清稿的提示里带了召回的记忆（`RECALLED_MEMORY_BACKGROUND`）。较早一次运行的澄清稿用上了 15 秒撤销、批量撤销最近一次和 ConfirmDialog 三个决定。
- Gate 评审：评审清单记录了 5 条项目记忆，另有 113 条超出预算未附带。评审结果保存后自动写入记忆，抽出 16 条。
- 讨论栏：两种协议都把记忆和沟通偏好一起发送（6 条），用中文提问时用英文回答；都会调用 `memory_search`，并从结果中回答。
- 超限时先去掉记忆：输入上限设得比带记忆的请求小一点时，两种协议都不发送记忆（回执里有 0 条发送、约 120 条省略），而且不压缩历史。
- 降级和归属：Hindsight 不可达时召回在 5 秒内降级为空、不报错；其他用户召回得到 null。

## 自动采集

验证过程中产生的讨论在空闲 3 分钟后写入，Coding Run 结束时写入，Gate 评审结果保存时写入，澄清被批准时写入，当天的提交在最后一个提交之后 30 分钟写入，最后都保存下来了。之后用“发布日期是哪天”召回，能找到压缩讨论里的 11 月 3 日。

## 编辑、遗忘和清空

- 遗忘一条记忆：选的是 Coding Run 简报里用过的一条。遗忘后它不再被列出或召回，那次 Coding Run 继续执行时被拒绝（“Coding Memory changed, expired or was deleted”）。
- 编辑一条记忆：编辑之前的回执变为过期，之后的有效；四个知识页立即清空；召回返回编辑后的文字。
- 遗忘来源：选的是含内部代号 Bluefin 的讨论。Hindsight 删除了该文档（之后查询返回 404），由它得到的 1 条事实和 1 条观察都没有了，召回也找不到；知识页清空两次，重写后不包含它。
- 重写知识页：编辑和遗忘之后，四页在约 2 分钟内写回，用了 24 次模型调用，花费 0.189 美元。编辑后的日期规则出现在新页里。
- 关闭和开启：关闭时不召回也不采集，重新开启后用的还是同一个 bank。
- 清空：换成新一代的 bank，旧 bank 被删除（返回 404），之前的召回全部过期；新 bank 为空，召回时没有降级。旧版记忆和之前的来源都不会再写入，新的讨论写入新 bank 后可以召回，旧记忆不会回来。

## 发现与处理

1. 召回在 bank 变大后超时（已修复，#270）：项目记忆 bank 关掉了交叉编码器，每次都要 8,192 tokens 的候选，并加重 BM25 的权重。数字见上表。
2. Native v2 压缩后不带记忆（已修复，#272）：修复前，压缩那一步的请求只用了 24,408 字节上限中的 19,370 字节，记忆放得下，但没有发送，最后一问用中文回答。修复后，压缩的各轮都带 6 条记忆，最后一问用英文回答“November 3, 2026”。
3. 自动采集会让记忆受到自身输出的影响（未修改）：验证本身的讨论、编码请求和澄清写进记忆后，产生了一些反馈：
   - 编码请求里的“注释按项目约定的语言写”被抽成一条事实“项目约定：代码注释须按项目约定的语言书写”。原来那条英文注释的约定被改写成“曾将注释语言统一为英文”。第一次成功的 Coding Run 写的是英文注释；之后两次运行时，前几次的编码请求已经写进记忆，这两次都写了中文注释。
   - 同样的归档需求重复了几次。最后一次阶段 Agent 召回的 5 条记忆都是前几次的澄清，没有包括 15 秒的决定。
   - 答复语言的观察被一段助手回复改写成“用户偏好助手用英语回复（助手称……）”。偏好本身还在。

   建议另行处理：降低只有助手陈述作为依据的事实的权重，在抽取说明里写明“请求里引用约定不等于新的约定”，并考虑合并重复的任务。
4. 结构化讨论超限时，沟通偏好随背景记忆一起被去掉（按 ADR 0024 §6 的设计，未修改）。压缩那几轮用中文回答。偏好最多 800 字节，可以考虑比背景记忆保留得更久。
5. 重写知识页的花费随记忆增多而增加（未修改）：约 570 条记忆时，四页重写一次花 0.189 美元，而 #269 在小 bank 上实测每页约 0.8 美分。每次编辑或遗忘都会清空全部四页。可以考虑把短时间内的多次修改合并成一次重写。
6. 阶段 Agent 偶尔收到不合法的 JSON（与记忆无关，未修改）：DeepSeek Flash 有时少写最后一个数组的 `]`。15 次中有 4 次失败，其中小实验里带记忆和不带记忆各 5 次，各失败 1 次。验证脚本像用户一样最多重试两次。可以考虑像讨论栏那样，对这种失败自动重试一次。
7. 其他观察：
   - 那段 57 KB 的长讨论大多是排查过程的记录，抽出了 85 条记忆。抽取说明要求忽略过程性内容，这一条没有完全做到。
   - 知识页是在抽取还在进行时写成的（4 页都早于最后一份文档保存），这次内容仍包含了全部后期决定。
   - Native v2 用中文提问、记忆偏好英文时，9 次里有 8 次用英文回答，另一次用中文回答，但按“先结论后原因”的偏好组织了内容。结构化讨论 3 次都用英文回答。
8. 没有通过的两项检查：
   - “删除和撤销的快捷键是什么”在讨论栏预算（4 条）里没有命中，相关记忆排第 6，在编码和阶段 Agent 的预算里都命中了。
   - consolidate 阶段之后，“答复语言”观察的文字改成了“英语”，检查只认“英文/English”。观察本身仍写着英文偏好，见第 3 条。检查已修正。

## 没有验证

- 桌面端界面，以及 Electron 主进程里实际的后台循环（脚本直接调用了同一个 worker、采集和召回代码）。
- 已配对的团队项目，以及按团队预算的中继路由；这次项目没有配对，花费记在本地账本里。
- OpenCode 执行器、仓库知识 bank（ADR 0027）、其他模型和提供方、Windows 和 Linux。
- 长时间的行为：Hindsight 6 小时一次的知识页刷新，以及几天里陆续产生的提交。

## 复现

```sh
corepack pnpm hindsight:up   # 令牌与中继端口见 docs/engineering/project-memory.md
DEVFLOW_MEMORY_LIVE_AUTHORIZED=1 DEVFLOW_MEMORY_LIVE_MAX_USD=1.5 \
DEVFLOW_MEMORY_RELAY_TOKEN=<与 Hindsight 相同的令牌> DEVFLOW_MEMORY_RELAY_PORT=8899 \
DEEPSEEK_API_KEY=<已授权的密钥，只在环境中> \
corepack pnpm exec tsx scripts/project-memory-full-validation.mts
```

从某个阶段续跑：设 `DEVFLOW_MEMORY_FULL_RESUME=<工作目录>` 和 `DEVFLOW_MEMORY_FULL_FROM=<阶段>`。`DEVFLOW_MEMORY_FULL_DRY=1` 只构造文档并做不花钱的检查。报告写在工作目录的 `report.json` 里。
