# 项目记忆多语言召回验证（2026-10-29）

#270 为了让中文问题召回到对的记忆，用 DevFlow 自己的中文 BM25 给 Hindsight 的结果重新排序，向量检索几乎不起作用。这次改为让 Hindsight 用多语言 embedding 自己排序，DevFlow 保持它的顺序。本文记录模型和参数的比较、部署与迁移检查，以及新配置下用真实模型重新抽取的验证。

## 方法

- 评估 bank：用[完整验证](project-memory-full-20261029.md)的数据重新抽取的一个 bank，52 份文档，200 条事实（world 164、experience 36），118 条观察。先用 Hindsight 的 bank 导出得到归档，再导入每种配置的独立实例。导入时用该实例的模型重新计算向量，不调用模型，所以各配置比较的是同一批记忆。
- 问题：完整验证的 25 个调参问题，加 20 个留出问题（#270 调参之后才写，措辞不同，4 个是英文），都在 `scripts/project-memory-full-fixtures.mts`。关闭图扩展是看过两组结果后决定的，所以留出问题对这一项不完全独立；独立的检查是下文用新配置重新抽取的 bank。
- 指标：按讨论栏（4 条、2,000 字节）和编码简报（8 条、4,000 字节）的预算，从 Hindsight 返回的顺序从前往后取，预期的词都出现算命中。MRR 按第一条含有全部预期词的记忆的名次计算。
- 环境：macOS，Docker 中的 Hindsight 1.0.0，限 2 个 CPU，与正式部署相同。机器负载在 5–15 之间，延迟有波动。

采用的一行在正式部署上测得（迁移后的 bank，见下文）。关闭重排时 Hindsight 仍按重排的候选上限截取候选：在上限设为 40 的实验实例上，采用的配置是 100% / 90%、MRR 0.93 / 0.80，「只留向量检索」一行也是在这个实例上测的。

重排的耗时随查询长度增加（多语言重排 40 个候选，5 次的中位数）：

| 查询长度 | 33 B | 297 B | 801 B | 1,398 B |
|---|---|---|---|---|
| 2 个 CPU | 2.0 s | 2.8 s | 4.6 s | 8.7 s |
| 4 个 CPU、4 线程 | 1.4 s | 2.4 s | 5.5 s | 6.5 s |
| 不重排（采用） | 37 ms | 36 ms | 68 ms | 118 ms |

编码简报的查询常有 1 KB 以上，重排会让它超过桌面端 5 秒的召回超时，记忆被静默降级为空。不重排时质量只差留出问题中的一两个，所以不用重排。

## 图扩展为什么有害

以「用户希望用什么语言回答？」为例（e5-small，开图扩展）。向量检索排第 1、2 的正是两条语言偏好（「用户要求以后都用中文回答」「用户要求从现在起用英文回答……」）。关键词检索对中文问题返回 0 条：Hindsight 的关键词索引按英文分词，镜像内置的 Postgres 没有中文分词扩展。图扩展沿共享实体返回 100 条事实，几乎每条都连着「user」，排在前面的是同步重试、分页条数这类无关决定。倒数排名融合时，向量第 25、图扩展第 4 的事实分数高于只有向量第 1 的事实，答案落到第 7，讨论栏只取 4 条，就漏掉了。关闭图扩展后答案排第 1。

## 排除的方案

- 只换成中文重排模型：质量最好，但如上表太慢；只重排前 20 个候选时质量明显下降。FlashRank 的 `ms-marco-MultiBERT-L-12` 单次召回超过 180 秒。
- `BAAI/bge-m3`：不重排时排序差，模型约 2.2 GB，导入 300 条记忆用了 278 秒。
- Hindsight 内的中文关键词检索：镜像内置的 Postgres 18.1 只有 `vector` 和 `pg_trgm`，中文需要外部 Postgres。按上游的 pgroonga 方案（`groonga/pgroonga:4.0.8-debian-17` 加 pgvector，`HINDSIGHT_API_TEXT_SEARCH_EXTENSION=pgroonga`，二元分词）试过：关键词检索对中文问题有了结果（一次返回 236 条），但质量下降，调参 / 留出的讨论栏命中 88% / 90%、MRR 0.73 / 0.68（采用的配置是 100% / 95%、0.87 / 0.92）。这个项目的记忆里「任务」「撤销」「删除」这类二元词到处都有，关键词检索的结果在融合中与向量结果同等计分，把排序拉乱了。下文多意图请求里注释语言那条记忆从第 19 位升到第 11 位，仍在编码简报的 8 条之外。没有采用。
- 云端重排（Cohere、阿里云等）：要另外付费，并把记忆原文发给第三方。

## 部署与迁移

- 镜像按 `deploy/hindsight/Dockerfile` 在本机构建，9 个模型文件都通过 SHA-256 校验，镜像 1.16 GB。启动日志确认加载 `/home/hindsight/models/multilingual-e5-small`，并使用 `query: ` / `passage: ` 前缀。
- `corepack pnpm test:hindsight-local` 通过：镜像的上游提交和 embedding 模型标签、新数据卷、健康检查、bank 配置重启后保留、测试 bank 清理。
- `corepack pnpm hindsight:migrate` 把旧卷 `devflow-hindsight_data` 的 12 个 bank 复制到新卷，没有调用模型。评估 bank 迁移前后都是 52 份文档、164 条 world、36 条 experience、118 条观察。上表采用的一行就是在这个迁移后的 bank 上测的。

## 新配置的真实模型验证

用新镜像和本分支的代码，按[完整验证](project-memory-full-20261029.md)的脚本从头抽取一个新 bank，跑 seed 到 agents（不含 Gate 评审、采集、编辑和清空，这些与排序无关）。抽取和归纳用 `deepseek-v4-flash`，编码和讨论用 `deepseek-flash`。

- 抽取与归纳：52 份文档抽出 206 条事实（world 170、experience 36），归纳成 118 条观察，29 条来自多条事实，最多一条来自 16 条；与上次（210 条事实、108 条观察）相当。6 个改变过的决定都有观察写的是最新值；另有 1 条观察仍写着「重试超过 3 次后，界面提示同步失败」，没有随重试改为 5 次而更新，上次没有这种观察。
- 召回（DevFlow 的实际召回路径，每个问题按三个入口的预算各召回一次）：

| | #270（英文 embedding + DevFlow BM25，上次的 bank） | 本次（多语言 embedding，Hindsight 排序） |
|---|---|---|
| 调参 25 题命中：编码简报 / 阶段 Agent / 讨论栏 | 100% / 100% / 96% | 100% / 100% / 100% |
| 调参 MRR | 0.81 | 0.90 |
| 留出 20 题命中 | 100% / 85% / 85% | 100% / 100% / 100% |
| 留出 MRR | – | 0.88 |
| 延迟 p50 / p95 / 最大 | 42 ms / 93 ms / 566 ms | 26 ms / 35 ms / 121 ms |

- 知识页：四页都有预期内容和后期决定。
- 讨论：Native 和结构化两种协议都带上项目记忆、按记忆用英文回答，都调用了 `memory_search` 并据此回答；压缩历史后，放得下的记忆重新附上。
- 编码：Native v2 运行完成，主机测试通过，按记忆把撤销窗口设为 15000 ms。第一次运行在分析阶段失败：模型列出了仓库清单之外的路径（`native_v2_analysis_path_not_in_manifest`），花费不到 0.1 美分。简报里有一条记忆提到仓库中不存在的 `src/undo/use-undo-toast.ts`，但模型输出没有保存，无法确认是否由它引起。重跑 agents 阶段后通过。
- 检查：最后一次报告 74 项检查全部通过。

### 发现：一个请求里有两件事时，次要的那件可能召回不到

编码请求是「把 `ARCHIVE_UNDO_WINDOW_MS` 设成和删除任务的撤销窗口相同的时长……注释按项目约定的语言写」。向量检索按整句的意思排序，前 8 条都是撤销窗口相关的记忆；两条注释语言的记忆（「代码注释统一使用英文」）排在第 25 和第 50 位，没有进入简报，代码注释写成了中文。上次用 DevFlow BM25 融合时，第一次编码运行写的是英文注释；BM25 会给含「注释」「约定」的记忆加分。上面 45 个只问一件事的问题没有这个问题。上游为中文推荐的 pgroonga 关键词检索也没有把它排进前 8（见「排除的方案」）。还没有试的做法有：把请求按句拆开分别召回再合并，或用 ParadeDB `pg_search` 的 `jieba` 分词。
